実行の履歴に「failed」と 1 語で書かれた回が並ぶと、同じ段で同じように落ちた回に見える。この記事では、エラーの欄を行に割り、人が登録した印がどこまで出てから止まったかを、回ごとに原文のまま並べる部品を作る。止まった理由は当てない。

**なぜ重要か**: 週に 1 回動く取込や集計の履歴は、たいてい状態の 1 語と、落ちたときのエラーの文字列を 1 行に持っている。状態の欄を数えれば「落ちたのは何回」とは言える。エラーの欄の 1 行目を読めば「どの段で落ちたか」も言える。けれども段の中には検査がいくつも入っていて、落ちる前に「何行読んだ」「重なりは何件」のような行を順に出していることがある。**同じ段の名前で止まった 2 回でも、その行がどこまで出ているかは同じとは限らない。** エラーの欄は長い 1 つの文字列なので、履歴を表にして眺めても、この違いは列にならない。

**要点**:
- 印は人が登録した字を、行頭にそのまま当てる。**字面から印を見つける経路は持たせない**
- 返すのは、印が在るか無いか・何行目か・印の後ろの文字列まで。**止まった理由は分類しない**
- 印の後ろの文字列は数に直さない。どちらが期待でどちらが実際かも当てない
- 実行した場所のパスのように写したくない行は、登録した字で伏せて、件数だけ返す

**数字で見る**: 合成した 4 表(回 16 行)を通すと、**状態が failed の 8 回が、下の層では 4 通りの区分に分かれた**。私の記録の 11 回では、failed の 2 回は上の層では同じ段で、下の層では「登録した印が全部在る」が 1 回、「一部が無い」が 1 回だった。残る 9 回はエラーの欄が空だった。

---

## 何を解決するのか

### 上の層では、2 回は同じ段で止まっている

材料は私の記録にある。社会保険や雇用保険の数表を公式の資料から取り込み、検証してから入れ替える道具の、実行の履歴だ。1 行が 1 回で、11 行在る。作業状況の記録の 99 行目にはこう書かれている。

```
パイプライン実行履歴: 11 回 (ok 9 / failed 2 = 意図的な失敗試験)。
```

`status` が `failed` なのは履歴の 3 行目と 4 行目で、`error` の欄が空でないのもこの 2 行だけだ。残る 9 行は `"error": null` になっている。

段の並びは、同じ記録の 50 行目に在る。

```
→ extract ×3 (自己整合 assert) → unify (validate + fixture) → formulas (検算) → diff → manifest / CHANGELOG
```

2 行の `error` は、どちらも 1 行目が `unify failed:` だ。つまり上の層で言えるのは「2 回とも unify の段で止まった」までになる。同じ記録の 96 行目には、検証の表の 1 行として「パイプラインの失敗経路 (上流値の改ざん / 重複期間)」という項目が在り、結果の欄に「09-19 の run 3・4」と書かれている。括弧の中に 2 つ、run も 2 つだが、**どちらがどちらに当たるかは 96 行目には書かれていない。**

以前、同じ 11 回を回の種類に分ける部品([run_kinds](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/run_kinds))を作った。あの部品は `error` の列を入力に持たず、「失敗の原因を分類しない」と限界に書いた。今回はその `error` の中に降りる。ただし降りても、原因を当てるところまでは行かない。

### エラーの欄の中に、段の中の検査が出した行が残っている

`error` の文字列を改行で割ると、3 行目の回は 29 行、4 行目の回は 25 行になる(どちらも末尾の空行を含む)。1 行目が `unify failed:`、2 行目が `rows by rule:`、3〜17 行目が rule の名前と行数の 15 行、18 行目が `total rows: 1301` で、ここまでは 2 回とも同じ字だ。

19 行目で分かれる。

```
3 行目の回  19 行目  validate overlaps: 0
4 行目の回  19 行目  validate overlaps: 6
```

3 行目の回は、その後に `MISMATCH` で始まる行が 3 行続き(20〜22 行目)、23 行目にこう在る。

```
fixture cross-check: 200/250 match, 50 mismatch
```

その先が `Traceback` で、26 行目が `assert bad == 0`、28 行目が `AssertionError` だ。4 行目の回は、19 行目のすぐ後が `Traceback` で、24 行目が `AssertionError:` で始まり、rule の名前と出典の名前の組が後ろに続く。`MISMATCH` も `fixture cross-check:` も、4 行目の回の `error` には無い。

**上の層では同じ「unify で failed」の 2 回が、下の層では、出した行の数も、最後に出した行も違う。** これを毎回目で追う代わりに、行頭の字を「印」として登録しておき、回ごとに在る・無いを並べたい。

### 読みすぎになりやすい所が 4 つ在る

エラーの文字列は、読もうと思えばいくらでも読める。だから先に、読まないと決めた所を書いておく。

ひとつめ。`MISMATCH` の行は 3 行だが、23 行目は 50 mismatch と書いている。**3 行は表示された行の数で、不一致の件数ではない。** 道具も「この印が 3 行在る」と返すだけで、件数とは呼ばない。

ふたつめ。20 行目はこういう形をしている。

```
  MISMATCH {'prefecture': 'Tokyo', 'health_grade': 1, 'smr': 58000, 'health_half': 2856.4999999999995,
            'health_ltc_half': 3326.2999999999997, 'pension_half': None} (2897.1, 3366.9, None)
```

波括弧の中に値が在り、後ろの括弧の中にも値が在る。どちらが期待した値で、どちらが実際に出た値かは、`error` のどこにも書かれていない。だから当てない。印の後ろの文字列として、そのまま置く。

みっつめ。96 行目の「上流値の改ざん / 重複期間」と、2 回のどちらがどちらか。`overlaps: 6` や `MISMATCH` の字から察しはつくが、それは私の読みで、記録に書かれた対応ではない。道具は結ばない。

よっつめ。`error` の中には、実行した場所の絶対パスを含む行が各 1 行在る(3 行目の回の 25 行目、4 行目の回の 21 行目)。この行は記事にも図にも写したくない。道具には「この字を含む行は伏せる」という登録表を持たせ、中身を返さずに件数だけ返すようにした。

行は回で、履歴の 3 行目と 4 行目の 2 回だ。いちばん左の列が上の層で、状態の 1 語と段の名前を置いた。2 行とも同じ字になる。その右が下の層で、私が登録した印を並び順どおりに置いている。藍の淡色が「登録した印が在る」、無彩色が「無い」だ。

違いは 3 か所に出る。重なりの印の後ろの文字列が ` 0` と ` 6` で違う。不一致の印と突き合わせの印は、上の行にだけ在る。止まった印は両方に在るが、行番号と後ろの文字列が違う。

**原因の列は置いていない。** 良い・悪いの列も、文字列を件数に直した列も無い。印と段の対応は私が登録したもので、道具が字面から当てたものではない。`MISMATCH` の 3 行は表示された行の数だ。伏せた行が各 1 行在り、残る 9 回はエラーの欄が空なのでこの表には出していない。手元の 11 回だけの話で、網羅ではない。

## 手順

ひな型を出す。回の台帳・印の登録表・段の登録表・伏せる行の登録表の 4 表が出る。

```
python halt_depth.py init ひな型/
```

印の登録表に、行頭の字を書く。`text` が印の文字列で、前の空白も字のうちになる。`order` は並び順の整数、`kind` は `通過の印` か `止まった印` の 2 語だけだ。

```csv
mark_id,text,stage,order,kind,source
M1,unify failed:,U,1,通過の印,私の印の登録
M2,total rows:,U,2,通過の印,私の印の登録
M3,validate overlaps:,U,3,通過の印,私の印の登録
M4,  MISMATCH,U,4,通過の印,私の印の登録
M5,fixture cross-check:,U,5,通過の印,私の印の登録
M6,AssertionError,U,6,止まった印,私の印の登録
```

`M1` が段の名乗り、`M2` が行数の印、`M3` が重なりの印、`M4` が不一致の印、`M5` が突き合わせの印、`M6` が止まった印、というのが私の呼び方だ。`通過の印` は「止まる前に出た行」という意味で付けていて、検査に通ったという意味ではない。`M4` は前に空白が 2 つ在る。

段の登録表は、印の `stage` の記号を、上の層の段の名前に結ぶ。

```csv
stage,name,source
U,unify (validate + fixture),作業状況の記録 L50
```

伏せる行の登録表には、写したくない行に含まれる字を書く。

```csv
text,source
"  File """,私の登録
```

回の台帳は、履歴のファイルをそのまま渡した。1 行 1 回の JSON なら、道具が `status` と `error` の欄を読み、回 id を行番号から `L3` のように付ける。手で写さないので、写し間違いが入らない。

```
python halt_depth.py check 実行の履歴.jsonl 印.csv 段.csv 伏せる行.csv --label 実行の履歴
```

上の層の「段」は 2 回とも同じ字で、下の層で分かれた。3 行目の回は、登録した通過の印が 5 つとも在り、止まった印も在る。4 行目の回は、重なりの印までが在り、不一致の印と突き合わせの印が無く、止まった印が在る。

ここで言えるのは「この印が在った・無かった」までだ。4 行目の回で不一致の印が無いのは、突き合わせの検査まで進まなかったからだろう、と私は読んでいる。けれどもそれは、印の並び順と検査の順が同じだという私の登録に依った読みで、道具が返したものではない。

補助の印は 2 つ付いた。`M4` が 3 行目の回の中に 3 行在ること、そして `M3` と `M6` の後ろの文字列が 2 回で違うことだ。`M3` は ` 0` と ` 6`、`M6` は空の文字列と、rule の名前の組が続く文字列になる。**道具は ` 0` と ` 6` を数として比べていない。** 字が違う、と返しているだけだ。

どの印にも当たらなかった行は、2 回とも 19 行在る。rule の名前と行数の 15 行や、`Traceback` の行がここに入る。これらを印として登録するかどうかは、私が決めることになる。伏せた行は各 1 行で、中身は出力のどこにも出ていない。

最後に、手続きそのものが決定論かを測る。

```
python halt_depth.py verify 実行の履歴.jsonl 印.csv 段.csv 伏せる行.csv --label 実行の履歴
```

`verify` は 5 つ見る。二度走らせて判定部分の指紋が同じか。登録表 3 つの行順を逆にしても指紋が同じで、回の台帳を逆にしても回ごとの結果が同じか。区分と別枠の合計が回の台帳の行数に戻り、行の内訳の合計が行数に戻るか。印を 1 つ抜いても、残りの印の在る・無い・行番号・後ろの文字列が変わらないか。そして、後ろの文字列のどれにも伏せる字が無いか、だ。手元の履歴では 5 つとも通った。

## 検証

数字の出どころは、合成した 4 表に対するテストになる。段の名前も印も架空のもので、実在の記録は入っていない。伏せる行も合成のパスで試している。

```
$ python -m pytest tools/halt_depth -q -s
[measure] runs_a / marks_a / stages_a / hides_a: 回の台帳 16 行 / 印の登録 12 行 / 段の登録 4 行 /
          伏せる行の登録 2 行
[measure] 区分は (A) 2 / (B) 3 / (C) 2 / (D) 4 / (E) 2(合計 13 回)、別枠の回は 3 回。
          合計 16 = 回の台帳の行数。使った印は 6 個、別枠の印は 5 枠で 6 行
[measure] 状態が failed の回は 8 回で、区分は (A) 2 / (B) 3 / (C) 1 / (E) 2 の 4 通りに分かれる。
          (B) の 3 回で、在った通過の印のうち並び順が最後のものは ['K2', 'K1', 'K3'] と 3 回とも違う
[measure] エラーの欄を割った行は合わせて 40 行で、印に当たった行 27 / 伏せた行 4 / 空の行 4 /
          どの印にも当たらなかった行 5。4 つの合計は行数に戻る
[measure] 補助の印: 同じ印が 1 回の中に 2 行以上在るのは 2 件(3 行と 2 行)、
          後ろの文字列が回によって違う印は 6 個。後ろの文字列を落とし重なりを消しても、
          区分が同じだった回は 13/13
[measure] 状態の文字列を 16 行すべて ok に替えても、区分が同じだった回は 13/13
          (状態の語は写すだけで読まない)
[measure] 伏せた行は 4 行。伏せた行に在った字 6 通りは出力のどこにも無い(0/6)。
          印が伏せた行に当たった 1 件は、在る・行番号 1・後ろの文字列は空で返る
[measure] 印に似ているが行頭の字が違う 7 通り(前に空白・大文字・前に 1 字・コロン無し・
          空白の数が違う)は、当たった印が 0 件で 7 回とも (C)
[measure] 後ろの文字列が 120 / 0120 / 120.0 の 3 回は、3 つとも原文のまま返り、
          「回によって違う」の印が付く(区分は 3 回とも同じ)
[measure] 登録表 3 つの行順を 5 通りに並べて読み直し: 判定部分の sha256 は 5 回とも同じ
          (5/5 一致、先頭 12 桁 4d9f793acb86)。回の台帳を逆順にすると、
          回ごとの結果は同じで並びだけが逆になる
[measure] verify: 5 つとも通る。印を 1 つ抜いても残りの印の在る・無い・行番号・
          後ろの文字列が変わらない(6/6)。後ろの文字列に伏せる字は 0 件
[measure] 止まる理由コードは 5 個。崩し方 8 通りは 8 通りとも区分を 1 回も返さずに止まる(8/8)
[measure] 表として読めない崩し方 6 通りは 6 通りとも例外で止まる(6/6)。登録表 3 つは 0 行でも読め、
          そのときはエラーの文字列が在る 9 回がすべて (C)、空の 4 回が (D) になる
[measure] 1 行 1 回の JSON 3 行を回の台帳として読むと、回 id は L1〜L3、
          エラーの欄が null の回は (D)。末尾の改行は空の 1 行に数え(3 行)、CRLF は LF として割る(2 行)
[measure] コマンドの終了コードは check 0 / verify 0 / 読めない表 2 / 理由コードで停止 3。
          走らせる前後で入力 4 ファイルの sha256 は同じ。ひな型は 4 表で、既に在るファイルは書き換えない
[measure] 部品が import している module は 7 個で、eval / exec / compile / float / round / 正規表現 /
          現在時刻 / 通信 / 外部コマンド の呼び出しと小数の定数は 0 件。
          出力に原因・理由・期待の欄は無く、「持たせていないもの」は 7 行
16 passed
```

読みどころは 3 つある。

ひとつめが、1 語の下に何通り在ったかだ。合成の台帳では、状態が `failed` の回が 8 回在る。下の層に降りると、登録した印が全部在る回が 2 回、一部が無い回が 3 回、印が 1 つも無い回が 1 回、通過の印は在るが止まった印が無い回が 2 回に分かれた。**一部が無い 3 回も、どの印まで在ったかは 3 回とも違う。** 状態の欄だけを数えていると、この 8 回は同じ 1 つの数になる。

ふたつめが、読まないと決めた所が区分に混ざらないことだ。状態の文字列を 16 行すべて同じ語に替えても、区分は 13 回とも変わらない。印の後ろの文字列を全部落としても変わらない。後ろの文字列が `120` と `0120` と `120.0` の 3 回は、3 つとも原文のまま返り、「回によって違う」の印が付く。数としては同じでも、字が違えば違うと返す。数に直す経路が無いことを、ここで確かめている。

みっつめが、伏せる行だ。合成の記録には、伏せる字を含む行が 4 行在る。その行に在ったファイルの名前や行番号の字を 6 通り探しても、出力のどこにも無い。印の字で始まる行が伏せる行でもあった 1 件は、「在る」と行番号だけが返り、後ろの文字列は空になる。伏せる行の登録表を空にすると、同じ字が出力に出てくることも見ている。伏せているのは登録した字で、道具がパスらしさを当てているのではない。

いつも成り立つことは 1 文にして、性質テストで確かめている。結果は 2 通りしかない。回 1 行ごとに区分 5 値か別枠のどれか 1 つだけが付き、その合計が回の台帳の行数に等しく、印が「在る」と返るのは登録した字が行頭にそのまま在る行だけで、行の内訳の合計がエラーの欄の行数に戻り、伏せる字を含む行の中身はどの欄にも出ず、登録表の行順を入れ替えても判定部分が同じバイト列になるか、1 回も並べずに理由コードが 1 つ返るか、だ。どちらの場合も 4 表は書き換わらない。区分と在る・無いの決め方はテストの側に別に書いてあり、部品の判定を呼ばずに決め直して突き合わせる。乱数は固定で、毎回同じ 300 通りになる。

## 図 2 状態の 1 語から印の表へ降りる流れ

![回の台帳と登録表 3 つを読み、エラーの欄を行に割り、伏せる行を外し、行頭の字で印を当て、回ごとに並べ、補助の印を付け、件数を検算して指紋を取るまでの流れ図](figures/halt_depth_flow.png)

段は 8 つで、橙のピルが止まる場所と別枠、それに伏せた行の出口になる。1 段目が上の層で、状態は 1 語のまま、エラーの欄は 1 つの文字列のまま受け取る。3 段目で改行ごとに割って、下の層に降りる。

4 段目を見てほしい。伏せる行は、登録した字を含むかどうかだけで決まり、そこから先へは件数しか送られない。**伏せた行の中身が出口に届く矢印は無い。** 印の字で始まっていれば「在る」と行番号は返るが、後ろの文字列は空になる。

5 段目の印は、行頭の字がそのまま同じかどうかだけで当てる。前に空白が 1 つ多くても、大文字と小文字が違っても当たらない。正規表現は使っていない。6 段目の区分は 5 値で、7 段目の補助の印は区分を決めた後に付ける。

この図で見てほしいのは、描かれていない経路のほうだ。**「原因」へ出る矢印が無い。** 後ろの文字列を数に直す矢印も、期待と実際を分ける矢印も、上流の変化か実装の不具合かを分ける矢印も無い。実装でもそういう引数を持たせていない。

役割が重ならないことも書いておく。回を種類(初回・据え置き・入れ替わり など)に分ける話は [run_kinds](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/run_kinds)、回ごとの件数と判定を台帳に並べる話は [update_ledger](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/update_ledger) という別の道具が扱っている。この部品が読むのは、エラーの欄の中だけになる。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/halt_depth) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。通信の経路も、現在時刻を読む呼び出しも、浮動小数点も、正規表現も持たない。コマンドとしても関数としても呼べる。

手元で書くのは登録表 3 つで、重いのは印の登録表になる。自分のバッチが落ちる前に出す行を眺めて、行頭の字を写す作業だ。**印に `通過の印` と付けても、検査に通ったという意味にはならない。** 「この行が出た」という意味でしかないので、不一致を知らせる行も、出たなら通過の印の側に入る。止まった印は、例外の名前のように、止まるときに出る行の頭の字を登録する。

区分は 5 値にした。止まった印が在って通過の印が全部在る回、一部が無い回、印が 1 つも無い回、エラーの欄が空の回、それに、通過の印は在るのに止まった印が無い回だ。最後のものは、途中で外から止められた記録や、止まった印の登録が足りないときに出る。どれに当たるかは道具には分からないので、区分の名前は「無い」とだけ言っている。

合成した 4 表が置いてあるので、同じ数字が手元で出るかを確かめられる。使い方として想定しているのは、落ちた回が 2 つ以上たまったときに 1 回通すことだ。出るのは回ごとの印の在る・無いと、行番号と、後ろの文字列と、区分だけで、順位も点数も出ない。

## 別の業種なら

この部品が持っている欄は、回 id・状態の文字列・エラーの文字列・印の文字列・出典だけで、給与や社会保険の言葉は入っていない。どの業種でも、夜間の取込や集計が「失敗」の 1 語で記録され、同じ段の名前で止まった回が並ぶ、と私は考えている。会計なら、仕訳の取込が同じ「検証で失敗」でも、件数の確認までは出た回と、貸借の一致の確認まで出た回が在りそうだ。通販なら、受注の同期が同じ段で落ちても、在庫の突き合わせの印が残っている回と残っていない回に分かれそうに見える。製造なら、実績の集計が止まった回のエラー文に、工程ごとの件数の印がどこまで出ているかが違う、ということが起こるかもしれない。印の登録表と入力例の業種を変えるだけで同じ表が書けるはずだが、私が測ったのは合成した 4 表と、自分の記録の 11 回の範囲だけなので、ほかの業種は同じ詰まり方になりそうな例であって実測ではない。

## できないこと

- **止まった理由は分からない。** 返すのは、登録した印が在ったか無かったかまでだ。上流の値が変わったのか、実装に不具合が在ったのかは分けていない
- **印が無いことは、その検査が走らなかったことを意味しない。** 行を出さずに通る検査も在る。印の並び順が検査の順と同じだというのも私の登録で、道具は確かめていない
- **印の後ろの文字列が正しいかは返さない。** ` 1301` や ` 200/250 match, 50 mismatch` を、写して並べただけだ。どちらが期待でどちらが実際かも当てていない
- **`MISMATCH` の 3 行は表示された行の数だ。** 不一致の件数ではない。件数に当たる字は別の行に在り、それも文字列のまま置いている
- **印の登録は私の読みだ。** 別の人が同じエラー文を見れば、`Traceback` や `rows by rule:` も印に登録するかもしれない。件数はその登録の結果になる
- **伏せる行は、登録した字を含む行だけだ。** 登録していない形で場所や名前が出ていれば、そのまま出力に出る。印の後ろの文字列は原文のまま返るので、公開する前に人が読む必要が在る
- **エラーの欄が 1 つの文字列で残っていることが前提になる。** 落ちたときの出力を履歴に残していない仕組みには当てられない
- 上の件数は合成した 4 表と、自分の記録の 11 回に対する測定で、ほかの人の環境で同じ数字になるとは限らない
