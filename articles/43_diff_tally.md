前回は、確かめた記録のほうの件数を層へ分けた。今回は同じ記録のもう一方、つまり**動いた記録のほう**を読む。骨は 1 行で言える。**「表が変わったか」には独立な 2 経路の数があり(差分の記録に出る増えた / 減った / 中身が替わった行数と、出力の指紋)、同じ回について別の答えを返す回が実際に在る。片方だけを見て「変わっていない」と書くと、もう片方が変わった回を取りこぼす。**

**なぜ重要か**: 私の記録には、自動更新の実行履歴が 1 ファイルある。1 行が 1 回の実行で、その 1 行が 2 経路の数を両方持っている。左のほうに差分の件数(増えた / 減った / 中身が替わった行数)、右のほうに出力の指紋。**記録は両方持っているのに、引用されて外に出るときは片方だけが出る。** そして実際に、同じ回について 2 つが別の答えを返している行がある。差分は 0 と書いてあるのに指紋は前の回と違う行があり、逆に差分が 0 でないのに指紋が過去の回の文字列に戻っている行もある。どちらも「変わっていない」とも「変わった」とも、片方だけでは書けない。

**要点**:
- 「変わったか」を 2 経路に分けて、同じ行に並べる。差分の件数と出力の指紋を、どちらが正しいかを決めずに、差だけ出す
- 判定は隣り合う回の対に付ける。差分が 0 か、指紋が前の回と同じか、の 2 つの軸で 4 通り。加えて、差分の欄が記録されていない回と、指紋が記録されていない回を別の値にする
- **指紋が前の回ではなく過去のどれかの回と同じ文字列に戻った対には、別に印を付ける。** 前の回と比べるだけでは、戻りは「動いた」としか見えない
- 中身が替わった行数は、差分の記録では「動いた」と言うのに行の数は動かさない。**累積に足す関数そのものを道具に置かない**

**数字で見る**: 合成した 5 枚(実行の記録 13 行 / 棚卸し 2 行 / 欄の登録表 3 行 / 結果記号の登録表 3 行 / 差の理由の宣言表 3 行)を通すと、**回の対 12 件が 6 値に分かれ、2 経路が別の答えを返した対が 2 件、指紋が過去の回へ戻った対が 2 件**になり、**累積 1,681 行は棚卸しの宣言 1,681 行と一致する一方、中身が替わった行数の 3 件を足した 1,684 では合わなくなる**。

## 何を解決するのか

### 記録は 2 経路を同じ行に持っている

私の記録の実行履歴は、1 行に 6 つの欄がある。いつ走ったか、結果の記号、上流の版、差分、出力の指紋、エラー。このうち **差分と指紋が、独立した 2 経路**だ。差分は「何行増えて何行減って何行の中身が替わったか」を数えた記録で、指紋は「出力のファイルそのものが同じ文字列か」を見た記録になる。

作りとしては、これは正しい。同じファイルについて別の角度から 2 回測っているからだ。問題は**読むときに片方しか出てこない**ことで、しかも 2 つが別の答えを返す回が、11 行のうちに実際に在る。

### 差分 0 なのに指紋が変わった回が在る

記録の 9 行目は 180 行足した回で、指紋も新しい。その次の 10 行目は、差分が増えた 0 / 減った 0 / 中身が替わった 0 と、全部 0 で記録されている。**それなのに指紋は前の回と違う。**

差分の記録だけを読めば「この回は何も変わっていない」になる。指紋だけを読めば「この回で出力は変わった」になる。どちらも記録に書いてある。並べて初めて、食い違っていることが見える。

同じ記録の中には、2 経路が揃う形もちゃんと在る。10 行目と 11 行目は差分 0 で指紋も同じで、収録範囲をまとめたほうの記録にも「冪等性 | offline 再実行で差分 0、sha 同一」と、その形が言葉で書いてある。**つまり 2 経路が揃うことを前提にした書き方をしているのに、揃わない回が隣に在る。**

### 指紋が前に戻ったのに差分が 0 でない回も在る

もうひとつ、逆向きの形がある。記録の 5 行目は 1 行足して 1 行の中身が替わった回で、指紋は新しい。その次の 6 行目は、1 行減って 1 行の中身が替わったと記録している。**差分は 0 でない。それなのに指紋は、1 行目・2 行目と同じ文字列に戻っている。**

これは前の回とだけ比べていると見えない。前の回とは違うのだから「動いた」になる。けれど過去の回まで見ると、**出力は前に出したものと同じ状態に戻っている**。足して引いたのだから当たり前に見えるが、記録の上では「動いた」としか残らない。だから私は、前の回との比較とは別に、**過去のどれかの回と同じ文字列かどうかの印**を分けた。

### 差分の欄そのものが空の回も在る

11 行のうち 2 回は、結果の記号が失敗で、差分も指紋も記録されていない。収録範囲の記録のほうには、上流の値を崩した試験と期間の重なりを作った試験の 2 つで、本番ファイルの指紋が変わらないことを確かめた、と書いてある。つまり本番の出力を差し替えていない回になる。

ここで気をつけたのは、**差分の欄が空なのを 0 と読まない**ことだ。0 と読むと「変わっていない回」に混ざる。実際には「測っていない回」で、意味がまるで違う。だから別の値にして、そこで判定を止めている。

### 差分の 3 つの欄は、同じ単位ではない

もうひとつ、同じ 1 つの差分の中にも食い違いがある。行の数を動かすのは増えた / 減ったの 2 欄だけで、**中身が替わった行数は行の数を動かさない**。記録の 8 行目には、同じキーの文言が別の文言に差し替わった例が中身の見本として載っていて、キーは増えても減ってもいない。

それでも、中身が替わった行数は差分の記録の側では「動いた」と言っている。つまり**同じ欄が、累積では足してはいけないのに、変化の判定では無視してはいけない**。この二面性が、片方の経路だけを見るときにいちばん紛れる。

### 累積は棚卸しと突き合わせられる

ここまでは食い違いの話だが、2 経路を分けると突き合わせられるものも出てくる。結果の記号が成功の回だけについて、増えた行数から減った行数を引いて積み上げると、収録範囲の記録が宣言している行数とそろう。**ただし中身が替わった行数まで足すと、その分だけずれる。**

そして「落ちた回を累積に入れるかどうか」は、差分の欄ではなく結果の記号の側の宣言で決まる。私の記録の README にも「検証に落ちれば `manifest.json.status = failed`、本番 `rules_unified.json` は前回のまま」と書いてある。**累積の定義は、回の側ではなく記号の登録のほうに在る。** だから道具でも、その宣言を別の表として外に出した。

この図は論評ではなく、1 つのファイルの 11 行をそのまま 2 経路へ割り直したものだ。行が実行 1 回、左から、経路A の値と出典、経路B の値と出典、差、差が生じる既知の理由、単位、対象の期間になる。出典はファイル名を伏せた行番号で書いた。

**どちらの経路が正しいかの列は置いていない。** 一致率の行も、合計の行も置いていない。単位が違うので足せないからだ。いちばん右の 2 列が、この図でいちばん地味で、いちばん効いている部分になる。単位と期間を先に宣言しないと、並べた 2 つが本当に同じものを指しているか分からない。

淡い無彩色の左端が、差分の記録の側だ。原文の件数をそのまま写した。淡い藍が、2 経路が同じ答えを返した行になる。

淡い橙が、食い違った行と、記録が無い行だ。10 行目が「差分は変わっていない / 指紋は変わった」で、6 行目が「どちらも動いたが、指紋は過去の回へ戻った」。3 行目と 4 行目が、差分も指紋も記録されていない回。5 行目は、前の回の指紋が無いので比べられない回になる。**橙が 5 行、つまり 11 行のうち 5 行は、片方の経路だけでは書けない。**

いちばん下が累積の行だ。左が差し替えた回の(増えた − 減った)で 1,681 行、右が棚卸しの宣言で 1,681 行、差は 0。**この行だけは 2 経路が別のものを指している**(片方は実行の積み上げ、もう片方は宣言された現在の行数)ので、単位の列に「行」とだけ書いて、指紋の経路が入らないことを明示した。

## 手順

ひな型を出す。実行の記録の台帳・棚卸しの台帳・欄の登録表・結果記号の登録表・差の理由の宣言表の 5 枚が出る。

```
python diff_tally.py init ひな型/
```

実行の記録の台帳には、実行 1 回を 1 行で書く。

```csv
run_id,seq,status,added,removed,changed,fingerprint,source
R01,1,S1,1301,0,0,sa010000000000000000,合成の実行履歴のメモ(架空)L1
R03,3,S2,記載なし,記載なし,記載なし,記載なし,合成の実行履歴のメモ(架空)L3
R10,10,S1,0,0,0,se050000000000000000,合成の実行履歴のメモ(架空)L10
```

列は 8 つで、**日付の列も時刻の列も無い**。順番は `seq` だけで決まる。記録が無い欄には `記載なし` と書く。空欄にはしない。空欄と「記録が無い」は別のことで、空欄のほうは読めない件数として別の扱いになるからだ。`fingerprint` は文字列をそのまま入れる。**道具はこれを計算しない**(ファイルを読んで hash にする経路を持っていない)。長さが揃っていなければ、そこで止まる。

棚卸しの台帳には、時点 1 つを 1 行で書く。

```csv
asof,rows,rules,source
A1,1301,15,合成の収録範囲のメモ(架空)L1
A2,1681,45,合成の収録範囲のメモ(架空)L2
```

突合に使うのは**時点記号の並びで最後の 1 行だけ**で、残りは「突合に使っていない棚卸しの時点」の一覧へ出す。黙って落とすと、どの時点と比べたのかが後から分からなくなる。

欄の登録表が、この道具のいちばん大事な表になる。

```csv
field,moves,unit,source
added,増やす,行,合成の登録のメモ(架空)L1
removed,減らす,行,合成の登録のメモ(架空)L1
changed,動かさない,行,合成の登録のメモ(架空)L1
```

`moves` が「行数を動かすか」で、`増やす` / `減らす` / `動かさない` の 3 つしか受け取らない。**3 つめが「行の数は動かない」という意味になる。** 累積に入るのは前の 2 つと宣言された欄だけで、3 つめと宣言された欄が累積に入る経路は、道具の中に無い。単位記号は `行` か `回` のどちらかで、**登録の外なら表として読めない**。単位を書かないまま並べさせない、という形にしてある。

結果記号の登録表で、累積の定義を宣言する。

```csv
status,replaces,cumulative,source
S1,差し替える,入れる,合成の登録のメモ(架空)L1
S2,差し替えない,入れない,合成の登録のメモ(架空)L1
S3,差し替えない,入れない,合成の登録のメモ(架空)L1
```

`replaces` が「本番の出力を差し替えるか」、`cumulative` が「累積に入れるか」になる。**この 2 つを別の列にしたのは、同じではないからだ。** 差し替えていないのに累積に入れたい回もあれば、その逆もある。どちらも人が宣言する。

差の理由の宣言表は、空でもよい。

```csv
from_run,to_run,reason,source
R02,R03,上流の値を崩した試験の回,合成の理由のメモ(架空)L1
R09,R10,出力の並べ方を変えた回,合成の理由のメモ(架空)L2
```

**この表に書いた分だけが、出力の「差が生じる既知の理由」に写る。** 書いていない対は `宣言なし` のままになる。原因を当てる辞書も、文字列から推測する経路も持っていない。隣り合っていない対を指す宣言は、止めずに別の一覧へ出す。

並べる。

```
python diff_tally.py check 実行の記録の台帳.csv 棚卸しの台帳.csv 欄の登録表.csv 結果記号の登録表.csv 差の理由の宣言表.csv
```

一致率を返す呼び方は無い。返るのは件数と分母だけで、**最後に並ぶ 14 行は消せない**。`pairs` にすると、判定ごとの一覧、**2 経路が別の答えを返した対の一覧**、片方の欄が記載なしの対の一覧、**戻りの印の一覧**(一致した実行 id つき)、突合に使っていない棚卸しの時点の一覧、どの対にも当たらない理由の宣言の一覧が出る。

上から順にどう見ているかも書いておく。出典が空、差分の欄が登録表に無い、結果記号が登録表に無い、順序番号が重複または飛んでいる、件数が整数でない、指紋の長さが揃っていない、棚卸しの時点記号が重複している、理由の宣言が実在しない実行 id を指している。このどれかが 1 行でも在れば、**どの対も数えない**。相手の「2 経路が別の答え」に、この部品の「読めない」を混ぜないためだ。

そこを抜けてから、隣り合う対を作る。差分の欄に `記載なし` が在ればそこで終わり、どちらかの指紋が `記載なし` でも終わり。その先ではじめて、差分の 3 欄が 0 かを見て、指紋の文字列を比べる。

最後に、この手続き自体が決定論かどうかを実測する。

```
python diff_tally.py verify 実行の記録の台帳.csv 棚卸しの台帳.csv 欄の登録表.csv 結果記号の登録表.csv 差の理由の宣言表.csv
```

`verify` は 5 つ見る。2 回読んで判定部分のバイト列の指紋が同じか、3 通りの入れ替え方で 5 枚の行順を入れ替えても同じ出力になるか、2 通りの数え方の合計が合うか、そして 3 つの写しだ。**ある回の指紋を前の回と同じ文字列に替えた写し**では、その対が「差分も指紋も動いた」から「差分は 0 でないのに指紋が前の回と同じ」へ移り、累積の突合の数は 1 つも動かないこと。**中身が替わった行数を 1 件増やした写し**では、累積の突合の差が変わらないこと。**累積の宣言を `入れない` から `入れる` に替えた写し**では、累積だけが動いて判定の区分が 1 つも動かないこと。写しはメモリの中だけで、入力の表には 1 文字も書かない。

## 検証

テストは 21 件で、測っているものは 8 つある。回 13 件が 12 対に分かれる側、2 経路の単位が別で足せない側、**差分 0 なのに指紋が変わった対と、指紋が過去の回へ戻った対が在る**側(これが骨)、累積が棚卸しの宣言と一致して中身が替わった行数を足すと合わなくなる側、落ちた回が「差分の欄が記載なし」になる側、指紋を書き換えると判定だけが移る側、累積の宣言を替えると累積だけが動く側、出力の末尾の「持たせていないもの」が 14 行そろっている側だ。6 値の分け方は、テストの側でも 5 枚の表の行から直に分類し直して確かめている。

読みどころは 4 つある。

ひとつめが、2 経路が別の答えを返した 2 件だ。合成した表では、差分 0 なのに指紋が変わった対が 1 件と、差分が 0 でないのに指紋が同じ対が 1 件ある。**後者は、足した行数と引いた行数が同じで、出力のファイルが元に戻った形**になる。どちらも、片方の経路だけを読むと逆の結論が出る。

ふたつめが、戻りの印の 2 件になる。前の回とだけ比べれば、どちらも「指紋が動いた」になる。過去の回まで見ると、同じ文字列に戻っている。**出すのは一致した実行 id だけで、戻っているのが良いか悪いかは書かない。** 冪等な再実行なら戻って当然だし、取り違えなら困る。どちらかは記録の側では区別できない。

みっつめが、1,681 と 1,684 の差だ。累積に入れると宣言された回だけで(増えた − 減った)を積むと 1,681 行になって、棚卸しの宣言とそろう。**中身が替わった行数の 3 件を足すと 1,684 になって、合わなくなる。** 合わなくなるのが正しくて、足してはいけない欄だからだ。だから道具には、単位をまたいで足す関数を置いていない。テストの側では、わざと全部足した数を作って、その数が出力のどこにも現れないことを確かめている。

よっつめが、3 つの写しの分かれ方になる。指紋を書き換えると判定だけが動いて累積は動かない。中身が替わった行数を増やすと、判定も累積も動かない。累積の宣言を替えると、累積だけが動いて判定は動かない。**3 つとも「片方だけが動く」ことを見ている。** 2 経路が本当に別の経路なら、こうなるはずだという形を、写しで確かめた。

いつも成り立つことは 1 文にして、性質テストで確かめている。読んだ範囲は 2 通りしかない。回の対 1 つごとに 6 値のどれか 1 つが付き、6 値の合計が回の件数から 1 を引いた数に等しく、結果記号ごとの内訳の合計が回の件数に等しく、「差分が 0 で指紋も前の回と同じ」の対は差分の 3 欄が 0 かつ指紋が前の回と同一で、「差分は 0 なのに指紋が前の回と違う」の対は差分の 3 欄が 0 かつ指紋が前の回と別で、「差分は 0 でないのに指紋が前の回と同じ」の対はその逆で、戻りの印が付く対は指紋が前の回と違いかつ過去のどれかの回と同じ文字列で、累積は増やす / 減らすと宣言された欄だけで決まり動かさないと宣言された欄を 1 件増やしても動かず、出力に「正しい経路」「一致率」の欄が無く、5 枚の行順を 3 通りに入れ替えても同じバイト列になるか、1 対も数えずに理由コードが返るか、だ。どちらの場合も入力は 1 文字も書き換わらない。回を 2 件から 5 件、差分の 3 欄をそれぞれ 4 通り、指紋を 4 通り、結果記号を 2 通り、棚卸しを 1 件から 2 件、理由の宣言を 0 件から 2 件まで引く。乱数は固定で、毎回同じ 200 通りになる。崩し方は 8 通りで、1 対も数えずに止まる理由コード 8 個すべてに道を付ける。2 本目は「差分の 3 欄が 0 かと、指紋が前の回と同じかの 2 つだけが判定を分ける」ことを総当たりで見ていて、上限は 300 にしてある。

書いている途中で 1 つ捕まえたのは、差分の欄が記載なしの回の扱いだった。**最初は、記載なしを 0 として読んでいた。** そうすると落ちた回が「差分が 0 で指紋も前の回と同じ」に混ざってしまい、「変わっていない回」として数えられる。しかも性質テストが、差分の 1 欄だけが記載なしで指紋は在る、という形を作ってきて落ちた。そこで記載なしを 0 と読まない形に変え、**記載なしが 1 欄でも在れば、指紋を見る前に判定を止める**ようにした。測っていないことと、測って 0 だったことは、同じ列に置けない。

段は 8 つで、橙のピルが関所になる。前の 4 段は並べる前の検査で、表の形と出典、記号が登録表に在るか、順序番号に重複と飛びが無いかを見ている。

この図で見てほしいのは、描かれていない経路のほうだ。**指紋を計算する矢印が無い。** 中身が替わった行数を累積へ足す矢印も、正しい経路を決める矢印も、原因を推定する矢印も、割合や一致率へ出る矢印も、成功率へ出る矢印も、周期を読む矢印も、差分の中身の値を読む矢印も、現在時刻を読む矢印も、pipeline を走らせる矢印も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

5 段目から 7 段目が本体になる。5 段目で 2 経路の欄を読む。件数は整数か `記載なし` か、指紋の長さが揃っているか。6 段目で隣り合う対に値を付ける。記載なしで止まる 2 つを先に見て、そこを抜けた対だけが、差分の 0 と指紋の一致の 2 軸で 4 通りに分かれる。7 段目で戻りの印を見る。前の回ではなく、過去のどれかの回と同じ文字列かどうかだ。

8 段目で累積の突合をして、2 通りの合計で検算する。6 値の合計が回の対の件数に戻り、結果記号ごとの内訳の合計が回の件数に戻る。**この 2 つは数えるものが違う**(片方は対、片方は回)ので、どちらか 1 つを差し替えると合わなくなる。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/diff_tally) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。日付の列も時刻の列も、差分の中身の値の列も持たない。入るのは件数と記号と指紋の文字列と出典だけだ。

手元で書くのは 5 枚で、重いのは実行の記録の台帳になる。といっても、多くの環境では自動更新の仕組みがすでに同じ内容を書いているはずで、そこから列を写すだけのことが多い。重いのはむしろ**欄の登録表と結果記号の登録表**で、「中身が替わった行数は行の数を動かすのか」「落ちた回を累積に入れるのか」を人が決めるところになる。道具が見るのは、その欄が埋まっているかまでだ。

合成した表が置き場に入っているので、同じ数字が手元で出るかを確かめられる。**実在の料率も実在の金額も 1 つも入っていない。** 実行 id は記号、結果記号は記号、指紋は 20 文字の合成文字列で実在のハッシュ値ではなく、出典は「合成の…(架空)」で、件数の桁だけ手元の記録と同じ形にそろえてある。手元の記録は 11 行だが、合成のほうは 13 行にしてある。手元に出てこない形(差分は 0 でないのに指紋が同じ回、累積に入れないと宣言された回)も入れて数えるためだ。

使い方として想定しているのは、自動更新の結果を人に説明する前に 1 回通すことになる。出てきた 6 値が、そのまま「この期間について『変わっていない』と書いてよいか」を決める材料になる。**一致率は出ない。出るのは対ごとの値と、戻りの印と、累積の突合 1 行だけだ。**

## 別の業種なら

この部品が持っている欄は、実行 id・順序番号・結果記号・3 つの件数・指紋の文字列・時点記号・行数・rule 数・欄名・動かすか記号・単位記号・理由コード・出典だけで、給与や社会保険の言葉は 1 つも入っていない。どの分野でも「更新したが変わっていない」を 1 つの経路だけで言ってしまう形は同じで、分けるのは差分の件数と出力の指紋の 2 経路になると考えている。会計なら、月次の仕訳の増減件数と、出力した帳簿ファイルの指紋(件数が同じでも科目の文言が替わればファイルは別物になる)。買い物の仕組みなら、在庫連携の差分件数と、連携先に渡した CSV の指紋(0 件更新と記録されたのに相手側の受領ファイルが違う回)。医療や介護なら、マスタ配布の差分件数と配布物の版番号。製造なら、部品表の改訂件数と図面ファイルの指紋。運送なら、運賃表の改定件数と配布した運賃表の指紋になる。私が測ったのは上の合成した 5 枚の範囲だけなので、ほかの分野は同じ詰まり方になりそうな例であって実測ではない。変わるのは表に書く語だけになると考えている。

## できないこと

- **どちらの経路が正しいかは分からない。** 2 経路が別の答えを返した対を並べるだけで、どちらを直すかは読む人が決める。終了コード 0 も「2 経路が全ての対で同じ答えを返した」であって、変わっていないという意味ではない
- **差の原因は分からない。** 出るのは宣言表の写しだけで、宣言が無ければ `宣言なし` のままになる。原因を当てる辞書も、文字列から推測する経路も持っていない
- **指紋が何を含んでいるかは分からない。** 文字列の一致しか見ないので、出力の並べ方が変わっただけなのか中身が変わったのかは、この部品では区別できない(区別するには、出力そのものを読む別の部品が要る)
- **累積が正しいかは分からない。** 累積に入れるかの宣言は人が書くもので、この部品は宣言どおりに足し引きするだけになる。合わないときに出すのは差の値だけで、どちらを直すかは書かない
- **記録されなかった回は分からない。** 順序番号の飛びは見るが、そもそも台帳に行として残らなかった実行は、飛びとしても現れない
- **戻りをどう扱うかは決めない。** 一致した実行 id を出すだけで、冪等な再実行なのか取り違えなのかは読む人の判断になる
- 図 1 の割り当ては、私の記録 1 ファイルの 11 行を読んだもので、私の環境での話になる。ほかの人の実行履歴が同じ形だとは言えない
- 上の件数は合成した 5 枚の表に対する測定で、ほかの人の環境で同じ数字になるとは限らない
