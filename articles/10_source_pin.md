前の 3 本で、毎年変わる数表を日付と公表時点で引ける形にし、数式も行に置き、更新を台帳に残した。どれも「行がすでにある」ことを前提にしている。今回はその前の工程、つまり配布元の xlsx や PDF や HTML から値を取り出して行にする工程を扱う。この工程は取れる場所と取れない場所がまだらで、取れなかった場所を空欄のまま下流に流すと、前年の値や近い行で静かに埋まる。この記事では、値 1 件をピン 1 行として持ち、使うたびに原本の場所と生の文字に突き合わせる部品を作る。

**なぜ重要か**: 数表を引く仕組みをどれだけ固めても、その表に値を入れたのは取り出しの工程だ。そして取り出しは全部が機械でできるわけではない。表の形をした xlsx は読めるが、同じ配布元の別のファイルは画像だけの PDF で 1 文字も取れない。日数の表は読めるが、その表がいつから適用されるかはページのどこにも書かれていない。この「取れなかった」という事実は、表の上では空欄か、もっともらしい値かのどちらかになって現れる。空欄なら下流が埋め、もっともらしい値なら誰も疑わない。どちらも後から見分けがつかない。だから取り出しの側にも、引き当てと同じ性質が要る。決まらないときに進まないことと、決まったときに何を根拠にしたかが残ることだ。

**要点**:
- 値 1 件をピン 1 行にする。生の文字・原本のファイルの指紋・原本の中の場所・正規化の名前を、値と同じ行に持つ
- 使うたびに原本と突き合わせる。配布元が差し替えたら止まり、生の文字が指定の場所に無ければ止まる
- 取れない原本は値を空にした行として残す。表から消えないので、取れない場所が数えられる
- 正規化の既定を持たない。正規化の名前が空欄の行は、値が合っていても評価せずに止める

**数字で見る**: 合成の原本 5 種に張ったピン 13 本のうち、検査を通ったのは 10 本(うち 2 本は人が転記した印が付く)で、残り 3 本は取れない原本として値が空のまま残っている。原本とピンの表を 1 か所ずつ書き換えた 19 通りのうち 18 通りは検査が止め、止められなかったのは人が転記した行の生の文字と値を揃えて書き換えた 1 通りだった。

## 何を解決するのか

まず、これが私の手元で起きている形だという前提のほうから書く。

私の数表は、いま 1,681 行、45 種類のルールが入っている。更新は無人で回す手順にしてあり、台帳には 11 回ぶんの実行が残っている。前回はその台帳を読み直す話を書いた。今回はその一段下、**その 1,681 行はどこから来たのか**の話になる。

来た先は 3 とおりある。表の形をした xlsx を機械で読んだ行、PDF から取り出したテキストを読んだ行、そして上流の公開データをそのまま使った行だ。このうち自分で取り出した側は、取り出したあとに再計算で突き合わせてある。たとえば料率の xlsx から作った行は、3 年ぶんの折半額を 7,050 とおり計算し直して全部一致した。だから「取れたものは取れている」ほうは、わりと固い。

固くないのは逆側だった。自分の記録を読み返すと、**原本から取れなかったために手当てをしている箇所が 5 つ**書いてある。1 つは画像だけの PDF で、そこにある乗率は 1 文字も取り出せていない。2 つは適用開始日で、原本のどこにも日付が書かれていないので、自分で決めた日を仮に置いてある。1 つは公表日で、一部の原本からは取れるが、それ以外は施行日で代用している。残る 1 つは配布ページの場所そのもので、年度ごとに番号が変わるため、次の年度のぶんは人が探して手で書き足すことになっている。

この 5 つは、どれも私が自分で書き残したから分かっている。**表の側を見ても分からない。** 仮に置いた日付は、取れた日付とまったく同じ顔をして行に入っている。公表日の代用も同じだ。取れなかったという事実は、値になった時点で消えている。

### 取れなかったことは、値の側には書けない

直し方として最初に思いつくのは、備考欄に「仮置き」と書くことだ。実際、私もそうしている。ただこれは弱い。備考は行が書き換わるときに一緒に消えるし、書き忘れても何も起きない。そして何より、**備考に何と書いてあっても、値は値として下流に流れる**。

もう 1 つ思いつくのは、取れなかった行を作らないことだ。これはもっと悪い。行が無ければ、引き当ては「該当なし」で止まる。止まるのは正しいのだが、**何件が取れていないのかが数えられなくなる**。取れない場所は、表に載っていないという形で表から消える。あとで埋めようと思っても、埋める対象の一覧が無い。

だから、取れなかったことは値の側ではなく、**行の種類**として持つことにした。値が空で、取り出し方が「取れない」と書いてある行を 1 本置く。引き当てはその行に当たると止まる。一覧には出る。数えられる。

### 足すのは列で、経路ではない

取れたほうの行にも足すものがある。足すのは検査の手順ではなく、行の列だ。手順に足したチェックは、手順を書き直したときに一緒に消える。

| 足す列 | その行が言えるようになること |
|---|---|
| 生の文字 | 原本に書いてあった文字そのもの。正規化する前の形 |
| 原本のファイルと指紋 | どのファイルから取ったか。配布元が差し替えたら指紋が変わる |
| 原本の中の場所 | シート名とセル、または行番号。もう一度そこを見に行ける |
| 取り出し方 | 機械で読んだのか、人が転記したのか、取れなかったのか |
| 正規化の名前 | 生の文字から値をどう作ったか。空欄なら評価しない |

この 5 つが揃うと、値は「原本のこの場所に、この文字で書いてあったものを、この名前の正規化に通した結果」と言い切れる形になる。言い切れない行は、どれかの列が埋まらない。

|---|---|---|---|
| 表形式の xlsx | 4 | 0 | 0 |
| テキスト層のある PDF | 3 | 0 | 0 |

## 手順

ピン 1 行はこれだけの列を持つ。

| 列 | 中身 |
|---|---|
| `key` | 何の値か |
| `value` | 正規化したあとの値。下流が使う値 |
| `raw_text` | 原本にある生の文字そのまま |
| `source_kind` | 原本の種類。対応表の行になる |
| `source_file` | 原本のファイル |
| `source_sha256` | 原本の指紋。配布元が差し替えたら止まる |
| `locator` | 原本の中の場所 |
| `method` | 取り出し方 |
| `normalizer` | 生の文字から値を作る正規化の名前 |
| `captured_at` | 取り出した時刻 |
| `note` | 覚え書き |

取り出し方は 4 種類と、取れないことを表す 1 種類で合わせて 5 つになる。

| 取り出し方 | 何をするか | 場所の指し方 |
|---|---|---|
| `xlsx_cell` | zip を開いて中の xml を直接読む | `シート名!B12` |
| `text_line` | 取り出し済みテキストの指定行 | 行番号 |
| `html_text` | tag を外したテキストの指定行 | 行番号 |
| `manual` | 人が転記した。値に転記の印が付く | 人が読んだ場所を文章で |
| `unavailable` | 取れない。値は空でなければ止まる | 取れなかった場所を文章で |

**PDF は自前で読まない。** 取り出したテキストを受け取るだけにして、PDF 本体には指紋と場所だけを張る。読む部分を自分で持つと、取り出しの品質が部品の中に隠れてしまうからで、外で取り出したテキストを渡す形にしておけば、どの取り出し器を使ったかは呼ぶ側の記録に残る。テキスト層の無い PDF は、この作りでは自動的に取れない行になる。

呼び方は 4 つで、見出しの書き出し・検査・引き当て・対応表になる。

```
python source_pin.py init pins.csv
python source_pin.py verify pins.csv
python source_pin.py get pins.csv 上限額_地域I
python source_pin.py map pins.csv
```

検査は 3 つを見ている。原本の現物の指紋が列と一致するか、場所に生の文字がそのまま在るか、正規化の名前を通した生の文字が値と一致するか、の 3 つだ。全部通ると値が返る。

```
$ python source_pin.py get pins.csv 上限額_地域I
{"ok": true, "key": "上限額_地域I", "value": "1230000", "raw_text": "１，２３０，０００円",
 "source_file": "genpon_ryouritsu.xlsx",
 "source_sha256": "dc18b1dec20076c7b102c13805853c949f87ca514cbedd1bcb62474dda8f86b3",
 "locator": "料率!C3", "method": "xlsx_cell", "normalizer": "全角半角+カンマ除去+円",
 "transcribed": false}
```

返ってくるのは値だけではない。どのファイルのどこに、どういう文字で書いてあって、どう正規化したかが一緒に付いてくる。人が転記した行なら、最後の印が `true` になる。

```
$ python source_pin.py get pins.csv 来年度の配布ページ
{"ok": true, "key": "来年度の配布ページ", "value": "page-00042", "raw_text": "page-00042",
 "source_file": "haifu_kiroku.txt", "locator": "手元の記録 3 行目(機械で辿れない)",
 "method": "manual", "normalizer": "そのまま", "transcribed": true}
```

取れない行を引くと止まる。終了コードは 3 になる。

```
$ python source_pin.py get pins.csv 乗率_世代I
{"ok": false, "key": "乗率_世代I", "reason": "unavailable",
 "detail": "取れない原本として台帳にある key: 乗率_世代I"}
```

引き当てには「決まらなければ近いほうへ」に相当する引数が無い。近い名前の行にも、前の年度の行にも、いちばん新しい行にも落ちない。これはテストで引数の形ごと固定してある。

### 正規化は名前で呼ぶ

生の文字から値を作る正規化は、`そのまま` / `全角半角` / `カンマ除去` / `パーセント` / `円` / `日付` の 6 つを登録してあり、`+` でつないで左から順に適用する。全角でカンマ付きの金額なら `全角半角+カンマ除去+円` になる。

ここで決めたのは、**部品の側に既定の正規化を置かない**ことだ。何もしない場合も `そのまま` と名前で書く。名前が空欄の行は、生の文字と値がたまたま一致していても評価せずに止める。

```
$ python source_pin.py verify pins.csv
{"ok": false, "pins": 13, "verified": 8, "transcribed": 2, "unavailable": 2, "failed": 3,
 "by_reason": {"normalizer 空欄": 1, "生の文字が指定場所に無い": 1,
               "unavailable なのに value がある": 1}}
```

```
{"key": "改定日", "method": "text_line", "status": "failed",
 "reason": "生の文字が指定場所に無い",
 "detail": "13 にあるのは '改定日 2027年8月1日'、ピンの生の文字は '2027年9月1日'"}
```

桁も勝手には落とさない。`1.60%` は `1.60` になり、`1.6` にはしない。原本に書いてある桁をそのまま値にして、丸めたいなら丸める側が名前を付けて丸める、という分け方になっている。

### 止まる理由コードは 8 つ

| 理由コード | 何が起きたか |
|---|---|
| 原本の sha が違う | 配布元が差し替えた、または原本が見つからない |
| locator が範囲外 | シート・セル・行番号が原本の範囲の外にある |
| 生の文字が指定場所に無い | 場所はあるが、そこに書いてある文字が違う |
| normalizer 空欄 | 正規化の名前が書かれていない。評価せずに止める |
| normalizer を通しても value と合わない | 通した結果が値と一致しない |
| unavailable なのに value がある | 取れないと書いた行に値が入っている |
| 同じ key が 2 行 | どちらを使うかが表から決まらない |
| 列が足りない | ピン行として読めない。登録されていない名前もここに入る |

取れない行があっても、検査そのものは通ったことにする。終了コードも 0 になる。**取れないことは異常ではなく記録だ**という扱いで、ここは意図して分けた。異常にしてしまうと、取れない行を消す動機が生まれる。

## 検証

テストは 37 件。fixture は合成データで、地域名も値も出典名も架空になっている。実在の料率や限度額は 1 つも入れていない。合成の xlsx も、生成器が zip に最小の xml を組んで作るので、外部ライブラリを使わずに毎回同じ指紋になる。

```
$ python -m pytest tools/source_pin -q
37 passed in 1.32s
```

測定は 3 つある。どれも決定論で、乱数を使っていない。

1 つめは、合成の原本 5 種に張ったピンの検査だ。

```
[measure] 原本 5 種に張ったピン 13 本: 検査を通った 10 本(機械で接地 8 本 / 転記の印 2 本)
          / 取れない 3 本 / 止まった 0 本
[measure] 機械で取り出した 8 本すべてで、生の文字が原本の指定場所に literal で在った(8/8)
```

ここで固定しているのは件数そのものより、**値と原本の場所と生の文字が 1 本も途切れずに繋がっている状態が作れる**ことのほうになる。繋がっていない行は検査が止めるので、止まった本数が 0 であることが接地できている証拠になる。

2 つめは、原本とピンの表を 1 か所ずつ書き換えて、検査が止めるかを見る測定だ。

```
[measure] 原本とピンの表を 1 か所ずつ書き換えた 19 通り: 検査が止めた 18 通り
          (止められなかった 1 通り = manual の生の文字と value を揃えて書き換える)
[measure]   原本の xlsx を書き換える → 原本の sha が違う
[measure]   ピンの sha256 列を書き換える → 原本の sha が違う
[measure]   原本のファイルを消す → 原本の sha が違う
[measure]   manual の行の原本を書き換える → 原本の sha が違う
[measure]   locator のシート名を変える → locator が範囲外
[measure]   text_line の行番号を原本の行数より大きくする → locator が範囲外
[measure]   raw_text を 1 文字変える → 生の文字が指定場所に無い
[measure]   locator を別の行にずらす → 生の文字が指定場所に無い
[measure]   xlsx の raw_text を部分文字列にする → 生の文字が指定場所に無い
[measure]   normalizer を空欄にする → normalizer 空欄
[measure]   登録されていない normalizer 名にする → 列が足りない
[measure]   value を 1 桁変える → normalizer を通しても value と合わない
[measure]   normalizer を そのまま に変える → normalizer を通しても value と合わない
[measure]   unavailable の行に value を入れる → unavailable なのに value がある
[measure]   同じ key の行を 2 行にする → 同じ key が 2 行
[measure]   manual の生の文字と value を揃えて書き換える → (止まらない)
```

8 つの理由コードには、この書き換えの集合から全部到達している。生の文字と値を同時に、辻褄が合うように書き換えた場合でも、機械で取った行なら止まる。原本のその場所に書いていない文字は、どう揃えても指定場所から出てこないからだ。

止められなかった 1 通りは正直に書いておきたい。**人が転記した行は、生の文字と値を揃えて書き換えられると検査が通る。** 転記した行には突き合わせる場所が無いので、構造として確かめようがない。だからこの部品がやれることは、その行に転記の印を付けて、引き当ての返り値にも印を載せ続けることだけになる。印を見た人が原本に当たるかどうかは、仕組みの外側の話だ。

3 つめは対応表で、図 1 と記事の表はこの出力をそのまま使っている。

```
[measure] 原本の種類 × 取り出し方(map の出力そのまま)
[measure]   表形式の xlsx: 機械 4 / 人が転記 0 / 取れない 0
[measure]   テキスト層のある PDF: 機械 3 / 人が転記 0 / 取れない 0
[measure]   日付の無い HTML: 機械 1 / 人が転記 1 / 取れない 0
[measure]   画像だけの PDF: 機械 0 / 人が転記 0 / 取れない 2
[measure]   URL が変わる配布元: 機械 0 / 人が転記 1 / 取れない 1
```

この測定の弱いところは、取れない原本をこちらで作って並べている点だ。現実の配布元で何割が取れないかは、これでは分からない。分かるのは、取れないものを並べたときに表から消えないという、部品の側の性質だけになる。

## 図 2 値 1 件を取る流れと、止まる場所

![指紋を取る、場所を開く、生の文字を確かめる、名前で正規化する、ピン 1 行に残す、引くたびに検査する、の流れ図](figures/source_pin_flow.png)

段は 6 つで、橙のピルが関所だ。いちばん右の段が「引くたびに検査する」になっているところを見てほしい。取り出したときに 1 回だけ確かめる作りにすると、確かめたあとに原本が差し替わっても気づけない。使うたびに指紋と場所を見に行くので、配布元が黙って差し替えた回に止まる。

この図でも、描かれていない経路のほうが本題になる。どの関所から出ても行き先は理由コードで、「取れなかったので前年の値を使う」や「近い行で代用する」に戻る矢印がどこにも無い。実装でも同じで、引き当ての関数には受け皿の引数を持たせていない。落ちる先が無ければ、落ちる経路も書けない。

## 道具

[source_pin](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/source_pin) に置いた。`source_pin.py` 1 ファイルと、テスト、合成 fixture の生成スクリプトが入っている。依存は無く、標準ライブラリだけで動く。ライセンスは MIT。

ピンの表は CSV でも JSON でもよく、列は前々回までの部品の行の表に足せる形にしてある。自分の環境に合わせるときに触るのは、原本の種類の名前と、正規化の名前の並びだけになる。部品のコードは触らない。正規化を増やしたい場合だけ、登録の 1 か所に名前と処理を足す形になる。

## 別の業種なら

この部品は、給与や社会保険の語彙をひとつも持っていない。持っているのは、ファイルの指紋と、原本の中の場所と、生の文字と、正規化の名前だけだ。会計の税率表や勘定科目の対応表、建設の歩掛り、医療や介護の点数表、通販の送料表と手数料表でも、配布元が PDF や xlsx で出していて、一部は機械で取れて一部は人が目で読むしかない、という形は同じだと考えている。私が実測したのは上の合成データと、自分の表の取り出し記録だけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。入力の例を料率の xlsx から税率の PDF に替えても、送料表の HTML に替えても、部品の側からは同じことになる。ピン 1 行が持つのが場所と文字と正規化の名前だけで、業種の語彙を持たないからだ。

## できないこと

- 値そのものの正しさは判定しない。原本の解釈もしない。原本のその場所にその文字が書いてあるかを見るだけで、原本の値が間違っていれば間違ったまま通る
- 人が転記した行は接地を確かめられない。生の文字と値を揃えて書き換えられると検査が通る。上の測定で止められなかった 1 通りがこれになる。印を付けて返すところまでが仕組みの範囲で、その先は人が原本に当たることになる
- PDF は読まない。取り出したテキストを受けるだけなので、取り出し器の良し悪しはこの部品の外側にある。取り出しが途中で崩れたテキストを渡されれば、崩れた行がそのまま場所になる
- 配布元の URL が生きているか、最新のものかは見ない。見るのはファイルの指紋と場所だけで、古いファイルを握ったまま検査を通し続けることはできてしまう
- 原本の種類の名前は人が書く。書かれていない行は「種類の記載なし」にまとまるので、対応表の行の分け方そのものは機械では決まらない
- xlsx の計算式が入ったセルは、計算結果の文字を返す。式そのものは見ないので、式が書き換わったのに結果が同じなら気づけない
- 上の数字は合成データと私の環境での測定で、他の人の原本で同じ内訳になるとは限らない。特に取れる・取れないの内訳は、こちらで原本を作って並べているので、その作り方で変わる値になる
- 私の記録にある取れない箇所 5 つは、私の手元の 3 領域の原本を見た範囲の話で、網羅ではない。別の分野の原本は見ていない
