前回は、宣言された実行コマンドを走らせて結果だけを台帳に残す部品を作った。今回はその裏側で、走らせずに見る側を作る。この連載は毎回「できないこと」の節を置き、道具の側にも「その引数が無い」「その経路が無い」と書いてきた。骨は 1 行で言える。**その宣言は文章であって、文章は読み手の側では確かめられない。**

**なぜ重要か**: 私がこれまでに公開した道具は 17 本あり、その全部に「できないこと」を書いた。読む人から見ると、それは私がそう言っているという事実でしかない。コードを開いて 1 行ずつ探せば確かめられるが、普通はしない。書いた私の側も、書いた時点では確かめていて、その後に足した機能については確かめ直していない。この記事の部品は、宣言のうち機械で見られる形のものだけを、対象のソースを走らせずに構文として読んで突き合わせ、宣言どおり・一致しない・宣言が無い・機械では読めない の 4 値を分母の内訳つきで台帳に残す。自分の 17 本に通した結果もそのまま載せる。

**要点**:
- 判定は 4 値にする。宣言どおり・一致しない・宣言が無い・機械では読めない。読めなかったものを宣言どおりに混ぜない
- 機械判定の種類は宣言表から取る。5 種だけで、宣言の文から種類を推測する経路は持たない
- 一致しない行に言葉を足さない。出すのは宣言の verbatim と、現れた行番号だけ。理由は推定しない
- 遵守率は単独では返らない。4 値の件数と、分母に何を含めたかが必ず一緒に付く

**数字で見る**: 公開済み 17 本の宣言を 17 行の宣言表にして通すと、機械で読めたのは 8 行だけで、そのうち宣言どおりが 6、一致しないが 2 だった。残りは文章だけの宣言が 7、その線について宣言が無いものが 2 で、遵守率は機械で読めた行だけを分母にすると 0.7500、宣言表の行すべてを分母にすると 0.3529 になる。

## 何を解決するのか

前回の部品は、宣言された実行コマンドを走らせて終了コードを見るものだった。走らせれば分かることは走らせればいい。問題は、**走らせても分からない宣言のほうだ。**

「ネットワークを持たない」「シェルを経由しない」「書き出しを持たない」「その引数が無い」。これらはどれも、何かが起きることではなく、**何かが起きないこと**を言っている。1 回走らせて起きなかったとしても、別の入力では起きるかもしれない。起きないことを走らせて確かめるのは、原理的に向いていない。

向いているのは、ソースを開いて「その経路が書かれていないこと」を見ることだ。実行しないので、どの入力かという話が消える。

### 宣言は、書いた側の自己申告のまま置かれている

私の連載の記事には、毎回「できないこと」の節がある。道具の README にも「持たせていないものが規律になっている」という節がある。どちらも私が書いた文章で、読む人の側には確かめる手立てが無い。

これは誠実さの問題ではなく、**形式の問題だ。** 文章で書いた線は、文章のままでは照合できない。照合できるようにするには、線を「ソースの中のどの形を探せばよいか」という名指しに置き換えるしかない。

### 自然文を読ませようとした瞬間に壊れる

ここで素直に作ると、たいてい次の形になる。できないことの節を読み込んで、意味を解釈して、対応するコードの箇所を探す。

この形には入れたくない経路が入る。宣言の文から「たぶんこれはネットワークの話だ」と推測する経路だ。推測が当たっているかは誰にも分からず、外れたときは**静かに宣言どおりの側へ落ちる**。確かめるための道具が、確かめていないものを確かめたことにしてしまう。

だからこの部品は、自然文を解釈しない。宣言表に「機械判定の種類」と「名指しの対象」の欄を置き、**人が埋めた分だけを見る。** 欄が空なら「機械では読めない」に落ちる。落ちた行は読めなかった行として件数に残り、宣言どおりの側には 1 件も混ざらない。

### 見えなかったことを、守られていることの代わりにしない

もうひとつ入れたくないのが、追えない形の扱いだ。構文だけを見ていると、どうしても見えないものがある。名前を変数で組み立てて呼ぶ形、ファイルを開くモードを変数で渡す形、キーワードを辞書で展開して渡す形。

ここで「見えなかった = 見つからなかった = 宣言どおり」としてしまうと、**いちばん見えない書き方をしている道具がいちばん高い遵守率を取る。** 逆向きの力がかかる。だから追えない形は「機械では読めない」に落とし、理由コードを付ける。同じソースに確かに現れた行と追えない形が両方あるときは、現れた側を取って「一致しない」にする。

### 直し方は、線ごとに 1 行を書かせること

入力は宣言表 1 枚だけにした。1 行が 1 つの線で、列はこれだけになる。

| 欄 | 何を宣言するか |
|---|---|
| `tool` | 道具名 |
| `line` | 線の名前。「外向きの通信を持たない」など |
| `declaration` | 宣言の verbatim。空欄は「この線について宣言が無い」を意味する |
| `source` | その宣言の出典。ファイル名と行番号。空欄は止まる |
| `kind` | 機械判定の種類。5 種か空欄 |
| `target` | 名指しの対象。モジュール名や呼び出しの名前など |
| `path` | 対象ソースのパス |

`declaration` を verbatim で持たせているのがこの部品の肝になる。要約して書くと、判定の対象が「私が後から要約した文」にすり替わる。原文のまま持ち、出典の行番号を付けておけば、読む人は元の文に戻れる。

## 図 1 公開済み 17 本の宣言を、走らせずに突き合わせた結果

![線の種類 6 とおりを行に、宣言どおり・一致しない・宣言が無い・機械では読めない を列にした対応表](figures/scope_ledger_cases.png)

行が線の種類、列が判定の 4 値になる。藍が機械で読めて名指しの経路が現れなかったところ、橙がその箱に入って人に戻すところ、無彩色が 0 件だ。各セルの件数は、公開済み 17 本のソースに対してその場で突き合わせた出力で、テストが固定している。

いちばん大きい箱が右下の「機械では読めない」の 7 件であることが、この表のいちばんの読みどころになる。「差の原因は推定しない」「値そのものの正しさは判定しない」「同一人物かどうかは決めない」といった宣言は、経路として名指しできない。**書いてある線の多くは、そもそも機械で確かめられる形をしていない。** 読めなかった 7 件には出典が残してあるので、どの文が読めなかったのかは追える。

上から 4 行は、機械で読めた 8 件の内訳になる。外向きの通信を持たないと書いた 2 本は、名指ししたモジュールを取り込む行が 1 つも無かった。シェルを経由しないと書いた 1 本は、値まで名指しして突き合わせている。名指しの引数を持たないと書いた 3 本のうち 2 本は、関数名まで絞って引数の定義を見た。

3 行目が「一致しない」の 2 件だ。書き込まないと宣言した 2 本で、名指しした書き込みの経路が、それぞれ 635 行目と 555 行目に現れた。**台帳に出るのはこの行番号と、宣言の verbatim だけになる。** 嘘とも違反とも書かないし、なぜ現れたのかも書かない。理由を書かないのは意図的で、理由は私の推測でしかなく、出典が無いからだ。

いちばん下は「宣言が無い」の 2 件になる。この 2 本のソースには、実際には名指しの経路が無い。それでも宣言どおりとは書かない。**宣言が無い線について「していない」と書けるのは、宣言を確かめる道具ではなく、宣言を書く人のほうだからだ。**

## 手順

宣言表のひな型を出す。

```
python scope_ledger.py init 宣言表.csv
```

埋めるとこうなる。17 本に通した表から 4 行だけ抜き出す。

```
tool,line,declaration,source,kind,target,path
answer_check,外向きの通信を持たない,**モデル名・API・ネットワークを持たない**(推論は関所の外。文章は人が貼る),tools/answer_check/README.md L19,import,urllib,../../answer_check/answer_check.py
check_census,シェルを経由しない,**シェルを経由しない**(argv は配列のまま渡す。…),tools/check_census/README.md L16-17,kwarg,shell=True,../../check_census/check_census.py
jp_name,同一人物を決めない,同一人物かどうかは決めない。決めるのは「照合キーが一致するか」だけ。…,tools/jp_name/README.md L79,,,
wareki,書き込まない,,tools/wareki/README.md L73-77 の できないこと 節を見た(この線についての宣言は無い),,,
```

3 行目は種類の欄が空で、これが「機械では読めない」に落ちる行になる。4 行目は宣言の欄が空で、「宣言が無い」に落ちる。どちらの行も出典の欄は埋まっている。**どこを見て読めなかったのか、どこを見て無かったのかが残らない行は、台帳に入れずに止める。**

機械判定の種類は 5 種だけだ。

| 種類 | 見るもの | 名指しの書き方 |
|---|---|---|
| `import` | 名指しのモジュールを取り込んでいないか | `urllib` |
| `call` | 名指しの呼び出しが無いか | `eval` |
| `kwarg` | 名指しのキーワード引数が無いか | `shell` か `shell=True` |
| `option` | 引数定義に名指しの文字列が無いか | `prefer` か `resolve:fallback` |
| `write` | 名指しの書き込み経路が無いか | `open` |

`kwarg` で値まで書けるようにしてあるのは、`shell=False` と書いてある行を `shell=True` の宣言に対する一致として数えないためだ。`option` の `関数名:引数名` という書き方は、その関数の定義だけを見る。関数を絞らずに書くと、関数の引数定義と `add_argument` の文字列の両方を見る。

通すとこうなる。

```
python scope_ledger.py ledger 宣言表.csv
```

返るのは 4 値の件数、分母の内訳、2 つの遵守率、それに 1 行ごとの判定になる。

```
{"ok": true, "stage": "台帳にした",
 "宣言どおり": 6, "一致しない": 2, "宣言が無い": 2, "機械では読めない": 7,
 "宣言表の行数": 17, "機械で読めた数": 8, "機械では読めなかった数": 7, "宣言が無い数": 2,
 "遵守率_機械で読めた行のみ": "0.7500", "遵守率_宣言表の行すべて": "0.3529",
 "分母に含めたもの": "機械で読めた行のみ = 宣言どおり 6 + 一致しない 2 = 8(機械では読めない 7 +
                   宣言が無い 2 を除いた分母) / 宣言表の行すべて = 17(読めなかった行と
                   宣言が無い行を含む分母)",
 "機械では読めない行を宣言どおりに寄せていない": "読めなかった 7 件は別の箱のまま(内訳
                   種類の欄が無い 7 / 対象が Python でない 0 / 構文解析できない 0 /
                   名前が動的に組み立てられている 0)"}
```

同じ台帳から遵守率が 2 つ出る。読めなかった行と宣言が無い行を分母から落とすと上がるので、片方だけを引用できない形にしてある。前回の合格率、その前の接地率と同じ作りだ。

1 行ごとの判定は 7 欄で固定されている。

```
{"道具名": "intake_triage", "線の名前": "書き込まない", "判定": "一致しない",
 "理由コード": "", "現れた行": [635],
 "宣言": "**書き出しを持たない**(ファイルはこの部品からは開かない)",
 "出典": "tools/intake_triage/README.md L21"}
```

この行に足せる欄は無い。判定を言い換える欄も、重さを付ける欄も、直し方を書く欄も持たせていない。

読んだ対象の絶対パスと、読んだ時刻と、ホスト名は、判定とは別の欄に出る。

```
"読んだ条件": [{"道具名": "intake_triage", "線の名前": "書き込まない", "種類": "write",
             "名指しの対象": "open", "読んだ絶対パス": "…", "読んだ時刻": "…", "ホスト名": "…"}]
```

この 3 つを判定部分から外してあるのが、次の `verify` の前提になる。

```
python scope_ledger.py verify 宣言表.csv
```

2 回判定して、判定部分のバイト列の sha256 を突き合わせる。合わなければ、どの行のどの欄が違ったかを観測としてそのまま返す。平均も多数決も取らない。

関数として呼ぶ形も同じになる。

```python
from scope_ledger import Declaration, ledger

lg = ledger(Declaration.load("宣言表.csv"))
print(lg.rate() if lg.report.ok else [x.reason for x in lg.report.pending])
```

引数は宣言表 1 つだけで、「読めなかった行を宣言どおりに含める」「遵守率だけ返す」「一致した行を直す」に相当する引数は 1 つも無い。CLI の option も `-h` 以外に 1 つも無く、これもテストで固定してある。

合成の側を先に補う。18 行のうち 11 行が機械で読める形で、宣言どおりが 6、一致しないが 5 だった。一致しない 5 件は 5 種の判定それぞれに 1 件ずつ置いてあり、現れた行番号が付いている。読めなかった 6 件は、種類の欄が空のもの 1、対象が Python でないもの 1、構文として壊れているもの 1、名前が動的に組み立てられているもの 3 で、理由コード 4 個すべてに道がある。**追えない形の 3 件が宣言どおりの側に落ちていないことが、ここでいちばん見たいところだと考えている。**

公開済み 17 本の側は、1 行も実行していない。対象を実行する経路も、取り込む経路も持たないことを、この部品が自分のソースに対して確かめているテストがある。名指しを `subprocess` と `importlib` と `urllib` に変えて自分を読ませると、どれも現れない。

止まる理由コードは 6 つで、崩した宣言表を 5 枚通し、残る 1 つは読み込みの結果が途中で変わる形を作って通した。**止まったときは 1 行も判定しない。** 宣言表が読めないのに一部だけ判定すると、件数の分母が何なのか決まらなくなる。列そのものが足りない宣言表は理由コードにせず、宣言表として読めないこととして終了コード 2 で返している。

決定論の確認は 2 つある。1 つは同じ宣言表から 2 回判定して判定部分のバイト列が一致すること、もう 1 つは同じ 2 回で「読んだ条件」のほうは違っていることだ。後者が違っていなければ、時刻を判定に混ぜていないことの確認にならない。

書き換えていないことも測った。突き合わせの前後で、合成の対象と repo の道具全体の指紋が同じになる。ソースを直す経路も、宣言を書き戻す経路も持っていない。

いつも成り立つことは 1 文にして、性質テストで確かめている。台帳の結果は 2 通りしかない。宣言表の行のひとつひとつがちょうど 1 つの判定に入り、その合計が宣言表の行数に等しく、宣言の欄が空の行は必ず宣言が無いに入り、種類の欄が空で宣言がある行は必ず機械では読めないに入り、一致しない行には現れた行番号が 1 つ以上あって他の 3 値には 1 つも無く、どの行にも出典が残り、判定部分のバイト列に時刻・ホスト名・絶対パスが 1 つも入らないか、判定が 1 件も返らず理由コードが返るか、だ。どちらの場合もソースと宣言表は 1 文字も書き換わらない。宣言表を毎回乱数で作り直し、1 行ごとに 13 とおりの在り方から引き、3 割くらいの確率で表のどこか 1 か所を崩して、毎回この 1 文が成り立つかを見る。乱数は固定で、毎回同じ 60 通りを試す。**その行が宣言どおりになるはずか一致しないはずかは、部品の判定を呼ばずにテストの側で持っている。** 同じファイルの 2 本目は分母の恒等式を見ていて、機械で読めた行だけを分母にした遵守率が、宣言表の行すべてを分母にした遵守率を下回らないこと、つまり狭い分母だけを引用すると必ず上振れする側に出ることを、300 通りで確かめている。

## 図 2 台帳を作る流れと、止まる場所

![宣言表を読み、出典と名前を見て、種類と名指しを見て、構文木として読み、4 値に分け、2 回判定して返すまでの流れ図](figures/scope_ledger_flow.png)

段は 6 つで、橙のピルが関所だ。前の 3 段は 1 行も判定する前の検査で、宣言表の形だけを見ている。

この図で見てほしいのは、描かれていない経路のほうになる。種類を決める段へ入ってくる矢印は宣言表からの 1 本だけで、宣言の自然文から種類を決める経路が無い。構文木として読む段から対象を実行する段へ出る矢印も無い。4 値に分ける段から「読めなかった行を宣言どおりにまとめる」へ出る矢印も無い。一致しない行から「言葉を足す」へ出る矢印も、ソースを直す段へ戻る矢印も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

最後の段は前回までと同じで、判定を 2 回行って自分の出力を突き合わせている。静的に読むだけの部品なので、同じ入力に同じ答えが出るのは当たり前に見える。それでも突き合わせているのは、対象のファイルが読んでいる途中で変わる場合があるからで、そのときは吸収せずに不一致として返す。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/scope_ledger) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。

自分の手元で使うときは、宣言表の CSV を書くだけでいい。部品のコードは触らない。終了コードは、止まらずに一致しない行が 0 件のときだけ 0 で、一致しない行があれば 3、宣言表として読めなければ 2 になる。まとめて走らせる仕組みの中に置いて、3 で止められる。

公開済み 17 本に通した宣言表は `fixtures/sengen_koukai17.csv` に入れてあるので、同じ結果が手元で出るかを確かめられる。

## 別の業種なら

この部品が持っている欄は `tool` と `line` と `declaration` と `source` と `kind` と `target` と `path` の 7 つだけで、給与や社会保険の語彙は 1 つも入っていない。会計なら締めのチェック表の「ここは自動で直さない」、EC なら受注取込の「送料は補完しない」、建設なら検査票の「現場判断に戻す範囲」、医療・介護なら請求前点検の「コードを書き換えない」。どれも手順書の側には書いてあるが、実物にその経路が無いかは誰も確かめていない形で置かれるので、同じ台帳がそのまま使えると考えている。私が測ったのは上の合成の対象と自分の 17 本の範囲だけなので、他の分野は同じ詰まり方になりそうな例であって実測ではない。変わるのは宣言表に書く中身だけで、部品のコードはそのまま使える。

## できないこと

- 判定したことは「名指しされた経路が静的に現れないか」までで、**道具が宣言どおり振る舞うことは判定しない**。現れなくても、別の書き方で同じことをしているかもしれない
- **宣言が十分かも判定しない**。書かれていない線の良し悪しも、線の引き方の妥当性も見ない
- **現れた行が、その宣言の対象の経路かどうかは分からない**。名指しは関数を特定しないので、同じ名前が別の経路で現れても当たる。そこを確かめるのは人の側になる
- 別名での取り込み・再公開・動的な属性参照は追わない。追えない形は読めない行に落ちるだけで、そこに何が在るかは分からない
- Python でない対象は読めない。他の言語のソースも、設定ファイルも、ドキュメントも対象の外になる
- 文章だけの宣言は、原理的にこの部品の外になる。今回の 17 行のうち 7 行がそれで、**読めないことは守られていないことではない**
- 一致しない行の理由は書かない。私の側にその出典が無いからで、理由を推定する経路は入れていない
- 宣言表の正しさは判定しない。verbatim が原文と一致しているか、種類と名指しがその宣言の意味に合っているかは、宣言表を書く人の側になる
- 上の件数は、合成の対象と公開済み 17 本に対する測定で、他の人の手元で同じ数字になるとは限らない。対象のソースを直せば数字は変わる
