前回は、新しい行を足したときに閉じる端を足す前に一覧にした。今回は行ではなく、そもそも表に入れないと決めた項目のほうを並べ直す。骨は 1 行で言える。**「表に入らない」は 1 つの状態ではない。外し方が 7 通りあって、外した先で誰が値を決めるか・どの層の行になるかがそれぞれ違う。1 つの「対象外」に潰すと、実は表に入るもの(期限)と、同じ行形式の第 2 層で持つもの(主体ごとに違う値)と、人が起票して渡すもの(事実認定)が同じ袋に入り、問いが来たときどこへ返すかが決まらない。**

**なぜ重要か**: 私はこの連載で、道具の外に出たものを 2 回以上並べている。[返ってきた値で計算が終わるとは限らない回](https://chronicles-of-solo-parenting.blogspot.com/2026/10/blog-post_22.html)では、求める値ごとに「道具の中で済む / 返るが一手残る / 外から渡す前提 / 止まる」の 4 つに分けた。[できないと書いたことを確かめる回](https://chronicles-of-solo-parenting.blogspot.com/2026/10/blog-post_09.html)では、宣言が機械で見られるかで 4 つに分けた。[取り込めない行を仕分ける回](https://chronicles-of-solo-parenting.blogspot.com/2026/10/blog-post_04.html)では、行が取り込めるかで 3 つに分けた。**どの軸でも「外から渡す前提」が 1 列に潰れたままだった。** 外の内訳は、どの回でも手を付けていない。そして手元の記録を読み返すと、外し方は 7 通りに書き分けられていて、受け取り方もそれぞれ別に書いてある。1 列に潰れていたのは、私がその軸で並べたことが無かっただけだ。

**要点**:
- 旧軸は「呼んだときにどう見えるか」で分ける。新軸は「誰が値を決め、どの層の行として持つか」で分ける。欄を別に持ち、同じ欄名なら道具が止まる
- 分類の規則を道具が持たない。宣言された印 7 つの組み合わせを置き場の登録表に当てるだけで、登録表に無い組み合わせは別枠に出す
- 外に出た先は 8 つに分かれる。そのうち 2 つは表に戻る(期限は起算日 + N 日の式として、通達は特例の順位の行として)
- 自然文を読まない、期限を足さない、判断を起票しない、履歴を舐めない。並べ直すだけで、どの置き場が良いとも言わない

**数字で見る**: 合成した問いの台帳 20 行・置き場の登録表 8 行・新軸の定義 1 行を通すと、判定できた 12 件が 8 つの置き場に分かれ、残り 8 件が別枠の 8 つの理由に 1 件ずつ入った。**旧軸で「外から渡す前提」の 1 列に入っていた 12 件のうち、判定できた 8 件は新軸の 7 値に割れた。** その 7 値に「公的層の行で埋まる」は入っていない。手元の記録から拾った実際の 8 件でも、旧軸の一覧に行があるのは 3 件だけで、残り 5 件は「設計上の対象外」という 1 語の中にいた。

## 何を解決するのか

引き当ての道具を作ると、必ず「表に入れないもの」が出る。私もそう決めて、設計の記録に章を 1 つ立てた。そこには外し方が 7 通り書いてある。要件該当性の判断、主体ごとに違うパラメータ、手続きと期限と添付書類、通達と疑義照会と裁判例、状態遷移と履歴依存、施行日が未確定の改正、裁量と協議事項だ。

**各行には、どう扱うかまで書いてある。** 要件該当性の判断は、判断結果を case の属性として受け取る、人か大規模言語モデルが起票する、表は属性が確定した後だけ動く。主体ごとのパラメータは、同じ行形式の第 2 層を持って選びの欄に主体の id を足し、公的層より順位を高くする。期限は「基準日 + N 日」の式として**表に入る**、ただし添付書類はチェックリストなので表の外。通達は行の出典から参照できる解釈メモの層に置き、特例の順位の行として計算に入る場合だけ表に入る。状態遷移は数式側が状態機械を持ち、表からは閾値と率だけ供給する。施行日が未確定の改正は、知識としては登録して計算には使わない行にする。裁量と協議事項は表の対象外で、決まったものが第 2 層に入るだけだ。

### 1 語に潰れる

ところが、同じことを 1 行に潰した記述も手元にある。作業状況の記録には、表に入らないものとして要件該当性の判断・事業所固有パラメータ・状態遷移の 3 つが名前で挙がり、設計上の対象外、判断結果を case 属性として受け取る前提、と書いてある。

**7 通りのうち 3 つだけが名前で残り、期限・添付書類・通達・政令待ち・裁量は「設計上の対象外」の 1 語に入っている。** 受け取り方も 1 通りに書かれている。

この 1 行だけを読むと、期限は表に入らないことになる。けれど設計の記録のほうには、表に入る(準整理可)と書いてある。**どちらも私が書いた文書で、同じ事象を指していて、粒度だけが違う。**

### 引いた結果からは分からない

引き当ての道具が返すのは、終了コード 3 値と値だけだ。成功、該当なし・入力不足、表の不備。**この 3 値のどこにも「この値は第 2 層で持つ」「この値は人が起票してから渡す」は入っていない。** 返り値を見ても置き場は分からない。だから置き場は、引く前に別の表として持つしかない。

### 旧軸では足りないこと

旧軸(出口と実装の状態)は、呼んだときにどう見えるかで分ける軸だ。値が返るのか、返るが一手残るのか、そもそも外から渡す前提なのか、止まるのか。**呼ぶ側にとっては正しい軸だが、「外から渡す前提」の中身は見えない。** 誰が値を決めるのかも、どの層の行として持つのかも、1 列に潰れている。

新軸は置き場で分ける。どの層の行になるか、誰が値を決めるか。**旧軸と新軸は一対一にならない。** 旧軸の 1 列が新軸の複数の値に割れるし、新軸の 1 値が旧軸の 2 つの列から集まることもある。

## 図 1 同じ 8 件を旧軸から新軸へ並べ直す

![手元の記録に書かれている 8 件を、旧軸の値 / 新軸の値(置き場)/ 誰が決めるか / 要求する欄 / 出典 の 5 列で並べ直した表](figures/fill_owner_axis.png)

軸の定義は図の冒頭に 1 行で書いた。旧軸は出口と実装の状態、新軸は置き場だ。**良し悪しの列は置いていない。** どの置き場が楽か、どれをあきらめるかは、この図の仕事ではない。実在の料率も金額も入っていない。入っているのは分類の記号と出典だけだ。

読みどころは 3 つある。

ひとつめが、左の列の色の分かれ方になる。藍の 3 行は、旧軸の一覧に行がある。橙の 5 行は、旧軸では「設計上の対象外」の 1 語に入っていて、**一覧の何行目かを指せない。** 道具に入れるなら、この 5 件は一覧 id が無いので判定の対象にならない。並べ直す前に、まず旧軸の一覧を書き足すところからになる。

ふたつめが、新軸の列で「表に戻る」2 件だ。期限は起算日 + N 日の式として公的層の行に入る。通達は解釈メモの層から参照して、特例の順位の行として計算に入る場合だけ表に入る。**旧軸で「外から渡す前提」と書いた袋の中に、表に入るものが混ざっていた。** 置き場の軸で並べ直さないと、この 2 件は外のままになる。

みっつめが、右から 2 列目の「要求する欄」になる。置き場ごとに要る欄が違う。第 2 層なら順位の欄と主体の id、人が起票するなら受け取る属性の名前、数式側なら供給する閾値の名前、政令待ちなら施行日が決まったときに埋める欄の名前。**ここが空のまま「外に置く」と決めても、渡し方が決まらない。** だから道具の側でも、置き場が要求する欄が空の問いは判定しない。

収集範囲の限界も書いておく。見たのは手元の 2 つの記録だけで、条文も官報も実装のコードも見ていない。この型はふつう各行に URL を求めるが、ここに URL は無く、ファイル名を伏せた行番号で代えている。8 件という数は、手元の記録の章に書かれている行の数であって、世の中の外し方が 8 通りだという話ではない。

## 手順

ひな型を出す。合成の 3 枚が出る。

```
python fill_owner.py init ひな型/
```

置き場の登録表には、印の組み合わせ 1 つを 1 行で書く。

```csv
印の組み合わせ,置き場の記号,外し方の記号,誰が決めるか,要求する欄の名前,出典
はい|はい|いいえ|いいえ|いいえ|はい|はい,①,A,行政,有効開始日,設計の記録 L129 の前
はい|はい|いいえ|いいえ|はい|はい|はい,②,C3,行政,起算日の欄の名前,設計の記録 L131
いいえ|はい|いいえ|いいえ|いいえ|はい|はい,③,C2,主体,順位の欄,設計の記録 L130
いいえ|いいえ|いいえ|はい|いいえ|はい|いいえ,④,C1,人,受け取る属性の名前,設計の記録 L129
```

印は 7 つで、順番は固定だ。行政が誰でも同じ答えを出すか、主体内では一意か、履歴を舐めないと決まらないか、人が読んで決めるか、起算日 + N 日で書けるか、施行日が決まっているか、法が値を決めているか。値は `はい` と `いいえ` と `宣言なし` の 3 つだけで、ここに無い語を書くと止まる。

**ここが仕掛けになっている。印から置き場を導く規則は、道具の中に無い。** この表の行がそのまま規則で、行を差し替えれば同じ印の問いが別の置き場へ動く。登録表に無い組み合わせが来たら、近い行に寄せずに別枠へ出す。手元の記録には判定のコツも 1 行で書いてあるが、**それを道具の既定値として焼き込んでいない。** 焼き込むと、規則を直したいときに実装を直すことになる。

問いの台帳には、求める値を 1 件ずつ並べる。列は 14 で、印 7 つのほかに旧軸の値と旧軸の一覧 id が要る。

```csv
問い id,求める値の名前,旧軸の値,旧軸の一覧 id,外し方の記号,印_行政一意,…,要求する欄の値,出典
Q01,合成の値 甲(架空),道具の中で済む,L31#1#道具の中で済む,A,はい,…,合成の開始日(架空),設計の記録 L129 の前
Q05,合成の値 戊(架空),外から渡す前提,L31#5#外から渡す前提,C2,いいえ,…,順位 20(架空),設計の記録 L130
```

一覧 id は `一覧 id#行#一覧に書かれた旧軸の値` の 3 つ組で書く。一覧の側から写してくる形だ。**3 つ組になっていない問いは判定しない。写した値が台帳の旧軸の値と違う問いも判定しない。** 並べ直すというのは旧軸の一覧があって初めて言えることなので、旧記事のどの行を指しているかを持たない問いは受け付けない、という形にした。

新軸の定義は 1 行だけ書く。

```csv
新軸の欄名,旧軸の欄名,出典
置き場(どの層の行になるか),出口と実装の状態,設計の記録 L137 / 旧軸は公開済みの記事の一覧
```

**新軸の欄名と旧軸の欄名が同じなら、そこで止まる。** 同じ軸で並べ直したものを「別の軸」と呼ばないための関所になっている。

数える。

```
python fill_owner.py check 問いの台帳.csv 置き場の登録表.csv 新軸の定義.csv
```

割合を返す呼び方は無い。件数には必ず分母が付くし、**最後の「しないこと」は消せない。** `rows` にすると、問い 1 件 1 行の並べ直した一覧が出る。問い id / 求める値の名前 / 旧軸の値 / 旧軸の一覧 id / 置き場 / 別枠の理由 / 誰が決めるか / 要求する欄 / 原文の記号 / 登録表の記号 / 出典の 11 列だ。**どれから手を付けるべきかの順位は付かない。**

別枠の理由には順番がある。手前の関門が勝つ順で、問い id の重複、出典が空、一覧 id が無い、一覧の記載と違う、宣言なしを含む、組み合わせが登録外、外し方の記号が登録外、要求する欄が空、と並ぶ。**この順番そのものが仕様だ。** 同じ問いに 2 つの理由は付かない。

最後に、この手続きが決定論かどうかを実測する。

```
python fill_owner.py verify 問いの台帳.csv 置き場の登録表.csv 新軸の定義.csv
```

`verify` は 5 つ見る。2 回読んで判定部分のバイト列の指紋が同じか、3 枚の行順を入れ替えても同じ出力になるか、件数の合計が合うか、そして 2 つの写しだ。**行政一意の印を 1 件だけ裏返す写し**では、その問いが ① から登録表の組み合わせ行が指す先へ移り、さらに**登録表のその 1 行だけを差し替えると同じ印で別の置き場になる**ことを見る。2 通り出すのは、移り先を道具が決めていないことを示すためだ。**施行日確定の印を 1 件だけ裏返す写し**では、その問いだけが ⑦ から ① へ移ることを見る。写しはメモリの中だけで、入力の表には 1 文字も書かない。

読みどころは 4 つある。

ひとつめが、旧軸の 1 列の割れ方だ。「外から渡す前提」に入っていた 12 件のうち、判定できた 8 件が新軸の 7 値に分かれた。**8 件で 7 値だから、ほとんど全部が別の置き場になる。** そして ① は 0 件だった。外から渡す前提と書いた袋の中に、公的層の行でそのまま埋まるものは入っていなかった。

ふたつめが、逆向きの集まり方になる。新軸の ⑦(施行日が決まるまで登録だけして計算に使わない行)には、旧軸の「外から渡す前提」からも「止まる」からも 1 件ずつ来ている。**旧軸で別の列だったものが、置き場では同じ行になる。** 一対一の読み替え表は作れない、ということだ。

みっつめが、印 1 つで行き先が変わることだ。施行日確定の印を裏返すと ⑦ から ① へ移り、動くのはその問いだけだった。**政令待ちの行と、ふつうに表に入る行の分かれ目は、印 1 つしかない。** だから施行日が決まった日にやることは、印を 1 つ `はい` にして並べ直すことになる。

よっつめが、移り先を誰が決めているかの検算だ。行政一意の印を裏返すと ① から ③ へ移る。ここで**登録表のその 1 行だけを ⑧ に差し替えると、同じ印のまま ⑧ になった。** 道具の中に規則があるなら、登録表を替えても ③ のままになるはずだ。登録表を 1 行ずつ外した側も同じで、動いた延べ 15 件はすべて別枠に落ち、既定の置き場に化けた問いは 0 件だった。

いつも成り立つことは 1 文にして、性質テストで確かめている。問いごとに付く答えは 1 つだけで、置き場 8 値か別枠の理由のどちらか一方に入り、置き場に入った問いの置き場は必ず登録表のその行が指す先と同じで、8 値と別枠の合計も旧軸の値ごとの内訳の合計も問いの件数に等しく、入力の表は 1 文字も書き換わらない。**登録表の「印の組み合わせ → 置き場の記号」の対応は乱数で割り当てている。** 道具が印から置き場を導く規則を内側に持っていれば、乱数の対応と食い違って落ちる。問いは半分の確率でどこか 1 か所を崩す。乱数は固定で、毎回同じ 300 通りになる。同じファイルの 2 本目は 200 通りで、登録表の 1 行を 8 つの置き場に順に差し替えて、答えがその行の指す先へ動くことを見ている。

この性質テストは、書いている途中で 1 つ順番の問題を捕まえた。外し方の記号が登録表のどこにも無いことを見る関門を、組み合わせを引く関門より手前に置いていたとき、**登録表の行を 1 つ外すと、その組み合わせを使っていない問いまで別枠に移った。** 記号の一覧が登録表の行から作られているからだ。そこで順番を入れ替えて、先に組み合わせを引き、次に記号を見るようにした。動く問いの数が 15 件に減り、そのうち 14 件が「組み合わせが登録外」になった。

## 図 2 判定するまでの流れと、止まる場所

![3 枚の表を読み、軸と登録表と問いの形を見て、印の組み合わせを登録表に当てて 8 値へ振り分けるまでの流れ図](figures/fill_owner_flow.png)

段は 7 つで、橙のピルが関所になる。前の 4 段は判定の前の検査で、表の形と軸の欄名と登録表の鍵、それに問いの id と出典と一覧 id を見ている。

この図で見てほしいのは、描かれていない経路のほうだ。**印から置き場へ直接出る矢印が無い。** 置き場は必ず登録表の行を経由する。求める値の名前から印を推測する矢印も無い。**起算日から期限を計算する矢印も無い。** ② は置き場を仕分けるだけで、暦も休日表も持っていない。判断を起票する矢印も、履歴を舐める矢印も、値を引く矢印も無い。今日の日付を読む矢印も無い。置き場に順位や難易度を付ける矢印も無い。入力の表に書き戻す矢印も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

5 段目が、この回の本体になる。印の組み合わせを鍵にして登録表を引く。**無ければ、近い行に寄せない。** 7 つの印のうち 6 つが一致する行があっても、残り 1 つが違えば別の組み合わせだ。寄せてよいかどうかは規則の話で、規則は登録表の側にある。

6 段目で置き場を写す。置き場の記号も外し方の記号も、登録表に書かれた文字をそのまま写す。**原文の記号と登録表の記号が違っても、道具はどちらが正しいとも言わない。** 両方を並べて、違う問いが何件あるかを数えるだけだ。合成の表では 1 件あった。直すかどうかは、並べ直した一覧を見た人が決める。

最後に、関所がぜんぶこの部品自身の話であることを書いておく。**表の側の理由コード 4 つのどれか 1 つでも起きたら、どの問いも判定しない。** 8 値は全て 0 になり、理由コードだけが返る。測っている相手の「置き場なし」の欄に、この部品の「読めない」を混ぜないためだ。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/fill_owner) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。

手元で書くのは、問いの台帳と置き場の登録表と新軸の定義の 3 枚だけだ。合成した表が置き場に入っているので、同じ数字が手元で出るかを確かめられる。**実在の料率も金額も人名も 1 つも入っていない。** 求める値の名前は架空で、写したのは形だけになる。外し方が 7 通りあること、置き場が 8 値に分かれること、1 つの旧軸の列が複数の置き場に割れること、原文の記号と登録表の記号が食い違う行が在ることの 4 つだ。

使い方として想定しているのは、自分の「対象外」の一覧をそのまま入力にすることだ。対象外と書いた項目を 1 行ずつ並べ、印を 7 つ宣言する。**宣言できない印があれば `宣言なし` と書く。** そこは別枠に出るので、まだ決めていないことが件数で見える。推測で埋めるより、空いていることが分かるほうがいい。置き場が決まった項目には、その置き場が要求する欄の名前が付いて返る。渡すときに何を添えるかが、そこで決まる。

## 別の業種なら

この部品が持っている欄は、問い id・旧軸の値・旧軸の一覧 id・外し方の記号・印 7 つ・置き場の記号・要求する欄の名前・出典だけで、給与や社会保険の言葉も制度の言葉も 1 つも入っていない。会計なら、「マスタ外」と書いた項目の中に、科目の対応表に入る値と、会社ごとに決める値(部門コード・配賦基準)と、人が読んで決める値(交際費か会議費か)と、締めの期限(月次の提出日 = 起算日 + N 日)が混ざる。買い物の仕組みなら、全店共通の価格表と、店舗ごとの送料やポイント率と、与信や返品の可否の判断と、キャンペーンの受付期限。運送なら、公定の運賃表と事業者ごとの割増と、積載可否の判断。医療や介護なら、点数と単価と、施設ごとの加算の取得状況と、要介護認定という判断と、請求の期限。建設なら、公表された労務単価と現場ごとの歩掛りと、施工可否の判断。製造なら、規格値と工場ごとの公差と、外観検査の合否判定。どれも「全員に共通で決まっている値」「主体ごとに違う値」「人が読んで決める値」「期限だから式で書ける値」の 4 つが同じ袋に入るので、同じ部品がそのまま使えると考えている。私が測ったのは上の合成した 3 枚の範囲だけなので、ほかの分野は同じ詰まり方になりそうな例であって実測ではない。変わるのは登録表に書く印の組み合わせだけで、入力例の言葉を替えればそのまま動く。

## できないこと

- **分類の規則そのものは判定しない。** 印から置き場を導く規則は登録表の側にあり、その規則が正しいかは人が決める。道具は当てるだけだ
- **自然文を読まない。** 求める値の名前や例示の文から印を推測する経路が無い。事実認定を道具がやらない形にしてある
- **期限を計算しない。** ② は置き場を仕分けるだけで、起算日に N 日を足す経路も暦も休日表も持たない。そこは[期間を境界で切る回](https://chronicles-of-solo-parenting.blogspot.com/2026/10/blog-post_13.html)と[日付の種別を台帳にする回](https://chronicles-of-solo-parenting.blogspot.com/2026/10/blog-post_17.html)の領分になる
- **判断を起票しない。** ④ は受け取る属性の名前を返すだけで、値を作る経路も既定値も無い
- **履歴を舐めない。** ⑤ は供給する閾値の名前を返すだけで、通算も待期も実装しない
- **施行日が決まっている行は扱わない。** ⑦ は決まっていない行だけで、決まっている行は[効き始める日が来るまで予定として返す回](https://chronicles-of-solo-parenting.blogspot.com/2026/10/blog-post_19.html)の仕事になる。分かれ目は印 1 つだ
- **順位も良し悪しも付けない。** 「自動化しやすい」「あきらめる」のような語彙を持っていない
- **原文の記号と登録表の記号が違っても、どちらが正しいとも言わない。** 両方を並べて件数を数えるだけだ
- **一覧の側を読まない。** 一覧 id に写した値と台帳の値が合うかまでで、一覧が本当にそう書いてあるかは確かめない。写し間違いまでしか拾えない
- 図 1 の分け方は、手元の 2 つの記録に書かれている行までを拾ったもので、条文も官報も実装のコードも見ていない。8 件という数も、その章に書かれている行の数でしかない
- 上の件数は、合成した 3 枚の表に対する測定で、他の人の環境で同じ数字になるとは限らない
