前の 2 回で、数表を AI へ渡す側と、返ってきた文章を突き合わせる側が揃った。ここからは検証そのものを題材にする。この記事で作るのは、書かれている検証を数える部品ではなく、宣言された実行コマンドだけを実際に走らせて、その結果だけを台帳に残す部品になる。骨は 1 行で言える。**「検証が在る」と「検証が通った」は別の事実で、数えた件数は前者しか言っていない。**

**なぜ重要か**: 私の手元の棚卸し記録には、テストが在ると数えられたのが 39 本、無いのが 18 本、在るか分からないのが 10 本と書いてある。合わせて 67 本ぶんの行があり、検証が厚いように見える。ところが同じ記録の中に、その件数は文字列の検索で数えたもので実行はしていない、という注記が付いている。つまり走らせた結果は 1 件も無い。この 39 という数は「走らせてよい形になっているものが 39 本ある」という意味で、「39 本が通った」とは一言も言っていない。それでも報告に並ぶと通ったように読める。この記事の部品は、その読み替えが起きないように、在ると数えた列と走らせた結果の列を同じ表に並べて出す。

**要点**:
- 判定は 4 値にする。通った・落ちた・走らなかった・テストが無い。走らなかったものを通ったにも落ちたにも混ぜない
- 走らせるのは宣言表に書かれた argv だけ。フォルダを見て実行コマンドを推測で組み立てる経路も、文字列を結合してシェルに渡す経路も持たない
- 合格率は単独では返らない。4 値の件数と、分母に何を含めたかが必ず一緒に付く
- 台帳の判定部分に所要時間・時刻・ホスト名を入れない。2 回走らせて判定部分を突き合わせ、合わなければ合わなかったとだけ返す

**数字で見る**: 合成プロジェクトを 10 行の宣言表で走らせると、宣言では在るが 8 行なのに対し、走らせて通ったのは 3 行だった。落ちた 3・走らなかった 3・テストが無い 1 で、合格率は走らせた行だけを分母にすると 0.5000、宣言の行すべてを分母にすると 0.3000 になる。

---

## 何を解決するのか

棚卸しのとき、私は自分の道具を一覧にして、それぞれにテストが在るかどうかを書き込んだ。やり方は単純で、フォルダの中にテストらしきファイルがあるかを文字列で探しただけだ。結果は、在る 39・無い 18・不明 10。

この表を見た瞬間、私は「検証はだいたい足りている」と思った。思ってから、記録に自分で書いた注記を読み直した。文字列の検索で数えたもので、実行はしていない、と書いてある。

### 在ると数えた数は、結果を 1 件も言っていない

ここで何が起きていたかを分けて書く。私が持っていたのは「走らせてよい形になっているものが 39 本ある」という事実で、欲しかったのは「いま走らせたら何本通るか」という事実だった。この 2 つは別物で、前者から後者は出てこない。

出てこないのに混ざるのは、どちらも同じ「39」という数の見た目をしているからだ。報告に 1 行で書くと、どちらの意味だったかは文面から消える。

さらに悪いことに、数えた側の数は放っておくと増える。テストのファイルは消さないので、一度 39 になれば 39 のままだ。走らせた結果のほうは、環境が変わればすぐ落ちるのに、誰も走らせないので落ちたことが分からない。**件数は古くならないが、結果は古くなる。** 古くならない数だけが報告に残る形になっていた。

### 走らせるだけなら簡単だが、そこに罠がある

では走らせればいい、となる。ここで素直に作ると、たいてい次の形になる。フォルダを順に見て、テストらしきファイルを見つけたら、それらしい実行コマンドを組み立てて走らせる。結果を集計して合格率を出す。

この形には入れたくない経路が 4 つ入ってしまう。

1 つめは、実行するコマンドを機械が推測することだ。フォルダの中身から組み立てるということは、宣言されていないコマンドを自分の手元で動かすことになる。どれを走らせたのかは後から出力を読まないと分からず、宣言表と突き合わせることもできない。

2 つめは、走らなかったものの扱いだ。実行ファイルが無い、時間切れ、フォルダが無い。このとき多くの集計は、落ちた側に入れるか、黙って飛ばす。落ちた側に入れると「テストが壊れている」ように見え、飛ばすと分母から消えて合格率が上がる。どちらも、起きた事実と違う。

3 つめは、合格率を 1 つの数で返すことだ。分母に何を含めたかが付いていない合格率は、走らなかった行を外せばいくらでも上がる。

4 つめは、結果が揺れることだ。テストの出力には時刻や所要時間が混ざる。それを含めて指紋を取ると毎回変わり、変わるのが当たり前になると、本当に結果が変わったときに気づけなくなる。

### 直し方は、宣言を先に置くこと

やめ方は単純で、走らせるものを全部先に宣言表に書かせることだ。部品はその表に書かれた argv だけを、配列のまま実行する。表に無いものは走らせない。表から読めないものは走らせずに止まる。

表の列はこれだけになる。

| 欄 | 何を宣言するか |
|---|---|
| `name` | 行を指す名前。空欄も重複も止まる |
| `path` | 走らせるフォルダ |
| `declared` | 文字列検索で数えた「テストが在るか」。在る / 無い / 不明 |
| `runner` | 実行する argv を JSON の配列で書く |
| `timeout` | 秒。この表から取る |
| `required` | はい / いいえ。はい の行が通らなければ終了コード 3 |
| `allow_network` | はい / いいえ / 空欄。空欄は外向きの既定を落として走らせる |
| `source` | その宣言がどの記録から来たか |

`declared` の列を残してあるのがこの部品の肝になる。文字列検索で数えた数を捨てずに持ち、**走らせた結果と必ず並べて出す。** 捨ててしまうと、在ると数えていたのに走らなかった行が報告から消える。並べて出すと、その差が毎回目に入る。

## 図 1 検証の在り方と、走らせたらどの箱に入ったか

![検証の在り方 7 とおりを行に、宣言では在る・通った・落ちた・走らなかった・テストが無い を列にした対応表](figures/check_census_cases.png)

行が検証の在り方、列が宣言の側と判定の 4 値だ。藍が実走で通ったところ、橙が実走でその箱に入って人に戻すところ、無彩色が宣言の側の数か 0 件になる。各セルの件数は合成プロジェクトに対してその場で動かした判定の出力で、テストが固定している。

いちばん左の列と、その右の 4 列を見比べるのがこの図の使い方になる。

1 行目が「在ると数えた」行で、ここに手元の記録の 39 本が入る。合成プロジェクトでは 5 行あり、走らせると通った 2・落ちた 2・走らなかった 1 に分かれた。**在ると数えた 5 がそのまま通った 5 にはならない。** 手元の記録の側には、この右 4 列にあたる数がまだ 1 つも無い。

2 行目と 3 行目は、記録で「無い」「不明」と数えた行だ。無いと宣言した行は走らせず、テストが無いの箱に入る。不明の行は走らせる。**不明を「無い」に寄せない。** 寄せると、在るか分からないものが全部「テストが無い」に化けて、合格率の分母から消える。

4 行目から 6 行目は、在ると数えたのに結果が出ない 3 とおりになる。テストのファイルはあるが中に試験が 1 件も無い場合は、実行コマンドが「何も走らなかった」という終了コードを返すので落ちたに入る。実行する argv が宣言されていない場合と、時間切れの場合は、走らなかったに理由コード付きで入る。

7 行目は、2 回走らせると結果が変わる行だ。これは本体の台帳には入れず、別の宣言表で `verify` にかけている。終了コードは 2 回とも同じなのに、出力の指紋だけが違う。この部品はそれを吸収せず、不一致としてそのまま返す。

## 手順

入力は宣言表 1 枚だけだ。`init` でひな型が出る。

```
python check_census.py init 宣言表.csv
```

書き込むとこうなる。`runner` は JSON の配列で、文字列ではない。

```
name,path,declared,runner,timeout,required,allow_network,source
道具A_通る,proj/tool_a,在る,"[""python"", ""run_ok.py""]",20,はい,,合成の棚卸し記録(架空)
道具D_テスト無し,proj/tool_d,無い,,20,いいえ,,合成の棚卸し記録(架空)
道具E_在るか不明,proj/tool_e,不明,"[""python"", ""run_ok.py""]",20,いいえ,,合成の棚卸し記録(架空)
道具K_外向き許可,proj/tool_k,在る,"[""python"", ""run_net.py""]",20,いいえ,はい,合成の棚卸し記録(架空)
```

配列で書かせているのは、文字列を結合してコマンドを作る経路を 1 本も作らないためだ。配列のまま実行に渡せば、空白や引用符の入ったパスで意味が変わることがない。シェルを経由する指定はソースのどこにも無く、そのことをテストで固定してある。

走らせるとこうなる。

```
python check_census.py census 宣言表.csv
```

返るのは、宣言の側の件数と 4 値の件数、分母の内訳、2 つの合格率、それに 1 行ごとの判定になる。

```
{"ok": true, "stage": "台帳にした",
 "宣言で在る": 8, "宣言で無い": 1, "宣言で不明": 1,
 "通った": 3, "落ちた": 3, "走らなかった": 3, "テストが無い": 1,
 "宣言の行数": 10, "走らせた数": 6, "走らなかった数": 3, "テストが無い数": 1,
 "合格率_走らせた行のみ": "0.5000", "合格率_宣言の行すべて": "0.3000",
 "分母に含めたもの": "走らせた行のみ = 通った 3 + 落ちた 3 = 6(走らなかった 3 + テストが無い 1 を
                   除いた分母) / 宣言の行すべて = 10(走らなかった行とテストが無い行を含む分母)",
 "在ると数えた数は結果を 1 件も言わない": "宣言では在る 8 / 走らせて通った 3"}
```

同じ台帳から合格率が 2 つ出る。走らなかった行とテストが無い行を分母から落とすと `0.3000` が `0.5000` になるので、片方だけを引用できない形にしてある。これは前々回の一致率、その前の通した割合と同じ作りだ。最後の 1 行は、この記事の骨をそのまま出力の欄にしたもので、報告から外せない。

1 行ごとの判定は 6 欄で固定されている。

```
{"name": "道具C_時間超過", "宣言": "在る", "判定": "走らなかった",
 "理由コード": "timeout", "終了コード": null, "出力の末尾の指紋": ""}
```

走らなかった行とテストが無い行には終了コードが入らない。ここを `0` や `-1` で埋めると、集計のときに通ったか落ちたかに混ざる。空にしてあるので混ざらない。

走らなかったに付く理由コードは 4 つだけだ。

```
runner が無い(argv が空、または実行ファイルが見つからない) / timeout /
宣言の列が空欄(name か path が空) / path が無い
```

所要時間・時刻・ホスト名は、判定とは別の欄に出る。下は機器名を伏せた抜粋になる。

```
"測った条件": [{"name": "道具A_通る", "所要秒": "0.039", "始めた時刻": "…", "ホスト名": "…"},
             {"name": "道具C_時間超過", "所要秒": "", "始めた時刻": "…", "ホスト名": "…"}]
```

この 3 つを判定部分から外してあるのが、次の `verify` の前提になる。

```
python check_census.py verify 宣言表.csv
```

`verify` は 2 回走らせて、判定部分のバイト列の sha256 を突き合わせる。合えば一致と返し、合わなければどの行のどの欄が違ったかを返す。

```
{"ok": false, "一致": false, "判定した回数": 2,
 "観測": "走らせた対象が同じ入力に同じ結果を返していない(平均も多数決もしない)",
 "不一致の内訳": [{"name": "道具I_揺れる", "違った欄": {"出力の末尾の指紋": ["252b06…", "d6715a…"]}}]}
```

ここで返しているのは判定ではなく観測だ。2 回のうちどちらが正しいとは言わないし、平均も多数決も取らない。終了コードは両方 0 で、違ったのは出力の指紋だけ、という事実をそのまま出す。

関数として呼ぶ形も同じになる。

```python
from check_census import Declaration, census

c = census(Declaration.load("宣言表.csv"))
print(c.rate() if c.report.ok else [x.reason for x in c.report.pending])
```

引数は宣言表 1 つだけで、「走らなかったを落ちたに含める」「合格率だけ返す」「落ちたら直して再実行する」に相当する引数は 1 つも無い。CLI の option も `-h` 以外に 1 つも無く、これもテストで固定してある。

## 検証

テストは 25 件で、合成プロジェクトを相手に走らせている。実在の道具の名前もパスも入れていない。合成の実行ファイルは外へ 1 バイトも出ない。

```
$ python -m pytest tools/check_census -q
...
[measure] 宣言表 10 行(テストが在る 8 / 無い 1 / 不明 1)を走らせる
[measure] 4 値: 通った 3 / 落ちた 3 / 走らなかった 3 / テストが無い 1
[measure] 合格率: 走らせた行のみ(分母 6)= 0.5000 / 宣言の行すべて(分母 10)= 0.3000
[measure] 在ると数えた数は結果を言わない: 宣言では在る 8 / 走らせて通った 3
[measure] 在り方『在ると数えた』: {'宣言では在る': 5, '通った': 2, '落ちた': 2, '走らなかった': 1}
[measure] 在り方『無いと数えた』: {'テストが無い': 1}
[measure] 在り方『在るか不明』: {'通った': 1}
[measure] 在り方『試験が 1 件も無い』: {'宣言では在る': 1, '落ちた': 1}
[measure] 在り方『runner 未宣言』: {'宣言では在る': 1, '走らなかった': 1}
[measure] 在り方『timeout 超過』: {'宣言では在る': 1, '走らなかった': 1}
[measure] 在り方『2 回で変わる』: 本体の台帳には入れない(verify で観測)
[measure] 走らなかった 3 件の理由コード: path が無い / runner が無い / timeout(本体の宣言表)

[measure] 落ちた 3 件の終了コード: 1 が 2 件(落ちる runner / 外向きを落として走らせた runner)、5 が 1 件(試験が 1 件も無い)
[measure] 同じ宣言表で 2 回走らせる: 判定部分の sha256 が一致(先頭 12 桁 ab67d3d980ed)
[measure] 2 回で出力が変わる 1 行: 不一致として返る。違った欄は ['出力の末尾の指紋'] だけで、終了コードは 2 回とも同じ
[measure] 判定部分はバイト列として同一、測った条件(所要秒 / 時刻 / ホスト名)は 2 回で違う = 非決定な値は一致判定に混ざっていない
[measure] 止まった: 宣言表に必要な列が無い(宣言表に runner の列が無い)
[measure] 止まった: argv が配列でない(行 2(道具A_通る)の runner: python run_ok.py)
[measure] 止まった: timeout が空欄か数でない(行 2(道具A_通る)の timeout: 空欄)
[measure] 止まった: 出典の列が空欄(行 2(道具A_通る)の出典が空欄)
[measure] 止まった: 同じ name の行が 2 件以上(道具A_通る: 行 2 と行 3)
[measure] 止まる理由コード 6 個すべてに道がある
[measure] 走らせる前と後で合成プロジェクト全体(8 本の script を含む)の sha256 が同じ = 宣言表もテストもコードも書き換えていない
25 passed
```

4 値の内訳を補う。通った 3 件は、普通に終了コード 0 を返した行が 2 件(うち 1 件は在るか不明と数えられていた行)と、外向きの通信を宣言で許した行が 1 件だ。落ちた 3 件のうち 2 件は終了コード 1 で、片方は素直に落ちる行、もう片方は外向きの既定を落とした状態で走らせたために落ちた行になる。残る 1 件は終了コード 5 で、これはテストのファイルはあるが中に試験が 1 件も無い場合にあたる。**この 1 件を通ったに混ぜないことが、この部品でいちばん地味で大事なところだと考えている。** 試験が 0 件なら何も失敗しないので、素朴に作ると通ったに入ってしまう。

走らなかった 3 件は、時間切れ・実行する argv が宣言されていない・フォルダが無い、の 3 つだ。4 つめの理由コードである「宣言の列が空欄」は本体の宣言表には入れていないので、`path` 欄を空にした別の表を通して、4 つ全部に道があることを見ている。

止まる理由コードは 6 つで、こちらは崩した宣言表を 5 枚通し、残る 1 つ(2 回目の判定部分が不一致)は出力が毎回変わる行で通した。**止まったときは 1 行も走らせない。** 宣言表が読めないのに一部だけ走らせると、台帳の分母が何なのか決まらなくなる。

決定論の確認は 2 つある。1 つは、同じ宣言表から 2 回走らせて判定部分のバイト列が一致すること。もう 1 つは、同じ 2 回で「測った条件」のほうは違っていることだ。後者が違っていなければ、時刻を判定に混ぜていないことの確認にならない。

書き換えていないことも測った。走らせる前と後で、合成プロジェクト全体の指紋が同じになる。テストを直す経路も、宣言表を書き戻す経路も持っていない。

いつも成り立つことは 1 文にして、性質テストで確かめている。台帳の結果は 2 通りしかない。宣言表の行のひとつひとつがちょうど 1 つの判定に入り、その合計が宣言の行数に等しく、走らなかった行とテストが無い行には終了コードが無く、通った行の終了コードは 0、落ちた行は 0 以外で、判定部分のバイト列に所要時間・時刻・ホスト名が 1 つも入らないか、判定が 1 件も返らず理由コードが返るか、だ。どちらの場合も、宣言表もテストもコードも 1 文字も書き換わらない。宣言表を毎回乱数で作り直し、1 行ごとに 8 とおりの在り方から引き、4 割くらいの確率で表のどこか 1 か所を崩して、毎回この 1 文が成り立つかを見る。乱数は固定で、毎回同じ 50 通りを試す。**その行が通るはずか走らないはずかは、部品の判定を呼ばずにテストの側で持っている。** 同じファイルの 2 本目は分母の恒等式を見ていて、走らせた行だけを分母にした合格率が、宣言の行すべてを分母にした合格率を下回らないこと、つまり狭い分母だけを引用すると必ず上振れする側に出ることを、300 通りで確かめている。

## 図 2 台帳を作る流れと、止まる場所

![宣言表を読み、argv と出典を見て、timeout と name を見て、走らせて 4 値に分け、2 回判定して返すまでの流れ図](figures/check_census_flow.png)

段は 6 つで、橙のピルが関所だ。前の 3 段は 1 行も走らせる前の検査で、宣言表の形だけを見ている。

この図で見てほしいのは、描かれていない経路のほうになる。走らせる段へ入ってくる矢印は宣言表からの 1 本だけで、フォルダを見て実行コマンドを組み立てる経路が無い。4 値に分ける段から「走らなかったを落ちたにまとめる」へ出る矢印も無い。落ちた行から「直して再実行する」へ戻る矢印も無い。最後の段から「合格率だけを返す」へ出る矢印も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

検査を走らせる前に置いてあるのが今回の並びの肝になる。宣言表が読めないまま一部だけ走らせると、出てきた件数の分母が決まらない。分母が決まらない件数は、合格率に直した瞬間に意味を失う。

最後の段は前回までと同じで、判定を 2 回行って自分の出力を突き合わせている。違うのは、合わなかったときに返すものだ。前回までは止まる理由だったが、今回はそれに加えて、どの行のどの欄が違ったかが出る。終了コードが同じで指紋だけ違うのか、終了コードから違うのかは、見分けたい差だからだ。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/check_census) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。

自分の手元に合わせるときは、宣言表の CSV を書くだけでいい。部品のコードは触らない。終了コードは、止まらずに `required` が はい の行が全部通ったときだけ 0 で、それ以外は 3 になる。まとめて走らせる仕組みの中に置いて、3 で止められる。

外向きの通信は、行ごとに許すまで既定で落ちる。許していない行は、外向きの設定を落とした状態で走り、それで落ちたなら落ちたと書かれる。

## 別の業種なら

この部品が持っている欄は `name` と `path` と `declared` と `runner` と `timeout` と `required` と `allow_network` と `source` の 8 つだけで、給与や社会保険の語彙は 1 つも入っていない。会計なら締めのチェック表、EC なら在庫と受注の照合、建設なら出来高の検査、医療・介護なら請求前の点検。どれも「検査の手順は書いてあるが、最後に走らせたのがいつか誰も言えない」形で滞っていくので、同じ台帳がそのまま使えると考えている。私が測ったのは上の合成プロジェクトの範囲だけなので、他の分野は同じ詰まり方になりそうな例であって実測ではない。変わるのは宣言表に書く中身だけで、部品のコードはそのまま使える。

## できないこと

- 判定したことは「宣言された実行コマンドが終了コード 0 を返したか」までで、**テストが正しいことは判定しない**。通っても、そのテストが見るべきものを見ているとは言えない
- 対象が仕様どおり動くことも判定しない。見ているのは終了コードだけになる
- **カバレッジを測らない**。網羅しているか、どの行が通ったかは部品の外になる
- **なぜ走っていなかったのかは分からない**。在ると数えた数と走らせた結果の差は出るが、その差がなぜ生まれたかは出ない。理由を書かないのは意図的で、私の手元にその出典が無いからだ
- 外向きを落とすのは設定の側だけで、通信そのものを塞ぐわけではない。設定を見ない通信は通る。確実に塞ぐなら、この部品の外でやることになる
- 出力の指紋は末尾 10 行だけで、途中の行は見ていない。末尾に時刻や所要時間を書く実行コマンドは、結果が同じでも指紋が毎回変わり、`verify` が不一致として返す。吸収する経路は入れていない
- 時間切れで止めた行の途中までの出力は捨てる。**「途中まで通っていた」は残らない**
- 宣言表の正しさは判定しない。書いた argv が本当にその対象のテストなのか、`declared` の「在る」が合っているかは、宣言を書く人の側になる
- 上の件数は合成プロジェクトでの測定で、他の人の手元で同じ数字になるとは限らない。手元の記録の側の 39 / 18 / 10 については、**この記事でも 1 件も走らせていない**。走らせた結果を出すのはこれからになる
