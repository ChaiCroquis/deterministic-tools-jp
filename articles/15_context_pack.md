ここまでの数本は、機械が次の機械に渡す話だった。形の違う表を読み替え、2 つの軸から足して止め、取込先の仕様に入らない行を仕分ける。今回は同じ行を AI に渡す。引いた 1 行をプロンプトに貼るだけの工程なのだが、ここで落とすと上流で固めたものが全部効かなくなる。この記事で作るのは、引いた行 1 件を、版と出典を焼いた塊にして返す部品だ。短くするための部品ではない。

**なぜ重要か**: 数表を引く仕組みは、前に 2 本かけて作った。[基準日と公表時点を列にして引く部品](https://chronicles-of-solo-parenting.blogspot.com/2026/09/blog-post_28.html)と、[値 1 件をピン 1 行にして原本と突き合わせる部品](https://chronicles-of-solo-parenting.blogspot.com/2026/09/blog-post_30.html)だ。どちらも「決まらないときは値を返さない」という形にしてある。ところが、その 1 行をプロンプトに貼った瞬間、読み手の性質が変わる。人は表を開けば版が見える。機械は引数で版を指定できる。**AI は渡された塊の中にしか版を持てない。** 塊に版が焼かれていなければ、AI は自分が覚えている値で埋めるしかなく、それはもっともらしく古い。だからこの部品は、欠けている列があれば塊を作らずに止まる。この記事で見たいのは塊の書式ではなく、**同じ行を「誰が読むか」の軸で並べ直すと、版の辿り方だけが読み手ごとに違う**という点のほうだ。

**要点**:
- 焼くのは 8 列(値・対象・有効期間・公表時点・出典・原本のファイル名と行番号と指紋)。どれか 1 つでも空欄なら、塊を作らずに止まる
- 要約も言い換えも切り詰めもしない。宣言された字数の上限を超えたときは、短くするのではなく止まる
- 公表時点が仮置きの行は、仮置きだと塊の中に書く。確定値の顔のまま渡さない
- 減った量は文字数とバイト数でしか言わない。トークン数は返さない。分割器はこの部品の外にあり、出典にしてよいファイルにも無い

**数字で見る**: 合成の引いた行 12 行に問い 12 件を流すと、塊ができたのは 5 件で、残り 7 件は 7 種類の理由コードで止まった。同じ 1 件を渡す形で比べると、表全体をそのまま貼れば 4,174 字、機械が引数で引く 1 行 JSON が 346 字、この塊が 192 字、値だけなら 5 字だった。

## 何を解決するのか

まず、これが私の手元で起きている形だという前提から書く。

私の数表は、いま 1,681 行、45 種類のルールが入っている。引く側は 1 行 JSON を返し、出力には使った行の出典と有効開始日が必ず付く。収録は 5 つの軸を持つ行の形と、数式の登録簿でできている。料率の原本からは 3 年ぶんの折半額を 7,050 とおり計算し直して全部一致したので、「取れたものは取れている」ほうはわりと固い。更新も無人の手順で回していて、履歴は 11 回ぶんある。

足りていないのは、その 1 行をプロンプトへ貼る瞬間のほうだった。

AI に数表の値を聞くと、たいてい何か答えが返る。返ってきた値が去年のものでも、形は今年のものと同じだ。これは AI が嘘をついているのではなく、**渡された文字列の中に版が無いから、持っている知識で埋めている**だけになる。私がやっていたのは、引いた 1 行の中から値だけをコピーしてプロンプトに貼ることだった。貼られた側から見ると、その値がいつからのものか、いつ公表されたものか、どの表の何行目から来たのかは、どこにも書かれていない。

ここで効き目がありそうに見えるのは、表をまるごと貼ることだ。全部渡して選ばせれば間違えない、と考えたくなる。やってみると逆で、どの行が読まれたのかが分からなくなる。版は塊の中に入ってはいるのだが、複数入っている。後から「この計算はどの版でやったのか」と聞かれても、貼った塊を見せるしかなく、答えは決まらない。

### 版の辿り方は、読み手ごとに違う

整理すると、同じ 1 行でも渡し方は 5 つあって、どれも「版をどう辿るか」だけが違う。

人が開く表では、版は表の側にある。開けば年度が目に入るし、該当が無ければ気づく。見落としはするが、構造としては版が手元にある。

機械が引数で引く形では、版は引数と返り値の中にある。基準日と公表時点を渡し、返ってきた行に出典が付く。決まらなければ値が返らない。これが前の 2 本で作った形だ。

AI に貼る塊では、版は塊の中にしか無い。ここだけ、渡した瞬間に外部参照が切れる。

表全体をそのまま貼る形と、値だけを貼る形は、どちらもその切れた先での選択になる。前者は版が複数あって決まらず、後者は版が 1 つも無い。

**この 5 つを分ける軸は「大きさ」ではない。** 大きさで並べると、表全体がいちばん大きくて値だけがいちばん小さい、という順番になるだけで、何も言えていない。実際、この部品が作る塊は 192 字で、機械が引数で引く 1 行 JSON の 346 字より小さい。小さいほうが版を多く持っている。並べ直す軸は読み手で、見るのは版の辿り方になる。

### 足すのは宣言で、文面ではない

直し方として、プロンプトのひな型に「出典も書いてね」と足すことは思いつく。これは弱い。文面は人が書き換えるし、書き忘れても何も起きない。足すのは貼り先の宣言のほうだ。

| 欄 | 宣言すること |
|---|---|
| `field` | 塊に出す行の名前。そのまま `名前: 値` の 1 行になる |
| `required` | 印が付いていれば必ず出す。空欄なら要求されたときだけ出す |
| `max_chars` | その行の値の字数の上限。超えたら切り詰めずに止まる |
| `pin` | 版として焼く列の名前。`\|` で複数書ける |

宣言表を書く人が、何をどの名前で焼くかを決める。ただし **8 つの列だけは外せない**。値・対象・有効期間・公表時点・出典・原本のファイル名・原本の行番号・原本の指紋が、どれか 1 つでも宣言から落ちていれば、部品は塊を作る前に宣言の不備として止まる。線を動かすのは宣言を書く人だが、この 8 列の内側までは動かせない。

## 図 1 同じ 1 行を誰に渡すか

![渡す形 5 つと、版が中から辿れるか・問いが宣言の外なら止まるか・大きさ・古い値が黙って通り得るか の対応表](figures/context_pack_axes.png)

行が渡す形、列が 4 つの見どころだ。藍が実走で確かめて満たしていたところ、橙が満たさないか、こちら側からは閉じられないところ、無彩色がその形では問いにならないところになる。各セルの件数と字数は、合成の行に対してその場で動かした組み立ての出力で、テストが固定している。

この連載で軸を引いた図はこれで 3 枚目になる。[理由の列を軸にした回](https://chronicles-of-solo-parenting.blogspot.com/2026/09/blog-post_26.html)は「なぜこの色なのか」を列にし、[2 つの軸から足して止める回](https://chronicles-of-solo-parenting.blogspot.com/2026/10/blog-post.html)は集計の軸を列にした。今回の軸は読み手で、前の 2 枚とは別の切り方にしてある。同じ軸で並べ直しただけの図を増やしても、新しいことは出てこない。

読みどころは 3 つある。

1 つめは、**大きさの列と、ほかの 3 列が揃っていない**ところだ。塊は 192 字で、機械が引数で引く 1 行 JSON の 346 字より小さいのに、版の辿り方では同じ扱いになっている。逆に表全体は 4,174 字あって、いちばん大きいのに版が辿れない。大きさは読み手の軸と関係が無い、というのがこの表でいちばんはっきり出たところだった。

2 つめは、**右端の列だけ、藍が 1 つも無い**ことだ。古い値が黙って通る経路は、どの渡し方でも完全には閉じられない。塊に版を焼いても、AI がその塊を無視して記憶から答えることはできる。部品ができるのは「版の無い塊を作らない」までで、「版のある塊を読ませる」ところには手が届かない。ここを藍で塗りたくなったが、実走で確かめられないので橙にしてある。

3 つめは、下の 2 行が**どちらも「止まらない」**ところだ。表全体を貼る形と値だけを貼る形は、問いが収録の外にあっても何かが返ってくる。止まる仕組みが無いのではなく、止まる場所が読み手の側に移っている。だからこの部品は、表全体を貼る引数を持たせていない。持たせれば、止まる場所がそこから外へ出てしまう。

## 手順

入力は 2 つだ。1 つは引いた行で、前の工程が返してくる。列は 13 で、これ以外の列が混ざっていれば、引いた行として読めないものとして終了コード 2 で返る。

```
rule,selector,valid_from,valid_to,known_from,known_quality,priority,payload,source,source_file,source_row,source_sha256
保険料率_甲,地域=地域A,2026-03-01,,2026-02-10,実値,0,9.70,合成の料率表 2026 年度版(架空),moto_ryouritsu.csv,2,995a9e...
```

もう 1 つが貼り先の宣言表になる。1 つの `field` が 1 行で、欄は 4 つだ。

```
field,required,max_chars,pin
値,○,40,payload
対象,○,120,rule|selector
有効期間,○,40,valid_from|valid_to
公表時点,○,40,known_from|known_quality
出典,○,120,source
原本,○,160,source_file|source_row|source_sha256
順位,,20,priority
```

組み立てるときは、問いを 2 つとも渡す。どちらにも既定を持たせていない。

```
python context_pack.py pack 引いた行.csv --decl 宣言表.csv --rule 保険料率_甲 --select 地域=地域A
```

返るのはこの塊だ。

```
値: 9.70
対象: 保険料率_甲 / 地域=地域A
有効期間: 2026-03-01 / (なし)
公表時点: 2026-02-10 / 実値
出典: 合成の料率表 2026 年度版(架空)
原本: moto_ryouritsu.csv / 2 / 995a9e72d10370417205e3452889f7a82ce0ffbe83c86e5a8a9f3e1733a92745
```

行の順は宣言表の順、区切りは 2 種類だけ、改行は 1 種類だけで、最後の行の後ろにも改行が 1 つ付く。有効期間の終わりが無い行は `(なし)` と書く。ここを「以降」と書けば読みやすくはなるが、それは行に書かれていない言葉なので入れていない。値は Decimal の文字列で出すので、`9.70` の末尾のゼロも落ちない。

公表時点が仮置きの行だと、塊が 1 行増える。

```
値: 1.60
公表時点: 2026-03-01 / 仮置き
注記: 公表時点は仮置き(確定値ではない)
```

私の表では、公表日が実際に分かっている行は一部しかなく、残りは適用開始日で代用してある。これは前に書いたとおりの弱点で、直せていない。直せていないものを黙って確定値の顔で渡さないために、仮置きの行には塊の中で注記が付く。実値の行の塊が 192 字、仮置きの行が 215 字で、差の 23 字がこの 1 行になる。

欠けている列があるときは、塊を作らずに止まる。

```
{"ok": false, "stage": "組み立て", "行": 12, "該当": 1,
 "pending": [{"reason": "sha256 が無い", "detail": "source_sha256 が空欄"}]}
```

止まる理由コードは 10 個で、これ以上増やしていない。

```
出典が空欄 / sha256 が無い / 有効期間が空欄 / 公表時点が空欄 /
該当 0 件 / 該当 2 件以上 / 宣言に無い field を要求 /
max_chars 超過 / 2 回目の組み立てでバイト列が不一致 / pin に指定された列が行に無い
```

上限を超えたときに切り詰めないことは、理由コードの中に書いてある。合成の行の 1 つは出典の文字列が 122 字あり、宣言した上限は 120 字だ。ここで 2 字削れば入るのだが、削らずに止まる。要約は決定論ではないので、部品の仕事にしていない。

該当が 1 行に決まらないときも止まる。

```
$ python context_pack.py pack 引いた行.csv --decl 宣言表.csv --rule 保険料率_丙 --select 地域=地域A
{"ok": false, "stage": "突き合わせ", "pending": [{"reason": "該当 2 件以上",
 "detail": "問い rule=保険料率_丙 / selector=地域=地域A に 2 行当たった(行 11 / 12)"}]}
```

当たった 2 行は順位の列が違う。片方は本則で、片方は経過措置だ。それでも勝たせない。順位で勝ち負けを決めるのは引く側の仕事で、塊を作る側がもう一度やると、引く側の判断と食い違ったときに気づけなくなる。

大きさは、比べた相手と一緒にしか出てこない。

```
{"大きさ": {"文字数": 192, "バイト数": 270},
 "比べた相手": {"表全体をそのまま貼る": {"文字数": 4174, "バイト数": 4880},
                "機械が引数で引く 1 行": {"文字数": 346, "バイト数": 390},
                "値だけを貼る": {"文字数": 5, "バイト数": 5}},
 "表全体から減った文字数": 3982, "値だけより増えた文字数": 187,
 "proxy の限界": "文字数とバイト数は token 数の代わりにならない。分割器は部品の外にあり、
                  出典にしてよいファイルにも無いので、token 数は返さない"}
```

最後の行は飾りではない。文字数が減れば token も減る、とは限らない。どこで切るかはモデル側の分割器が決めていて、その分割器はこの部品の外にあり、私が出典として使えるファイルの中にも無い。だから測れるものだけを返し、測れないものは返さないことを出力自体に書いた。表全体の大きさは測るために内部で並べ直しているが、その文字列を返す経路は持たせていない。

関数として呼ぶ形も同じだ。

```python
from context_pack import Declaration, load_rows, pack

p = pack(load_rows("引いた行.csv"), Declaration.load("宣言表.csv"),
         {"rule": "保険料率_甲", "selector": "地域=地域A"})
print(p.text() if p.report.ok else [x.reason for x in p.report.pending])
```

`pack` の引数は行・宣言表・問い・出したい任意の `field` の 4 つだけで、「短くする」「全部渡す」「近い行で代用する」に相当する引数は 1 つも無い。これはテストでも固定してある。

## 検証

テストは 70 件で、fixture は全て合成データだ。地域名も料率も限度額も出典名も架空で、実在のものは 1 つも入れていない。原本にあたる CSV を 2 枚先に書き出し、その**本物の sha256** と行番号を引いた行に焼いてあるので、原本を 1 文字でも変えれば塊の中の指紋と合わなくなる。

```
$ python -m pytest tools/context_pack -q
```

止まった 7 件の内訳を補う。6 件は行の側で必ず焼く列が 1 つずつ欠けている行で、空にした欄は出典・指紋・有効期間の始まり・公表時点の品質・出典の長さの 5 とおりだ。公表時点の行は少し毛色が違って、日付そのものは入っているのに、それが実値か仮置きかの欄が空になっている。日付が入っていれば通してもよさそうに見えるが、通すと「仮置きを確定値として焼いた塊」ができてしまうので止めている。残る 1 件は、同じ問いに 2 行当たった側だ。

上の表には出ていないが、残り 3 つの理由コードにも道がある。宣言表に無い名前の `field` を要求したとき、宣言表が焼くと言っている列が行に無いとき、そして同じ問いから 2 回組み立ててバイト列が違ったときだ。最後のものは普通は起きないので、テストの中で組み立てだけを 1 か所差し替えて、その経路が本当に止まるかを見ている。10 個の理由コード全部に道があることは、テストで突き合わせてある。

入り口が違っても同じバイト列になることも測った。12 行の CSV から引いた場合と、引く側の CLI が返す 1 行 JSON をそのまま渡した場合で、塊の sha256 は一致する。変わるのは比べた相手の数字だけで、表全体の文字数が 4,174 から 346 になる。

残りのテストは、必ず焼く 8 列が塊の中に文字として現れること、行の順が宣言表の順と一致すること、任意の `field` を 1 つ足すと塊がちょうど 1 行増えること、組み立てのあいだ入力の行が 1 つも書き換わらないこと、止まったときに塊を取りに行くと例外になり途中まで作った塊も残っていないこと、要約や切り詰めや表全体を貼る引数がソースのどこにも無いこと、部品が依頼の文面らしき語を 1 つも書かないことを見ている。

いつも成り立つことは 1 文にして、性質テストで確かめている。組み立ての結果は 2 通りしかない。必ず焼く 8 列が欠けなく入った塊が 1 つ返り、同じ問いから 2 回目を組み立てても同じバイト列になるか、塊は 1 つも作られず理由コードが返るか、だ。どちらの場合も、この部品は入力の行を 1 つも書き換えず、要約も切り詰めもせず、ファイルを 1 つも開かない。宣言どおりの行を乱数で作り、9 通りから 1 つ引いて 1 か所だけ崩し、宣言表の側の上限と任意の `field` も乱数で動かして、毎回この 1 文が成り立つかを見る。乱数は固定で、毎回同じ 300 通りを試す。どの段でどの理由コードが返るかの判定は、道具の関数を使わず、テストの中に別に書いてある。

## 図 2 組み立ての流れと、止まる場所

![宣言を検査し、問いと行を突き合わせ、版を焼き、字数の上限を見て、2 回組み立てて返すまでの流れ図](figures/context_pack_flow.png)

段は 6 つで、橙のピルが関所だ。前の 3 段は宣言と問いの噛み合わせの検査で、1 文字も焼く前に置いてある。

この図でも見てほしいのは描かれていない経路のほうになる。字数の上限の段から先へ、「長いので要約する」や「上限まで切り詰める」に進む矢印がどこにも無い。突き合わせの段から「近い行で代用する」に出る矢印も無い。最初の段に「表全体を渡す」という入口も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

最後の段だけ少し変わっていて、組み立てを 2 回行って自分の出力を突き合わせている。同じ問いから 2 回作って違うものが出てきたら、それは決定論ではないということなので、そこで止める。実際に動かした範囲では 1 件も食い違っていないが、食い違わないことを確かめる段を持っているかどうかは別の話だと考えている。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/context_pack) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。宣言表のひな型は `init` で出る。

```
python context_pack.py init 宣言表.csv
```

自分の貼り先に合わせるときは、この CSV を書き換える。`field` の名前を日本語にしても英語にしてもいいし、順番も変えられる。部品のコードは触らない。ただし必ず焼く 8 列を落とした宣言表は受け付けないので、そこだけは書き換えられない。

## 別の業種なら

この部品が持っているのは、`field` と `required` と `max_chars` と `pin` という 4 つの欄だけで、給与や社会保険の語彙は 1 つも入っていない。税率や勘定科目の表、送料と手数料の表、歩掛、点数と加算の表。どれも「最新の値を AI に聞くと、もっともらしく違う値が返る」場面で、同じ構図だと考えている。私が実測したのは上の合成データの範囲だけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。変わるのは入力の行の中身だけで、保険料率の行を税率の行や送料の行に差し替えれば、部品はそのまま使える。焼く列の名前も、宣言表の `pin` を書き換えるだけで動く。

## できないこと

- 塊を作ったことは「宣言された列を欠けなく焼いた」までで、**AI がその塊を使うとは言えない**。貼った塊を無視して記憶から答える経路は、こちら側からは閉じられない。図 1 の右端の列に藍が 1 つも無いのはそのためだ
- **トークン数は測れない**。返しているのは文字数とバイト数で、分割器はモデル側にある。文字数が減れば token も減るとは限らないので、減った量を token で語らないことにした
- 値が制度として正しいかは判定しない。見ているのは行の列が埋まっているかと、字数が宣言に入るかだけになる
- 宣言表の正しさも判定しない。上限が雑なら止まりすぎるし、`pin` に要らない列を並べれば塊が太る。線を動かすのは宣言を書く人のほうだ
- 1 つの問いに 1 つの塊しか作らない。複数の値を 1 つのプロンプトに入れたいときは、問いの数だけ呼んで人が並べることになる。並べ方を部品の中に入れると、順序と区切りが塊の外で決まってしまう
- 公表時点が仮置きかどうかは、行の欄を読んでいるだけで、本当の公表日を調べてはいない。私の表では実値の行がまだ一部しかない
- 上の字数は合成データでの測定で、他の人の表で同じ数字になるとは限らない。塊の大きさは宣言表の `field` の数と出典の文字列の長さでほとんど決まる
