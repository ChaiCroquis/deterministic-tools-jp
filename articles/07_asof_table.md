料率・最低賃金・等級表・限度額のように毎年変わる数表は、たいてい「適用開始日つきの履歴」で持つ。私の記録でもそうしていた。表の各行に適用開始日を書いておき、引くときはその日以前でいちばん新しい行を採る。この形は素直で、ほとんどの月は正しい答えを返す。問題は「ほとんど」のほうではなく、そこから外れたときに**間違った値を黙って返す**ことだ。この記事では、日付 1 軸では表せないものを 4 つに分け、行の側に基準日・公表時点・対象・順位の列を足して、決まらないときは値を返さずに理由コードで止める小さな部品を作る。

**なぜ重要か**: ここまでの 6 本は、入ってきたデータの形を直す部品だった。文字コード、和暦、氏名、会社名、取込 CSV、差異の Excel。どれも「入力をどう読むか」の話で、読み方さえ決めれば答えは 1 つに決まる。今回からは相手が変わる。参照する側の表が毎年書き換わり、書き換わり方が 1 通りではない。ここで返ってくる値は、入力の形が正しくても間違いうる。しかも間違った値は例外にならず、そのまま給与の金額になって人に渡る。読み込みの部品をどれだけ固めても、引き当ての表が日付 1 軸のままなら、最後にそこで落ちる。

**要点**:
- どの日付で引くかは、ルールごとに違う。それを呼ぶ側に選ばせず、行の側に列として宣言させる
- いつ公表された知識かを列に持つ。公表日と施行日がずれる表は、日付 1 軸では当時の答えを再現できない
- 経過措置は「対象を限定した別の行」として持ち、どちらが勝つかは順位の列に書く
- 決まらないときは現行値や直近値へ落ちない。理由コードで止めて、引けた値には必ず出典と有効開始日を付ける

**数字で見る**: 合成した 44 行の表に 2,160 件の引き当てを流したところ、適用開始日 1 軸の引き方と答えが違ったのは 252 件(基準日の違いで 72 件、経過措置で 180 件、説明のつかない残差 0 件)で、うち 228 件は別の値が黙って返り、24 件は本来決まらないところに値が返っていた。この部品は同じ 2,160 件のうち 144 件を理由コードで止め、値を返した誤りは 0 件だった。

---

## 何を解決するのか

まず、これが私の手元で実際に起きている形だという前提のほうから書く。私の道具の棚卸しでは、履歴の扱いで詰まった道具は 27 本あった。料率・最低賃金・等級表を「適用開始日つきの履歴」で持つ共通の表が 1 つあり、その表を読み込む関数は 5 か所に同じものがコピーされていて、基盤にあたる層には 12 本の道具がぶら下がっている。つまり「日付 1 軸で持つ」という判断は、どこか 1 か所の設計ではなく、私の道具のかなりの部分がその上に載っている状態だった。以下は、一般にそう言われているという話ではなく、その自分の表を作り直してみて出てきたものだ。

作り直した表は、いまのところ 1,681 行、45 種類のルールが入っている。更新は無人の手順で回していて、履歴は 11 回ぶんある(うち 2 回は、わざと壊した値を流して本番の表が書き換わらないことを見るための失敗)。その作業のあいだに、日付 1 軸では表せないものが 4 つ出てきた。

**引く日付がルールごとに違う。** 3 月に支払う給与を 1 件計算するとき、社会保険の料率は対象になる月の初日で引き、雇用保険の料率は賃金の締切日で引く。締切が前月末なら、この 2 つは年度の境目をまたいで別の側に落ちる。表のほうに「この行はどの日付で引くか」が書いていないと、呼ぶ側が日付を 1 つ選んで両方に渡すことになる。片方は必ず年度を間違える。しかも間違えたことは分からない。どちらの年度にも値はあるので、例外は出ず、数字だけが変わる。

**数式そのものが改正される。** 値の履歴を持っていても、計算の仕方が変わった改正は表せない。免除の条件が月末在籍だけだったものに日数の条件が足された、というような改正は、値をいくら並べても出てこない。

**公表日と施行日がずれ、遡って適用される。** 新年度の料率が 2 月に公表され、3 月分から適用される表がある。2 月の上旬にその表を引くと、まだ公表されていないはずの値が返る。あとから「あの時点ではどう計算していたか」を再現しようとしても、日付 1 軸の表には引く時点を受け取る口が無いので、いまの知識で過去を塗り直した答えしか出ない。

**経過措置が対象を限定する。** 本則が改定されても、ある生年月日帯の人だけ旧い値が続く、という改正がある。日付 1 軸だと同じ適用開始日に行が 2 つ並ぶので、どちらが採られるかは表の並び順で決まる。どちらを採っても、片方の帯は必ず間違う。

この 4 つは、どれも「入力が壊れている」話ではない。入力は正しく、表にも値はあり、引き当ての手続きだけが足りていない。だから静かに間違う。

### 足すのは列で、経路ではない

直し方は、引く側に場合分けを足すことではない。場合分けを足すと、表を差し替えたときに壊れるのは引く側のコードになる。足すのは行の側の列だ。

| 足す列 | 行が宣言すること |
|---|---|
| `basis` | この行はどの日付で引くか(対象月の初日 / 賃金の締切日 / 請求日 …)。名前は呼ぶ側の表が決める |
| `known_from` / `known_to` | いつ公表された知識か。引く時点を渡せば、当時の知識のまま引ける |
| `priority` | 0 が本則、10 が経過措置、20 が特例。どちらが勝つかを明示する |
| `sel_` で始まる任意の列 | 対象セグメント。空欄はワイルドカードなので、次元を後から足しても既存の行は直さなくていい |

そして引き当ての側では、決まらないときに値を返さない。これがこの部品でいちばん大事なところだと考えている。日付 1 軸の引き方には、そもそも「決まらない」という返り値が無い。その日以前でいちばん新しい行を採るという規則は、いつでも何かを返してしまう。

## 図 1 日付 1 軸で壊れる 4 点と、それを潰す列

![4 点それぞれに、行の側へ足す列と、この部品での実装の状態を並べた表](figures/asof_table_axes.png)

行が 4 点、左の列が行の側に足す列、右の列がこの部品での状態だ。藍で塗った 2 行が実装して測ったところ、橙の 1 行が次回に回したところ、無彩色の 1 行が構造だけ入れて中身が仮置きのところになる。ここを 3 色に分けたのは、4 点すべてを潰したと書けないからだ。数式の改正は、行の形としては値の代わりに数式の名前を置けるようにしてあるが、その数式を評価する仕組みはこの部品に入っていない。公表時点のほうは、引く仕組みは入ったが、私の表では実際の公表日が分かっている行が一部しかなく、残りは適用開始日で仮置きしてある。

## 手順

表は 1 枚の行の表で、CSV でも JSON でもいい。1 行が 1 つの条項の適用単位になる。

| 列 | 意味 |
|---|---|
| `key` | 何を求めるか。同じ `key` の行は同じ `basis` を持つ(揺れたら表の不備として止まる) |
| `basis` | どの日付で有効期間を引くかの名前 |
| `valid_from` / `valid_to` | 有効期間。半開区間で、終わりの日は含まない。`valid_to` が空なら開いたまま |
| `known_from` / `known_to` | 知識の期間。公表側の時間 |
| `known_quality` | 公表日が実値か仮置きか |
| `priority` | 0 / 10 / 20 |
| `value` | 値。文字列のまま返す |
| `source` | 出典。返り値に必ず付く |
| `sel_` で始まる列 | 対象の次元。列名は呼ぶ側が決める |

引く手続きは固定で、順番を変えられない。`key` の行を集めて `basis` を読み、`case` からその日付を取り、知識の期間で絞り、有効期間で絞り、対象で絞り、残った中でいちばん高い `priority` の 1 行を返す。

```
python asof_table.py resolve 表.csv --key 保険料率_甲 --case 対象月初日=2025-06-01 --case sel_地域=地域A
python asof_table.py validate 表.csv
```

引けたときは、値だけでなく使った行の出典と有効開始日と行番号が返る。

```
{"ok": true, "key": "保険料率_甲", "basis": "対象月初日", "value": "9.60",
 "source": "合成の料率表 2025 年度版(架空)", "valid_from": "2025-03-01",
 "priority": 0, "priority_name": "本則", "row": 13}
```

引く時点を渡すと、同じ `key`・同じ対象月のまま、当たる行が変わる。次の 2 つは対象月がどちらも同じで、違うのは引く時点だけだ。合成の表では新年度の料率の公表を 2 月 10 日に置いてある。

```
$ python asof_table.py resolve 表.csv --key 保険料率_甲 --case 対象月初日=2026-03-01 --case sel_地域=地域A --as-of 2026-02-05
{"ok": false, "key": "保険料率_甲", "basis": "対象月初日", "reason": "as_of 時点で未公表",
 "detail": "行 25 は 2026-02-05 の時点で未公表", "rows": [25]}

$ python asof_table.py resolve 表.csv --key 保険料率_甲 --case 対象月初日=2026-03-01 --case sel_地域=地域A --as-of 2026-02-20
{"ok": true, ..., "value": "9.70", "valid_from": "2026-03-01", "row": 25}
```

上が公表前、下が公表後だ。公表前は値を返さない。ここで直近の値を返してしまうと、当時の計算を再現しているつもりで、いまの知識を過去に混ぜたものが出てくる。

決まらないときに返る理由コードは 5 つだけで、これ以上増やしていない。

| 理由コード | 何が足りないか |
|---|---|
| 基準日が case に無い | どの日付で引くかは行が宣言している。その名前の日付が渡されていない |
| as_of 時点で未公表 | 有効期間では当たる行があるが、引く時点ではまだ公表されていない |
| 収録範囲の外 | `key` が表に無いか、基準日がどの期間にも入らない(前後の外か、期間の穴) |
| 同順位で複数該当 | 同じ順位の行が 2 本以上当たった。どちらを採るかは表の外の判断になる |
| 公表日が仮置き | 当たるはずの行の公表日が仮置きなので、引く時点で公表済みだったかが表から決まらない |

最後の 1 つは、自分の表の弱いところをそのまま理由コードにしたものだ。公表日を適用開始日で埋めてある行は、引く時点を渡した引き当てで黙って「未公表」と答えてしまう。実際には公表されていたかもしれない。分からないものを分からないと言わせるために、仮置きの行は別の理由で止める。

対象の指定が細かい行を自動で優先することもしていない。ワイルドカードの行と具体的な行が同じ順位で当たれば、そこは止まる。優先したいなら順位の列に書く、という形にした。自動で優先する規則を入れると、表を書いた人が意図していない行が静かに勝つ経路ができる。

表そのものの検査は別にある。同じ `key` と対象と順位で有効期間が重なっている行、始まりが終わりより後ろの行、期間の穴、同じ `key` なのに基準日の名前が揺れている行、登録していない順位。見つけても直さない。一覧にして返すだけだ。

```python
from asof_table import Table, resolve, validate

table = Table.load("表.csv")
for f in validate(table):
    print(f.kind, f.key, f.rows, f.detail)

r = resolve(table, "保険料率_甲", {"対象月初日": "2026-03-01", "sel_地域": "地域A"})
print(r.value, r.source, r.valid_from, r.row) if r.ok else print(r.reason, r.detail)
```

`resolve` の引数は表・`key`・`case`・引く時点の 4 つだけで、「見つからなかったらこれを返す」に相当する引数は無い。これはテストでも固定してある。

## 検証

テストは 73 件。fixture は合成データで、地域名も料率も出典名も架空だ。実在の料率や最低賃金は 1 つも入れていない。

```
$ python -m pytest tools/asof_table -q
.....................................................................
73 passed in 0.77s
```

測定は 2 つある。どちらも決定論で、乱数を使っていない。

1 つめは引き当ての比較だ。合成した 44 行の表に対し、30 か月ぶんの給与を 12 の地域と 2 つの生年月日帯で作り、3 つのルールを引く。合わせて 2,160 件になる。同じ引き当てを、適用開始日 1 軸の引き方(`key` と 1 つの日付だけで、その日以前の最新の行を採る)と、この部品の両方に流して答えを比べた。

```
[measure] 引き当て 2160 件 / 答えが違った 252 件 (基準日 72 / 経過措置 180 / 残差 0)
[measure] うち 適用開始日 1 軸が黙って別の値を返した 228 件、値を返したが正しくは決まらない 24 件
[measure] この部品が理由コードで止めた 144 件(値を返した誤りは 0 件)
```

比べる相手を弱く作らないよう、対象の次元のうち古い形でも `key` 側に畳めていたもの(地域)は、1 軸の側にも渡している。そのうえで残った差が 252 件で、内訳は基準日の違いが 72 件、経過措置が 180 件だった。残差は 0 件になっているが、これは合成の作り方でそうなっているだけで、内訳が合うこと自体は何かの裏付けにはならない。ここで固定しているのは、日付 1 軸の引き方が黙って別の行を返す経路が実際に動くことと、同じ入力でこの部品は値ではなく理由コードを返すことの 2 つだ。

差の中身も 2 種類に分かれる。228 件は、どちらも値を返したが中身が違った。24 件は、1 軸の側が値を返し、この部品は「収録範囲の外」で止めた。後者のほうが危ないと考えている。表に収録されていない期間の引き当てに、いちばん近い行の値が付いて返ってくるからだ。

2 つめは引く時点だけを動かす測定だ。対象月を 3 月 1 日に固定し、引く時点を新年度の料率の公表前と公表後に置いて、12 の地域ぶん引く。

```
[measure] 引く時点だけを動かす 24 件: 適用開始日 1 軸は as_of を受け取る口が無く 12 通りのまま、
          この部品は公表前の 12 件を『as_of 時点で未公表』で止め、公表後の 12 件だけ値を返した
```

1 軸の側は、引く時点を渡す場所が無いので 24 件とも同じ値を返す。この部品は、公表前の 12 件を止め、公表後の 12 件だけ値を返した。遡りの再現が構造として動いているかどうかは、この差が出るかどうかで見ている。

残りのテストは、5 つの理由コードが全部通る道があること、順位の列で経過措置が本則に勝ち期限で切れること、対象の次元を後から 1 つ足しても既存の行が無修正で動くこと、施行日が政令待ちの行が引き当てにも重なりの検査にも決して現れないこと、検査が壊れた表の 9 行から 6 種類の不備を全部拾って 1 行も直さないこと、終了コードが引けたら 0・理由コードで止まったら 3・表や引数が壊れていたら 2 になること、を見ている。合成 fixture が生成器から決定論的に出ることも、ディスク上の CSV と突き合わせて確かめてある。

段は 6 つで、橙のピルが関所だ。この図で見てほしいのは、描かれている経路よりも、描かれていない経路のほうになる。どの段から出ても行き先は理由コードで、「当たらなかったので直近の行を返す」に戻る矢印がどこにも無い。実装のほうでも同じで、引き当ての関数に受け皿の引数を持たせていない。落ちる先が無ければ、落ちる経路も書けない。

## 道具

[asof_table](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/asof_table) に置いた。`asof_table.py` 1 ファイルと、テスト、合成 fixture の生成スクリプトが入っている。依存は無く、標準ライブラリだけで動く。ライセンスは MIT。

使い方は上の手順のとおり。関数として呼ぶなら `Table.load(path)` / `resolve(table, key, case, as_of)` / `validate(table)`、コマンドラインなら `resolve` と `validate` の 2 つ。比較用の `naive_lookup`(適用開始日 1 軸の引き方)も入れてあるので、自分の表で同じ比較ができる。自分の現場に合わせるときに触るのは表のほうで、`basis` の名前と `sel_` の次元名を差し替える。部品のコードは触らない。

## 別の業種なら

この部品は、給与や社会保険の語彙をひとつも持っていない。持っているのは行の形と、絞る順番と、止まる理由だけだ。会計の税率や勘定科目の改定、EC の送料表や手数料の改定、医療や介護の点数改定、建設の単価表でも、表が「適用開始日つきの履歴」で持たれ、公表と施行がずれ、経過措置が対象を限定する形は同じだと考えている。私が実測したのは給与まわりの表と、上の合成データだけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。変わるのは `basis` の名前(対象月の初日 / 締切日 / 受注日 / 診療日 / 着工日)と `sel_` の次元名だけで、部品そのものは書き換えずに持ち出せる。送料表なら `basis` を受注日、`sel_` を地域と重量帯にする。単価表なら着工日と工種になる。部品の側からは、料率も送料も単価も同じことになる。

## できないこと

- 数式を評価しない。値は文字列のまま返す。型変換も端数処理もしない。数式の改正を表せる形にはなっているが、その数式を計算する部分は入っていない
- 公表日が仮置きの行は、引く時点を渡した引き当てで止まる。仮置きを実値に直すのは表を作る側の作業で、この部品は直せない。私の表でも、実際の公表日が分かっている行は一部だけだ
- 収録されていない期間は引けない。表の外の日付に対して直近の行を返すことは決してしないので、収録範囲を広げるまでその期間の計算はできない
- 対象の指定が細かい行を自動で優先しない。優先を順位の列に書き忘れると止まる。止まるほうを選んだが、書き忘れが多い表では手間が増える
- 3 次元以上の表は、対象の次元に分解するか値の側に持つことになる。行の形そのものは 1 段しかない
- 表の意味は検査しない。検査が見るのは期間と順位と基準日の名前の形だけで、値が正しいかは見ない
- 上の数字は合成データと私の環境での測定で、他の人の表で同じ内訳になるとは限らない。特に 252 件という差は合成の作り方で決まる値だ
- 4 点に分けたのは、私が自分の表を作り直したときに出てきた分け方であって、これで全部という話ではない。別の分野の表を載せれば 5 つめが出ると考えている
