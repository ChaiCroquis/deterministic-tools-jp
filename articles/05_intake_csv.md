取込側のソフトが要求する形で CSV を書き出すとき、書く処理は数行で終わる。列を並べて、cp932 で開いて、書く。私の記録では、取込用の CSV を書き出しているコードが 2 か所あって、どちらもそうなっていた。だが CSV の書き出しは、書いた瞬間には気づけない壊れ方をする。値の中のカンマで列がずれ、cp932 に無い文字が置換文字に化け、cp932 に書けるのに読み戻すと別の字になる文字がある。この記事では、書き出しを「書いて終わり」にせず、出力ファイルを取込側と同じ読み方で読み戻し、元データから数えた件数・合計・全セルと突き合わせて、合わなければ出力を渡さない部品を 1 か所にまとめる。

**なぜ重要か**: 読み込み側には、私たちは検査を置いてきた。文字コードを推測せずに順番に試す部品も、和暦を改元表で照合する部品も、名前を寄せて決まらない行を人に返す部品も、入口に関所を置くという同じ形をしている。ところが出口には何も置いていなかった。書き出しは「自分が作ったデータを、自分が決めた形で書くだけ」に見えるからだ。しかしその形は取込側が決めていて、こちらの都合では変えられない。cp932 でなければならない、クォートを付けてはいけない、列の順は固定、という条件は全部あちら側の制約で、こちら側のデータがその制約に収まる保証はどこにも無い。収まらなかったとき、書き出しの処理は例外を出さない。置換文字を書き、クォートを足し、そのまま正常終了する。壊れていることが分かるのは取込の後だ。

**要点**:
- 書いたら読み戻す。取込側と同じ読み方で読み直して、元データから数えた件数・合計・全セルと突き合わせる
- 仕様と両立しない値はクォートで逃がさず、理由コードを付けて人に返す。判断待ちが 1 件でもあれば出力ファイルを作らない
- cp932 に無い文字は思っているものと違う。髙 も 﨑 も ① も ㈱ も書ける。書けないのは絵文字や欧文記号のほうだ
- cp932 に書けても読み戻すと別の字になる文字がある。書いて読む往復をしないと、この種類は見つからない

**数字で見る**: 合成した 1,000 行を、検査も読み戻しもせずに書き出すと 1,000 行とも書けてしまうが、取込側と同じ読み方で読み戻すと 1,007 行になり、元データと一致した行は 50 行だけで、支給合計は 5,707,000 円ぶん少なく読めた。この部品は同じデータで 50 行を判断待ちとして返し、出力ファイルを 1 つも作らなかった。

## 何を解決するのか

取込用の CSV には、こちらに選択の余地が無い。文字コードは cp932、行末は CRLF、クォートは付けない、列の順と見出しは固定、コードの先頭ゼロは落とさない。取込側の仕様書にそう書いてあるので、そのとおりに書く。書く処理そのものは短い。

短いので、検査を置く場所が無いように見える。実際、私が書いてきた 2 か所も、列を並べて開いて書くだけだった。問題は、その短い処理が黙って壊れる形を 4 つ持っていることだ。

1 つめは列のずれだ。値の中にカンマが入っていると、クォート無しの出力では列が 1 つ増える。標準のライブラリに任せると、こういう値は自動でクォートに包まれる。包まれた時点で取込側の要求と食い違うが、書いた側には何も起きない。

2 つめは文字化けだ。cp932 で表せない文字が入っていると、`errors="replace"` を付けている実装ではその字が置換文字になる。付けていなければ例外になるが、付いている実装は珍しくない。止まらないほうが運用が楽に見えるからだ。

3 つめは先頭ゼロの脱落で、これは書き出しそのものより、途中で表計算を経由したときに起きる。コードの列が数値として解釈され、`000042` が `42` になる。

4 つめが、この記事を書こうと思った理由になったものだ。cp932 に書けるのに、読み戻すと別の字になる文字がある。波ダッシュ(U+301C)を cp932 に変換すると 0x8160 になり、その 0x8160 を読み戻すと全角チルダ(U+FF5E)になる。cp932 側の 1 つの符号に Unicode 側の 2 つの字が当たっているので、往復しても元に戻らない。負符号(U+2212)と全角ハイフンマイナス(U+FF0D)も同じ関係にある。書き出しは成功し、例外も警告も出ない。値だけが静かに変わる。

この 4 つに共通しているのは、出力ファイルを見ても分からないことではない。見れば分かる。ただ、書き出した直後に誰も見ないというだけだ。1,000 行の CSV を目で確かめる人はいないし、確かめられる形でもない。

そこで順番を変える。書いて終わりにせず、書いたファイルを取込側と同じ読み方で読み直し、元データから数えた件数・合計・全セルと突き合わせる。合わなければ渡さない。読み戻しは推測を 1 つも含まない操作なので、機械に任せられる。

もう 1 つ決めたのは、取込側の要求と両立しない値を、書き出しの側で勝手に辻褄合わせしないことだ。値の中にカンマがあるとき、クォートで逃がせば出力は作れるが、取込側は素の CSV を期待しているので読めない。読める形にするには値からカンマを取るしかなく、それは値を変えることだ。どちらも機械が決めてよい話ではない。だから判断待ちとして返す。

左の列が検査も読み戻しもしない書き出し、右の列がこの部品だ。上の 2 行は、取込側の要求どおりに書けるものを書けている状態を指す。先頭ゼロも半角カナも、列仕様に従って書けば通る。下の 6 行は、書けないか、書けても値が変わるものだ。左はどれも「書けたように見える」で終わり、右は理由コードを付けて人に返すか、書かないで列名を返す。左右の違いは丁寧さではなく、壊れたことが取込の前に分かるか後に分かるかだ。

## 手順

最初に決めるのは列仕様で、これが出力の正本になる。列の順・見出し・型・桁・ゼロ埋め・空を許すか・合計を突き合わせるかを 1 つの表に持つ。表は CSV で持たせた。取込仕様が変わったら、この CSV を差し替えるだけにしたいからだ。

| 見出し | 型 | 桁 | ゼロ埋め | 空を許す | 合計 |
|---|---|---|---|---|---|
| 社員番号 | コード | 6 | ○ | | |
| 氏名 | 文字列 | 40 | | | |
| 部署 | 文字列 | 20 | | ○ | |
| 支給合計 | 金額 | 10 | | | ○ |
| 控除合計 | 金額 | 10 | | | ○ |
| 差引支給額 | 金額 | 10 | | | ○ |

この表に無い列は書かない。元データに「備考」のような列があっても出力には出さず、落とした列名だけを返す。逆に表にある列が元データに無ければ止まる。空欄で埋めない。空欄は取込側では別の意味になるので、埋めた時点でこちらが値を作ってしまう。

次が値の検査だ。理由コードは 8 つで、どれも「機械では書けない理由」の名前にしてある。

| 理由コード | 意味 |
|---|---|
| 必要な値が空 | 空を許さない列が空。空欄で埋めると取込側では別の意味になる |
| 数字でない | 整数・金額・コードの列に符号と数字以外が入っている(全角数字、桁区切りのカンマ、U+2010 のハイフンを含む) |
| 桁あふれ | 列仕様の桁を超えている。切り詰めると別の値になる |
| 改行が値の中にある | 1 行 1 レコードの形と両立しない |
| 引用符が値の中にある | クォート無しの要求と両立しない |
| 区切り文字が値の中にある | クォート無しで書くと列がずれる。クォートで逃がすと取込側が読めない |
| cp932 に無い文字 | cp932 で表せない。置換文字で書き進めると元の字が失われる |
| 書いて読むと別の文字になる | cp932 に書けるが、読み戻すと別の符号位置の字になる |

最後の 2 つは、1 文字ずつ cp932 に変換して戻すだけで分かる。判定に辞書は要らない。

```python
def _bad_char(s):
    """cp932 で書けない字、または書けても読み戻すと別の字になる字を 1 つ返す。"""
    for ch in s:
        try:
            back = ch.encode("cp932").decode("cp932")
        except UnicodeEncodeError:
            return "cp932 に無い文字", ch
        if back != ch:
            return "書いて読むと別の文字になる", ch
    return "", ""
```

ここで、cp932 に無い文字について思い込みを 1 つ捨てることになった。外字で困る字として名前が挙がる 髙(U+9AD9)や 﨑(U+FA11)は、cp932 にある。㈱(U+3231)も ①(U+2460)も半角カナもある。NEC と IBM の拡張が入っているからだ。実際に書けないのは、絵文字、サロゲートペアの漢字、½ や € や ✓ のような欧文記号で、どれも人が別のところから貼ってきた文字だった。名前の字より、貼られた記号のほうが落ちる。

値がすべて通ったら書く。書き先はいきなり出力先ではなく、作業ファイルにする。

```python
def _write_lines(path, spec, lines):
    with open(path, "w", encoding="cp932", errors="strict", newline="") as f:
        w = csv.writer(f, delimiter=",", quoting=csv.QUOTE_NONE, quotechar=None,
                       escapechar=None, lineterminator="\r\n")
        w.writerow(spec.names)
        w.writerows(lines)
```

`errors="strict"` は検査の二重化だ。検査を通った値しか来ないはずだが、来てしまったら例外で止まる。置換文字で書き進める道を残さない。`QUOTE_NONE` も同じで、逃がすべき値が来たら例外になる。

そして読み戻す。ここが要になる。読むときに、自分が書いたときの知識を一切使わない。取込側と同じように、cp932 で読み、CRLF で行に切り、カンマで列に切るだけにする。クォートは解釈しない。

```python
def read_back(path):
    text = Path(path).read_bytes().decode("cp932")   # errors 指定なし = 読めなければ例外
    if not text.endswith("\r\n"):
        raise ValueError("行末が CRLF で終わっていない")
    return [line.split(",") for line in text.split("\r\n")[:-1]]
```

突き合わせるのは、見出しの並び、件数、合計を取る列の合計、そして全セルの文字列だ。合計だけでも件数だけでも足りない。列が 1 つずれると合計は変わるが、値が別の字に化けただけでは合計は変わらない。逆に全セル比較だけしていると、行が増えたことを行単位のずれとして受け取ってしまう。3 つとも見るのは、壊れ方が 3 種類あるからだ。

差が 1 つでもあれば作業ファイルを消して、差の一覧を返す。行番号・列名・元の値・読み戻した値の 4 つを並べるだけで、どちらが正しいかは書かない。原因も推定しない。通ったときだけ、作業ファイルを本来の名前に付け替える。判断待ちが残っているあいだ、取込側に渡るファイルは存在しない。

コマンドラインからも使える。判断待ちがあれば終了コード 3 になるので、バッチの中に置いて止められる。

```
python intake_csv.py 元データ.csv 出力先.csv --spec 列仕様.csv
python intake_csv.py 元データ.csv --spec 列仕様.csv --check     # 検査だけ、書かない
```

計測のテストも同じファイルにある。固定した乱数の種で支給控除一覧を 1,000 行合成し、1 行につき 1 か所だけ問題を仕込む。仕込みは、値の中のカンマ 12 行、cp932 に無い文字 8 行、値の中の改行 7 行、波ダッシュ 6 行、数字でない 6 行、引用符 5 行、桁あふれ 4 行、空の氏名 2 行で、合わせて 50 行。残りの 950 行はそのまま書ける。

```
[measure] naive write: 1000 rows out, read back 1007 lines, diffs 5590, rows dragged in 950,
          totals off {'支給合計': Decimal('-5707000'), '控除合計': Decimal('-1331900'),
                      '差引支給額': Decimal('-6528200')}
[measure] this tool: pending 50 rows, files written 0
[measure] this tool, 50 pending rows removed: wrote 950 rows, read back 950 rows, diffs 0,
          totals {'支給合計': '314404600', '控除合計': '52586100', '差引支給額': '261818500'}
```

1 行目が、検査も読み戻しもしない書き出しだ。1,000 行とも書けて、例外は 1 つも出ない。ところが取込側と同じ読み方で読み戻すと 1,007 行ある。値の中の改行が 7 行ぶん、1 レコードを 2 行に割ったからだ。そして元データと一致した行は 50 行しかない。

この 50 行という数が、この記事でいちばん書きたかったところだ。仕込んだ問題は 50 行ぶんで、残り 950 行には何も仕込んでいない。それでも一致したのは 50 行だけだった。理由は、最初に改行が入った行から後ろは、記録がまるごと 1 行ずつずれるからだ。ずれた先で比べているので、何も問題の無い行まで違う値として出てくる。壊れているのは 50 行だと思って直しにいくと、実際に取込側が読んでいるのは 950 行ぶん別の内容だ、ということになる。金額の合計も、支給合計で 5,707,000 円、控除合計で 1,331,900 円、差引支給額で 6,528,200 円ぶん、読み戻した側が少なくなる。

2 行目がこの部品で、同じ 1,000 行に対して 50 行を判断待ちとして返し、出力ファイルを 1 つも作らなかった。作業ファイルも残っていない。検査で止まっているので、書く処理まで進んでいない。

3 行目は、判断待ちの 50 行を外した 950 行を書いたものだ。950 行が書けて、読み戻しても 950 行で、差は 0 件だった。合計も一致している。ここで言えるのは「950 行は取込側と同じ読み方で読み直しても元データと同じだった」ということまでで、取込側のソフトが実際にどう解釈するかは別の話だ。

なお、5,590 という差の件数や 50 行という一致件数は、合成の仕方(どの種類を何行仕込むか、改行の行が何行目に来るか)で変わる値で、実際のデータでこの割合になるという意味ではない。比べているのは割合ではなく、「壊れたことが取込の前に分かるか、後に分かるか」という性質の違いだと考えている。

## 図 2 書き出しの流れ

![取込用 CSV の書き出しの流れ — 書いたら読み戻して、元データと突き合わせてから渡す](figures/intake_csv_flow.png)

段は 5 つ。列仕様と突き合わせる、値を検査する、作業ファイルに書く、読み戻す、渡す。橙のピルが関所で、前半では判断待ちの行が出た時点で出力ファイルを作らず、後半では突合に差が出た時点で作業ファイルを消す。書く段が真ん中にあって、その後ろにもう 1 つ関所があるところがこの図の要点になる。書いた後にしか分からない壊れ方があるので、書く処理を最後の工程にしない。

## 道具

[intake_csv](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/intake_csv) に置いた。`intake_csv.py` 1 ファイルと、テスト、合成 fixture の生成スクリプトが入っている。依存は無く、標準ライブラリだけで動く。ライセンスは MIT。

使い方は上の手順のとおり。関数として呼ぶなら `Spec.from_csv(path)` / `check_rows(spec, rows)` / `write(path, spec, rows)` / `read_back(path)` / `verify(path, spec, lines)`、コマンドラインなら `--check` で検査だけ、CSV を 2 つ渡して書き出し。列仕様を自分の取込仕様に合わせたいときは `fixtures/retsu_shiyou.csv` を差し替える。部品のコードは触らない。fixture を作り直したいときは `python fixtures/make_fixtures.py`。

## 別の業種なら

この部品は、給与や社会保険の語彙を 1 つも持っていない。持っているのは列仕様の表と、値の検査と、読み戻しの突合だけだ。会計ソフトの仕訳取込 CSV、EC モールの商品・在庫の一括登録 CSV、勤怠システムの打刻取込でも、取込側が文字コードと列の順を固定で要求し、値の中のカンマで列がずれる形は同じだと考えている。私が実測したのは給与まわりの支給控除一覧と、上の合成データだけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。変わるのは列仕様の CSV だけで、部品そのものは書き換えずに持ち出せる。たとえば仕訳の取込なら「日付,借方科目,借方金額,貸方科目,貸方金額,摘要」を列仕様の表にして、借方金額と貸方金額に合計の印を付ける。摘要は人が入力する欄なので、カンマと改行が入る確率が高い列になる。そこが判断待ちに出てくるのは、部品の側では給与も仕訳も同じことだ。

## できないこと

- 取込側のソフトが実際にどう解釈するかは確かめていない。読み戻しは「取込側と同じ読み方」をこちらが決めて読んでいるだけで、相手の実装を見たわけではない。仕様書の記述と食い違っていれば、この突合は通っても取込は落ちる
- 桁は文字数で数える。取込側がバイト数で桁を決めている仕様には合わない。列仕様にその区別を持たせていないので、足すなら表の側を変えることになる
- 文字コードと行末と区切り文字は cp932 / CRLF / カンマで固定した。TSV や UTF-8 の取込仕様には使えない。設定にしなかったのは、揺らすと読み戻しが「自分の書き方をもう一度なぞるだけ」になるからだ
- 差の原因は推定しない。元データと読み戻しのどちらが正しいかも決めない。判断待ちの行を自動で直す機能も無い。直し方が業務の判断になる
- 数値は文字列のまま出す。丸めも桁揃えもしないので、丸めが要る取込仕様なら渡す前に人が決める
- 読み戻しは自分が書き終えた直後のファイルを読む。渡した後にファイルが差し替わったり、転送で壊れたりすることは見ていない
- 上の数字は合成データと私の環境での実測で、他の人の環境で同じになるとは限らない。特に 5,590 と 50 と 1,007 は、合成の仕方で変わる
