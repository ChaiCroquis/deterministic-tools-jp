前回、毎年変わる数表を行で持つ部品を作ったとき、1 つだけ次回に回したところがある。数式そのものが改正される回だ。値をいくら履歴で並べても、計算の仕方が変わった改正は表せない。この記事では数式を文字列の列として行に持ち、有効期間と公表時点を値の行と同じ形で付ける。そのうえで、この部品でいちばん強く決めたのは別のところにある。**丸め方を式の隣の列に書かせ、書いていない式は評価せずに止める**ことだ。

**なぜ重要か**: 規定の側は、項目ごとに別の丸め方を定めている。保険料の被保険者負担は端数 50 銭までを切り捨てて 50 銭を超えたら切り上げ、雇用の給付日額は 1 円未満を切り捨て、年金額は円未満を四捨五入する。一方で、計算を書く実行環境の既定の丸めは、いま何の項目を計算しているかを知らない。Python の組み込みの丸めは端数ちょうど半分のとき整数部が偶数になる側へ寄せるし、`Decimal` の既定も同じで、整数に落とすだけなら切り捨てになる。つまり丸めの指定を省いた瞬間、規定とは別の答えが、例外も警告も出さずに返る。値がずれるのは 1 円だが、それが保険料や給付額として人に渡る。だから丸めは「書き忘れたら既定で動く」ものにしてはいけない。

**要点**:
- 数式は文字列の列として行に持つ。式の版は値の版と同じ引き方(公表時点 → 有効期間 → 順位)で 1 行に決まる
- 丸めの名前は式の隣の列に書かせる。空欄の行は評価せずに理由コードで止める。部品は既定の丸めを持たない
- 評価は文字列をそのまま実行せず、構文を絞った木をたどる。属性アクセス・添字・内包表記・lambda は構文の段で拒否する
- 数は `Decimal` だけで扱い、float が混ざった時点で止める。返り値には使った式の版と値の行の出典を全部付ける

**数字で見る**: 合成した金額 120 件のうち 107 件に端数が出た。同じ金額に対して、表で丸めを明示指定した値と、実行環境の既定に任せた値を突き合わせると、被保険者負担の丸めでは組み込みの丸めと 8 件、切り捨てと 46 件が食い違い、給付日額の丸めでは組み込みの丸めと 54 件、年金額の丸めでは組み込みの丸めと 10 件、切り捨てと 64 件が食い違った。

## 何を解決するのか

まず、これが私の手元で起きている形だという前提のほうから書く。

私は社会保険や雇用保険の公的なパラメータを、行の表 1 枚で引ける形に作り直している。いまのところ 1,681 行、45 種類のルールが入っていて、そこに計算式が 14 式ぶら下がっている。作り直しの動機は前回書いたとおりで、日付 1 軸では表せないものが 4 つあったからだ。そのうち 3 つは前回の部品で潰したが、残る 1 つ「数式そのものの改正」は、値の行の形としては置けるようにしただけで、評価する仕組みは作っていなかった。この記事はその続きにあたる。

作り直しの途中で気づいたのは、数式を data にすると、数式と対になっているもう 1 つの情報が表に出てくる、ということだった。丸め方だ。

私の表では、丸めは値ではなく計算式の側の属性として記録してある。保険料の端数処理は、出典欄に「厚労省通達」と書かれた行があり、備考に「被保険者負担分 50 銭ルール」と残してある。雇用の給付日額は、厚労省が公表している計算式の PDF から取った行で、帯ごとの計算式と一緒に「区分計算 + 1 円未満切捨て」と記録してある。年金額の端数処理は、出典欄が「国年法 / 厚年法」で、備考が「円未満四捨五入 等」になっている。この「等」がくせもので、項目ごとにさらに分かれることを示している。

つまり規定の側は、項目ごとに丸め方を分けて定めていて、それが私の表の行にも出典つきで残っている。ところが計算するほうの実行環境は、この区別を持っていない。

### 既定の丸めは項目を知らない

たとえば合成の報酬月額 110,000 円に合成の料率 8.13% を当てて折半すると、端数が付いて 4,471.50 になる。ここで何が起きるか。

表で「50 銭以下切捨て」と指定すれば 4,471 になる。表で「円未満四捨五入」と指定すれば 4,472 になる。どちらも規定のどこかに実在する丸め方で、どちらを使うかは項目が決める。ところが丸めを書かずに実行環境の既定に任せると、組み込みの丸めは 4,472 を返し、`Decimal` の既定も 4,472 を返し、整数に落とすだけなら 4,471 を返す。この 3 つは、どの項目を計算しているかを一切見ていない。

もっと悪いのは、既定の丸めの向きが金額によって変わることだ。端数ちょうど半分のとき、組み込みの丸めは整数部が偶数になる側へ寄せる。4,471.50 は 4,472 へ上がるが、4,472.50 は 4,472 のまま下がる。規定の「円未満四捨五入」なら 4,472.50 は 4,473 だ。つまり既定に任せると、同じ項目の中でも 1 円上がる行と上がらない行が混ざる。合計が合わないという形ではなく、個々の値が静かに別の値になる。

だからこの部品では、丸めの名前が書かれていない式は評価しない。既定を持っていれば書き忘れは既定で動いてしまうので、既定そのものを持たないことにした。`evaluate` には丸めを渡す引数も、見つからないときの逃げ道の引数も無い。これはテストで固定してある。

## 手順

式の表は 1 枚の行の表で、CSV でも JSON でもいい。1 行が 1 つの式の 1 つの版になる。

| 列 | 意味 |
|---|---|
| `id` | 何を計算するか |
| `expr` | 式の文字列 |
| `inputs` | 名前ごとの入力元。`名前=種類:参照先` を並べる。種類は `case` / `value` / `formula` |
| `rounding` | 丸めの名前。**空欄は許さない** |
| `valid_from` / `valid_to` | 有効期間。半開区間で、終わりの日は含まない |
| `known_from` / `known_to` | 知識の期間。公表側の時間 |
| `priority` | 0 が本則、10 が経過措置、20 が特例 |
| `source` | 出典。返り値に必ず付く |

値の表のほうは `key` と `value` を持ち、期間と順位の列は式の表とそろえてある。**式の版も値の版も同じ引き方で 1 行に決まる**ので、数式の改正と値の改定を同じ形で書ける。

```
python formula_table.py eval 式.csv --values 値.csv --id 折半額 --input 報酬月額=300000 --on 2025-06-01
python formula_table.py validate 式.csv
```

評価できたときは、値だけでなく、丸める前の値、使った丸めの名前、そして使った式の版と値の行の出典が全部返る。

```
{"ok": true, "id": "折半額", "value": "15030", "raw": "15030.00", "rounding": "50銭以下切捨て",
 "used": [{"kind": "式", "name": "折半額", "row": 1, "valid_from": "2024-03-01",
           "source": "合成の端数処理メモ 2024(架空)"},
          {"kind": "値", "name": "合成料率_甲", "row": 2, "valid_from": "2025-03-01",
           "source": "合成の料率表 2025 年度版(架空)"}]}
```

同じ `id`・同じ入力のまま、引く日付だけを改正の前後に置くと、当たる式の行が変わる。合成の表では、改正で式に加算率の項が 1 つ増える形にしてある。

```
$ python formula_table.py eval 式.csv --values 値.csv --id 折半額 --input 報酬月額=300000 --on 2026-03-01
{"ok": true, "value": "15525", "used": [{"kind": "式", "row": 1, ...},
                                        {"kind": "値", "name": "合成料率_甲", "row": 3, ...}]}

$ python formula_table.py eval 式.csv --values 値.csv --id 折半額 --input 報酬月額=300000 --on 2026-04-01
{"ok": true, "value": "15975", "used": [{"kind": "式", "row": 2, ...},
                                        {"kind": "値", "name": "合成料率_甲", "row": 3, ...},
                                        {"kind": "値", "name": "合成加算率", "row": 4, ...}]}
```

使われた式の行番号が 1 から 2 に変わり、依存する値の行も 1 本増えている。値の履歴だけでは、この差は出せない。

引く時点を渡すと、式の版のほうも公表前には出てこない。

```
$ python formula_table.py eval 式.csv --values 値.csv --id 折半額 --input 報酬月額=300000 --on 2026-04-01 --as-of 2026-02-05
{"ok": false, "id": "折半額", "reason": "式の版が as_of 時点で未公表",
 "detail": "式『折半額』の行 2 は 2026-02-05 の時点で未公表"}
```

丸めが書かれていない行は、計算できるかどうかに関係なく止まる。

```
$ python formula_table.py eval 壊れた式.csv --id 丸めが無い式 --input 報酬月額=300000 --on 2025-06-01
{"ok": false, "id": "丸めが無い式", "reason": "丸めが空欄",
 "detail": "式『丸めが無い式』の行 1 に rounding が無い"}
```

止まる理由コードは 8 つで、これ以上増やしていない。

| 理由コード | 何が足りないか |
|---|---|
| 丸めが空欄 | 式の行に丸めの名前が書かれていない。部品は既定の丸めを持たない |
| 未登録の丸めの名前 | 書かれた丸めの名前が登録されていない |
| 未登録の関数 | 式が呼んでいる名前が登録されていない |
| float 混入 | 入力か定数に float が混ざっている |
| 式の版が as_of 時点で未公表 | 有効期間では当たる行があるが、引く時点ではまだ公表されていない |
| 依存が循環している | 式が直接または間接に自分自身を参照している |
| 入力が足りない | 式が要求している項目が渡されていない |
| 依存先が決まらない | 引こうとした式の版か値の行が、収録範囲の外か、同順位で複数該当した |

### 式を文字列のまま実行しない

数式を data にすると、その文字列をどう計算するかという問題が出てくる。ここは言語の汎用の評価機能をそのまま使わず、構文を絞った木をたどる形にした。

通すのは、四則、単項マイナス、比較、条件式、登録した関数の呼び出し、名前の参照だけだ。属性アクセス、添字、内包表記、lambda、代入、`and` と `or`、べき乗、剰余は構文の段で拒否する。拒否は理由コードではなく表の不備として扱う。表に書いた式がそもそも許されない形なら、それは引き当ての失敗ではなく、表を直すべき話だからだ。

数は `Decimal` だけで扱う。float が入力に混ざったら止める。式の中の小数のリテラルも float を経由させず、元の文字列から `Decimal` にしている。二進小数の誤差が端数処理に乗ると、ちょうど半分の境界が 1 つ手前へずれて、丸めの向きが変わるからだ。これはテストで押さえてある。

丸めの関数は式の中から呼べない。丸めるのは表の `rounding` 列だけで、式の側に丸めを書く道を残していない。書ける場所が 2 か所あると、片方に書いてもう片方を空にした行が必ず出る。

```python
from datetime import date
from formula_table import FormulaTable, ValueTable, evaluate, validate

ft = FormulaTable.load("式.csv")
vt = ValueTable.load("値.csv")
r = evaluate(ft, "折半額", {"報酬月額": "300000"}, on=date(2026, 4, 1), as_of=date(2026, 2, 5), values=vt)
print(r.value, r.rounding, [u.source for u in r.used]) if r.ok else print(r.reason, r.detail)
```

表そのものの検査は別にある。同じ `id` で有効期間が重なっている行、丸めが空欄の行、許可外の構文を含む式、依存が循環している式。見つけても直さない。一覧にして返すだけだ。

## 検証

テストは 70 件。fixture は合成データで、率も単価も出典名も架空だ。実在の料率や給付額、端数処理の規定値は 1 つも入れていない。

```
$ python -m pytest tools/formula_table -q
......................................................................
70 passed in 0.62s
```

測定は 2 つある。どちらも決定論で、乱数を使っていない。

1 つめが丸めの測定だ。合成の報酬月額 20 通りと合成の料率 6 通りを掛け合わせた 120 件について、折半額を出す。まず丸めずに端数を見て、次に同じ金額を、表で丸めを指定した場合と、実行環境の既定に任せた場合の両方で丸め、食い違う組み合わせを数える。既定の側は 3 通りで、組み込みの丸め、`Decimal` の既定、整数に落とすだけの切り捨てになる。

```
[measure] 合成の金額 120 件 / 端数が出た 107 件 (うち端数ちょうど 0.5 が 18 件)
[measure] 表で『50銭以下切捨て』を指定 vs 実行環境の既定: round 8 件 / Decimal の既定 8 件 / int 46 件 が食い違う
[measure] 表で『1円未満切捨て』を指定 vs 実行環境の既定: round 54 件 / Decimal の既定 54 件 / int 0 件 が食い違う
[measure] 表で『円未満四捨五入』を指定 vs 実行環境の既定: round 10 件 / Decimal の既定 10 件 / int 64 件 が食い違う
```

被保険者負担の丸めで組み込みの丸めと食い違ったのは 8 件で、これは端数がちょうど半分だった 18 件のうち、整数部が奇数だったものにあたる。半分ちょうどが出なければ両者は一致するので、食い違いの件数は合成の作り方で決まる。ここで固定しているのは件数そのものではなく、**同じ金額・同じ項目でも、丸めを指定するかどうかで答えが変わる経路が実際に動く**ことのほうだ。

この測定の比べ方には限界がある。実行環境の既定として測ったのは組み込みの丸め、`Decimal` の既定、整数への切り捨ての 3 つだけで、表計算ソフトの丸め関数や他の言語の既定は測っていない。だからこの記事の数字は「言語や道具を問わずこうなる」という話ではなく、私が使っている実行環境ではこうなった、という話になる。

2 つめは式の版の測定だ。式をコードに 1 本だけ焼いて値だけ表から引く側と、式も表から引く側を、改正の前後の日付で比べる。

```
[measure] 式の版 40 件: 式をコードに固定して値だけ表から引く側と 20 件で答えが違った(改正後の 20 件が全部)
[measure] 同じ引き当てで as_of だけ動かすと、公表前の 20 件は 『式の版が as_of 時点で未公表』で止まり、公表後の 20 件だけ値を返した
```

式をコードに固定した側は、料率の値が新しくなっても計算の形が古いままなので、改正後の 20 件が全部ずれる。値の履歴をどれだけ正確に持っていても、この差は埋まらない。引く時点を動かす測定のほうは、式の版にも公表時点が付いていることの確認で、公表前の 20 件は値を返さずに止まった。

残りのテストは、8 つの理由コードが全部通る道を持つこと、丸めの名前ごとに境界の値が固定値どおりになること、式が式を引けて途中は丸めずに渡せること、改正の前後で入力の数が変わってもそれぞれの版が自分の入力を要求すること、施行日が政令待ちの行が評価に決して現れないこと、許可外の構文 10 通りが全部拒否されること、`0.1 + 0.2` が `0.3` になること、壊れた表の 11 行から 4 種類の不備を全部拾って 1 行も直さないこと、終了コードが評価できたら 0・理由コードで止まったら 3・表や引数が壊れていたら 2 になること、を見ている。合成 fixture が生成器から決定論的に出ることも、ディスク上の CSV と突き合わせて確かめてある。

私の参照表の側でも、同じ丸めの境界は固定値で押さえてある。端数 50 銭ちょうどは切り捨て、そこから 1 銭でも超えれば切り上げ、という 2 つの値を、2,856 円台の金額で試験に置いてある。今回作った部品の丸めは、その境界と同じ振る舞いになるようにした。

## 図 2 評価の流れと、止まる場所

![式の版を引き、丸めを確かめ、依存を辿り、構文を絞り、計算して丸め、出典を付けて返す流れ図](figures/formula_table_flow.png)

段は 6 つで、橙のピルが関所だ。2 段目が丸めの確認で、ここは計算の前に置いてある。計算してから丸め方を探すのではなく、丸め方が決まらない式はそもそも計算しない。順番を逆にすると、「計算はできたが丸め方が分からないので、とりあえず既定で返す」という経路が書けてしまう。

この図でも、見てほしいのは描かれていない経路のほうになる。どの段から出ても行き先は理由コードで、「丸めが分からないので既定で丸める」や「この版が無いので直近の版を使う」に戻る矢印がどこにも無い。実装でも同じで、評価の関数に丸めを渡す引数も、受け皿の引数も持たせていない。落ちる先が無ければ、落ちる経路も書けない。

## 道具

[formula_table](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/formula_table) に置いた。`formula_table.py` 1 ファイルと、テスト、合成 fixture の生成スクリプトが入っている。依存は無く、標準ライブラリだけで動く。ライセンスは MIT。

丸めの名前は 4 つ用意してある。50 銭以下を切り捨てて超えたら切り上げるもの、1 円未満を切り捨てるもの、円未満を四捨五入するもの、丸めないものだ。足りなければ登録を増やす。増やす場所は 1 か所で、式の側には書けない。自分の現場に合わせるときに触るのは表のほうで、`id` と式と丸めの名前を差し替える。部品のコードは触らない。

## 別の業種なら

この部品は、給与や社会保険の語彙をひとつも持っていない。持っているのは行の形と、引く順番と、丸めを表から取るという決まりだけだ。会計の消費税と源泉徴収の端数、請求書の単価と数量を掛けたあとの丸め、EC の送料や手数料やポイント、医療や介護の点数計算、建設の歩掛りでも、丸め方が項目ごとに定められていて実行環境の既定と食い違う形は同じだと考えている。私が実測したのは上の合成データと、自分の参照表の範囲だけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。変わるのは `id` の名前と式の中身、それに丸めの名前だけで、部品そのものは書き換えずに持ち出せる。消費税の端数なら丸めの名前を切り捨てにし、送料の丸めなら四捨五入にする、という差し替えになる。部品の側からは、保険料も消費税も送料も同じことになる。

## できないこと

- 値そのものの正しさは判定しない。式が制度に合っているかも見ない。表に書いてあるとおりに計算するだけで、書いた人が間違っていれば間違った値が出る
- 丸めの名前は 4 つしか持たない。別の丸め方が要るなら登録を足す作業が要る。式の側に丸めを書いて済ませることはできない
- 状態を持つ計算はできない。履歴を走査して決まるような判定は、式 1 本の評価では閉じない。そこは表の外に置く
- 表計算ソフトや他の言語の既定の丸めは測っていない。測ったのは私の実行環境の 3 通りだけで、上の件数はその範囲の話になる
- 単位を持たない。円なのか銭なのか率なのかは式の側に書く。単位の取り違えは検査できない
- 表の検査が見るのは期間の重なりと丸めの空欄と構文と循環の形だけで、式の意味は見ない
- 上の数字は合成データと私の環境での測定で、他の人の表や環境で同じ内訳になるとは限らない。特に食い違いの件数は、端数がちょうど半分になる金額がどれだけ含まれるかで変わる
- 私の参照表のほうも、丸めが出典つきで記録できている項目はまだ一部だ。表に丸めの列を足したからといって、全部の行が埋まるわけではない
