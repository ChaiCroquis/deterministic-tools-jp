前回は、相手先ごとに形の違う表を核の列仕様へ読み替える部品を作った。その前は、人ごとと項目ごとに足して両方が合うまで次に渡さない関所だ。ここまでで「同じ形の行がそろっていて、足し算も合っている」状態までは来た。次に来るのは「その行が、相手の取込仕様に入るか」になる。この記事で作るのは、入らない行を 1 件も直さずに 3 つへ仕分ける部品だ。

**なぜ重要か**: ここで機械が「たぶんこう直せばいい」まで踏み込むと、直した跡が残らないまま元の表と合わなくなる。全角の数字を半角に寄せ、足りない桁をゼロで埋め、似たコードに寄せる。どれも単体では正しそうに見えるが、後から「どの値を機械が動かしたのか」を言えなくなる。だからこの部品は値を 1 つも書き換えない。列ごとの違反を「そのまま通る」「宣言された直し方で通る」「人が決めるしかない」の 3 つに分け、行の分類はその最悪値で決める。この記事で見たいのは仕分けの実装ではなく、**3 本目の線がどこに引かれるかが、値ではなく宣言の側で決まる**という点のほうだ。

**要点**:
- 部品は 1 件も直さない。返すのは適用すべき直し方の名前と、対象の列と、現在の値だけになる
- 同じ値・同じ違反でも、それを覆うと宣言された直し方が仕様表に在れば 2 本目、無ければ 3 本目に落ちる。線を動かすのは仕様表を書く人で、部品は自分で広げない
- 宣言では動かせない線もある。桁あふれを覆う直し方は 1 つも登録していないので、常に人の判断に落ちる
- 人が決めるしかない行が残っているあいだ、通る行だけを集めて渡す経路を持たない。取り込める率も分母の内訳と一緒にしか出さない

**数字で見る**: 合成の行 18 行を仕分けると、そのまま通る 6 / 宣言された直し方で通る 6 / 人が決めるしかない 6 で、違反は 12 件だった。仕様表の直し方を 1 欄だけ空にすると、同じ 18 行が 6 / 5 / 7 に動いた。

---

## 何を解決するのか

渡す前の検査は、ここまでに 2 つ作っている。1 つは書き出した取込用 CSV を読み戻して突き合わせるもの、もう 1 つは人ごとと項目ごとの合計が全部一致するまで出力を作らない関所だ。どちらも「こちら側で作った数字が壊れていないか」を見ている。

今回はその先で、相手の取込仕様という外側の宣言に照らす。私の記録では、取込側の制約に合わせている道具が 36 本ある。型と値域の検査、符号の置き方、コードの登録有無。帳票の書式のズレを踏んでいる道具が 30 本、コードや名前のマスタ不一致を踏んでいる道具が 29 本あって、これらはどれも最後に「取込側の仕様に入るか」で合流する。

痛い記憶もそこに残っている。ある移行作業の見積もりが、1 社あたり 4〜5 日、100 社で 500 日になって頓挫している。この数字を見ると、人の手を減らす方向に力がかかる。つまり「機械が決めてよい範囲」を広げたくなる。実際、その頃に作ったものは 3 分類に加えて、相手への問い合わせ文の下書きまで作るようになっていた。

ただ、広げた境界はコードの中に溶ける。「この列は全角が来たら半角に寄せる」「このコードは未登録なら近いものに寄せる」という判断が実装の分岐として埋まると、半年後には誰がどの範囲を機械に任せたのか読めなくなる。直した値はもう元の印字と違うので、相手先の表と突き合わせても合わない。

だからこの部品では、境界を宣言の側に出した。部品が持っているのは、違反の名前 7 つと、直し方の名前 8 つと、その名前がどの違反を覆うと言っているかの対応だけだ。どの列にどの直し方を宣言するかは仕様表の側にしか無い。**同じ違反でも、覆うと宣言された直し方が在れば 2 本目に入り、無ければ 3 本目に落ちる**。そして問い合わせの文面は作らない。渡すのは「どの行のどの列が、どの宣言とどう違うか」までで、宛先も依頼の内容も優先順位も人が決める。

## 図 1 線はどこで引かれるのか

![違反 8 種類と、そのまま通る・宣言された直し方で通る・人が決めるしかない・止まる の 4 つの分類の対応表](figures/intake_triage_boundary.png)

行が違反、列がその違反の落ちる先だ。各セルの実走の件数は、合成の行に対してその場で動かした仕分けの出力で、テストが固定している。記録の側の件数は私の棚卸し記録から取っている。この型の元の指示は「各セルに規制文書の URL を置く」なのだが、本シリーズの出どころは公開された規制文書ではなく手元の仕様表なので、仕様表のファイル名とその sha256、それに私の記録の該当箇所に読み替えてある。

読みどころは 3 つある。

1 つめは、**2 本目の列と 3 本目の列が、同じ値のまま入れ替わる**ところだ。引く側の列に正の数が入っている行は「範囲の外」という違反になる。この列に「印字は符号なし」という直し方が宣言されていれば 2 本目、宣言の欄が空なら 3 本目に落ちる。値は `48250` のままで、違反の名前も同じだ。変わったのは仕様表の 1 欄だけになる。実走でも、同じ 18 行が 6 / 6 / 6 から 6 / 5 / 7 へ動いた。

2 つめは、**宣言では動かせない線がある**ことだ。桁あふれを覆う直し方は 1 つも登録していない。桁を詰めれば形式としては通るが、それは別の値になる。だから桁あふれは常に 3 本目で、仕様表に何を書いても 2 本目には来ない。線が動く違反と動かない違反がある、というのがこの表のいちばんの収穫だった。

3 つめは、右から 2 列目の中に紛れている厄介さのほうだ。**2 本目は「人が宣言した範囲」であって「機械が直せる範囲」ではない**。日付の列に「区切りを外して 8 桁に」を宣言しておくと、`2026-09-25` も `20260931` も同じ「形が違う」という違反になるので、どちらも 2 本目に入る。後者は暦に無い日なので、区切りを外しても直らない。部品は宣言の正しさを判定しないから、宣言が雑なら 2 本目が太る。これは欠陥であって、仕様ではない。線を宣言の側に出した代償がここに出ていると考えている。

## 手順

入力は 2 つだ。1 つは仕分ける対象の行で、前の工程(形の違う表を読み替える部品 → 2 つの軸から足す関所)が渡してくる。もう 1 つが取込先の仕様表になる。

仕様表は 1 列が 1 行で、欄は 6 つだ。

```
column,type,domain,required,repair,source
社員番号,コード,長さ: 6,○,先頭をゼロで埋める,合成の取込仕様(架空)
氏名,文字列,長さ上限: 40,○,,合成の取込仕様(架空)
部署コード,コード,集合: 10|20|30,○,,合成の取込仕様(架空)
支給年月日,日付,形: YYYYMMDD,○,区切りを外して 8 桁に,合成の取込仕様(架空)
支給合計,金額,範囲: 0..9999999,○,半角の数字に直す,合成の取込仕様(架空)
控除合計,金額,範囲: -9999999..0,○,印字は符号なし,合成の取込仕様(架空)
差引支給額,金額,範囲: -9999999..9999999,○,桁区切りのカンマを外す,合成の取込仕様(架空)
備考,文字列,制限なし,,,合成の取込仕様(架空)
```

| 欄 | 意味 |
|---|---|
| `column` | 列名。行の見出しと一致する |
| `type` | 型の名前。文字列 / 整数 / 金額 / コード / 日付。**空欄は許さない** |
| `domain` | 許容する値。**空欄は許さない**(制限を付けないなら `制限なし` と書く) |
| `required` | 埋まっていなければ違反とする列に印を付ける |
| `repair` | その列の違反を覆うと宣言する直し方の名前。**空欄なら 3 本目に落ちる** |
| `source` | 出典。報告に載る |

部品は取込先の製品名も分野の語彙も持っていない。`支給合計` も `部署コード` も、ただの文字列として宣言から受け取る。型の名前は 5 つ、値域の書き方は 6 通り(`制限なし` / `集合:` / `範囲:` / `長さ:` / `長さ上限:` / `形:`)で、どちらも空欄を許さない。既定の型を持たせると、宣言を書き忘れた列が黙って通ってしまうからだ。

仕分けるときは識別子の列名も宣言する。これにも既定を持たせていない。

```
python intake_triage.py triage 行.csv --spec 仕様表.csv --key 社員番号
```

```
{"ok": true, "stage": "仕分けた", "行": 18,
 "件数": {"そのまま通る": 6, "宣言された直し方で通る": 6, "人が決めるしかない": 6},
 "分類": [{"識別子": "000109", "分類": "宣言された直し方で通る",
           "違反": [{"列": "控除合計", "現在の値": "48250", "違反": "範囲の外",
                    "分類": "宣言された直し方で通る",
                    "宣言": "型 金額 / 値域 範囲: -9999999..0(埋まっていなければ違反)",
                    "適用すべき直し方": "印字は符号なし"}]}]}
```

返っているのは「現在の値」と「適用すべき直し方の名前」で、直した後の値ではない。部品の中に値を書き換える経路が無いので、出しようがない。

明細だけを表で受け取ることもできる。人に渡す素材はここまでだ。

```
python intake_triage.py report 行.csv --spec 仕様表.csv --key 社員番号 --format csv
```

```
識別子,列,現在の値,違反,分類,宣言,適用すべき直し方,出典
101,社員番号,101,長さが違う,宣言された直し方で通る,型 コード / 値域 長さ: 6(埋まっていなければ違反),先頭をゼロで埋める,合成の取込仕様(架空)
000113,部署コード,40,集合の外,人が決めるしかない,型 コード / 値域 集合: 10|20|30(埋まっていなければ違反),,合成の取込仕様(架空)
000116,支給合計,99999999,範囲の外,人が決めるしかない,型 金額 / 値域 範囲: 0..9999999(埋まっていなければ違反),,合成の取込仕様(架空)
```

3 行目が、さっきの「2 本目に入らない」例だ。`支給合計` には直し方が宣言されているが、それが覆うのは「型と違う」だけで、「範囲の外」は覆わない。同じ列の同じ宣言でも、違反の種類が違えば落ちる先が変わる。適用すべき直し方の欄は空のまま返る。

線が宣言で動くことは、仕様表を 2 枚用意すれば目で見える。差は `控除合計` の `repair` の 1 欄だけで、ファイルの sha256 も違う。

```
$ python intake_triage.py triage 行.csv --spec 仕様表.csv       --key 社員番号
{"件数": {"そのまま通る": 6, "宣言された直し方で通る": 6, "人が決めるしかない": 6}}
$ python intake_triage.py triage 行.csv --spec 仕様表_符号なし.csv --key 社員番号
{"件数": {"そのまま通る": 6, "宣言された直し方で通る": 5, "人が決めるしかない": 7}}
```

そのまま通る行は動かない。動いたのは 2 本目と 3 本目のあいだだけだ。

仕様表か行の側が噛み合っていない時は、1 行も判定せずに止まる。

```
{"ok": false, "stage": "突き合わせ", "行": 7,
 "件数": {"そのまま通る": 0, "宣言された直し方で通る": 0, "人が決めるしかない": 0},
 "pending": [{"reason": "行の識別子が重複",
              "detail": "識別子『000101』の行が 2 行ある(1 行目 / 7 行目)"}]}
```

止まる理由コードは 8 つで、これ以上増やしていない。

```
型の名前が空欄 / 値域の宣言が空欄 / 同じ column が仕様表に 2 行 / repair の名前が辞書に無い /
必須列が仕様表に無い(識別子の列が無い等)/ 仕様表に無い列が行に在る / 行の識別子が重複 /
判定前に出力を要求した
```

仕様表そのものが読めない場合(登録していない型の名前、値域の書き間違い、型に書けない値域の種類)は理由コードにせず、表を直す話として終了コード 2 で返す。終了コードは、全ての行がそのまま通れば 0、それ以外の行が在るか理由コードで止まれば 3、仕様表や引数が壊れていれば 2 になる。

取り込める率は、分母の内訳と一緒にしか出てこない。

```
{"そのまま通る": 6, "宣言された直し方で通る": 6, "人が決めるしかない": 6,
 "行": 18, "判定した行": 18, "判定しなかった行": 0,
 "そのまま通る割合_判定した行のみ": "0.3333",
 "分母に含めたもの": "判定した行 = そのまま通る 6 + 宣言された直し方で通る 6 + 人が決めるしかない 6 = 18 / 全ての行 = 18(仕分けできずに判定しなかった 0 行を含む分母)"}
```

前の部品で一致率を出したときと同じ規律だ。止まって判定できなかった行を分母から落とすと、数字だけが良くなる。

```python
from intake_triage import Spec, triage

t = triage(rows, Spec.load("仕様表.csv"), "社員番号")
for v in t.violations():
    print(v.key, v.column, v.value, v.violation, v.judgment, v.repair)
rows = t.handoff()      # 全ての行がそのまま通った時だけ返る(それ以外は例外)
```

`handoff()` は、そのまま通る以外の行が 1 行でも残っていれば例外で止まる。直し方待ちの行だけが残っている場合も渡さない。通る行だけを抜き出して先に流す経路を持たせると、「半分だけ取り込んで、残りは後で」という状態が作れてしまうからだ。部品自身はファイルを書かないので、渡した先で書くことになる。

違反の内訳を少し補う。2 本目に落ちた 6 件のうち、1 件は長さが違う識別子、2 件は型と違う値(全角の数字と桁区切りのカンマ)、1 件は範囲の外(符号なしで印字された引く側の値)、2 件は日付の形だ。3 本目の 6 件は、未登録のコード、空欄、桁あふれ、範囲の外、そして型と違う値が 2 件になる。同じ「型と違う」「範囲の外」という違反が 2 本目にも 3 本目にも出ているのが、この記事でいちばん見てほしいところだ。落ちる先を決めているのは値ではなく、その列の宣言のほうになる。

残りのテストは、8 つの理由コードが全部通る道を持つこと、7 つの違反の名前が全部出る道を持つこと、行の分類がその行の列の最悪値と一致すること、適用すべき直し方の欄が 2 本目の行にだけ入ること、仕分けのあいだ入力の行が 1 つも書き換わらないこと、閾値や優先順位の引数が関数にも CLI にも無いこと、部品のソースに問い合わせ文らしき語も分野の語彙も無いことを見ている。判定に使った仕様表のファイル名と sha256 が報告に載ることも、ファイルを読み直して突き合わせてある。

いつも成り立つことは 1 文にして、性質テストで確かめている。仕分けの結果は 2 通りしかない。全ての行がちょうど 1 つの分類に入り、どの行の分類もその行の列の最悪値と一致するか、行は 1 つも分類されず理由コードが返るか、だ。どちらの場合も、この部品は値を 1 つも書き換えず、ファイルを 1 つも開かない。宣言どおりの行を乱数で作り、15 通りから 1 つ引いて 1 か所だけ壊し、さらに各列の直し方の宣言を乱数で付け外しして、毎回この 1 文が成り立つかを見る。乱数は固定で、毎回同じ 300 通りを試す。判定は道具の関数を使わず、テストの中に別に書いてある。

## 図 2 仕分けの流れと、止まる場所

![仕様表を検査し、行と突き合わせ、列ごとに 3 値で判定し、行を最悪値で分類して件数と明細を返すまでの流れ図](figures/intake_triage_flow.png)

段は 6 つで、橙のピルが関所だ。前の 3 段は宣言と入力の噛み合わせの検査で、1 行も判定する前に置いてある。ここで止まると分類は 0 件になり、率は「分母が 0」と返る。

この図でも見てほしいのは描かれていない経路のほうになる。判定の段から先へ、「覆う直し方が無いので近い値に寄せる」や「3 本目が少ないので閾値を下げて通す」に進む矢印がどこにも無い。実装でも同じで、値を書き換える関数も、閾値や優先順位の引数も持たせていない。最後の段から「そのまま通る行だけを集めて取込ファイルにする」へ出る矢印も無い。落ちる先が無ければ、落ちる経路も書けない。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/intake_triage) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。仕様表のひな型は `init` で出る。

```
python intake_triage.py init 仕様表.csv
```

自分の取込仕様に合わせるときは、この CSV を書き換える。部品のコードは触らない。足りない直し方があれば、部品の側に名前を 1 つ登録してから仕様表で宣言する。名前を登録するところまでは機械の仕事だが、どの列にその名前を書くかは人の仕事だ。

## 別の業種なら

この部品が持っているのは、列名・型・値域・埋まっていなければ違反という印・直し方の名前という欄だけだ。仕訳の取込(科目コードが未登録、貸借の桁あふれ、日付の形)、出荷データの取込(配送コードが未登録、住所の桁あふれ)、実行予算の取込(工種コードの不一致)、請求データの取込(区分コードの未登録)。どれも「機械がたぶん直せると踏み込みたくなる」場面で、同じ構図だと考えている。私が実測したのは上の合成データの範囲だけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。変わるのは仕様表の中身だけで、入力の例を仕訳や受注データに差し替えれば部品はそのまま使える。

## できないこと

- 分類が合っていても、取込先が実際にその行を受け取るとは言えない。見ているのは手元の仕様表の宣言だけで、取込先に投げて確かめてはいない。値が業務として正しいかも判定しない
- **宣言が覆うと言った違反は、実際には直せない値でも 2 本目に入る**。暦に無い日に日付の形の直し方が宣言されている場合がそれで、宣言の正しさを部品は判定しない。2 本目は「人が宣言した範囲」であって「機械が直せる範囲」ではない
- 違反は 1 列につき 1 つだけ返す(型 → 値域 の順で最初に当たったもの)。同じ列に 2 つ重なっている場合、2 つめは 1 つめを直した後にもう一度かけて見つけることになる
- 宣言した列が行に無ければ、その列は全行で空として判定される。黙って通ることはないが、「列が無い」という理由コードは持たない
- 直し方の名前は部品に登録した 8 つだけで、どれも値を直す実装は持っていない(覆う違反の一覧を持つだけ)。実際に直すのは人か後の工程になる
- 文字コードも区切りも扱わない。この部品は読み込んだ行を受け取る
- 上の件数は合成データでの測定で、他の人の表で同じ内訳になるとは限らない。違反の一覧も私の記録の範囲で、網羅ではない
