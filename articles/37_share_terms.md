前回は、引ける状態にした行のうちどれが実際に参照されるかを数えた。今回は同じ表を、外に出す側から見る。骨は 1 行で言える。**手元で引ける行と、外に出して配れる行は別で、配れる形かどうかは行の欄に書かれた許諾の宣言からしか決まらない。**

**なぜ重要か**: 私の記録には、行の形を決めた表がある。そこには `source` と `source_url` と `license` の列が最初から並んでいる。**つまり「許諾を書く場所」は最初から在る。** 配る側の宣言も、自分の書いたものについてははっきり書いてある。公開している repo の README には「ライセンス」の見出しがあり、その下に MIT だと書き、コード・図の生成器・生成した図・記事本文を含む repo 全体に適用する、と続けてある。ところが収録した行の側を見ると、許諾の名前が書かれている出どころと、書かれていない出どころが混ざっている。名前が在るのは上流由来の 2 か所で、上流 clone に MIT、別の節に公共データ利用規約と書いてある。名前が無いのは自前抽出の 3 領域で、出典元もファイル名も抽出器も年度も書いてあるのに、許諾の名前だけがどこにも無い。**列は在る。宣言は一部だけ在る。この状態を「ライセンス未整理」の 1 語で呼ぶと、配る前に何をすればよいかが決まらない。**

**要点**:
- 外に出す宣言を先に見る。`出さない` と書かれた行は、許諾が何を要求していようと足りない欄を数えない。宣言そのものが無い行も、欄が足りない行とは別の値で返す
- 許諾の名前を推測しない。出典元の名前やファイルの拡張子から名前を当てる経路を道具に持たせず、登録表に無い名前と空欄はどちらも別枠に出す
- 要求される欄は、許諾の登録表に人が書いた宣言から読む。規約の原文を取りに行く経路も本文を読む経路も持たず、道具は規約の中身を知らない
- 配ってよいかは判定しない。返るのは宣言が揃っているかの 4 値と別枠だけで、終了コード 0 も「手元の表に欠けが無い」の意味にとどめる

**数字で見る**: 合成した 4 枚(台帳 15 rule・867 行 / 許諾の登録表 3 行 / 出典元 7 行 / 配布物の目録 8 行)を通すと、**出すと宣言されているのは 12 rule・769 行、そのうち宣言が揃っているのは 5 rule・389 行**だった。残りは **欄が空 3 rule・169 行** と **許諾の名前が登録表に無い 4 rule・211 行** に分かれた。

## 何を解決するのか

### 「収録済み」から「配れる」までに、別の状態が並んでいる

表に行が入ると、どの行も同じ顔をする。rule の名前があり、行数があり、出典があり、引けば値が返る。前回はここから「参照されるか」を数えた。今回はもう 1 つ先の問いを立てる。**この行を外に出してよいと、誰がどこに書いたか。**

聞いた瞬間に、答えが分かれる。

- 出すと宣言され、その許諾が要求すると宣言した欄も全部埋まっている行
- 出すと宣言されたが、要求される欄が空の行
- 出さないと宣言された行
- 出すとも出さないとも書かれていない行
- 出すと宣言されたが、許諾の名前がそもそも書かれていない行

最初の 1 つだけが、そのまま配布物に入れられる行だ。残りはどれも手が要るが、**要る手が全部違う**。2 つ目は埋める欄の名前が決まっている。3 つ目は何もしなくてよい。4 つ目は出すか出さないかを決める番で、5 つ目はどの許諾が当たるかを決める番になる。

この 5 つを「ライセンス未整理」という 1 つの名前で呼ぶと、**埋める欄が決まっている状態と、そもそも誰も決めていない状態が、同じ列に並ぶ**。並んだ時点で、次にやることが表から読めなくなる。

### 足りない欄と、決めていないことを潰さない

この回でいちばん書きたかったのが、2 つ目と 4 つ目の差だ。

2 つ目は、宣言までは済んでいる。出すと書いてあり、許諾の名前も書いてあり、その許諾が何を要求すると宣言されているかも登録表に書いてある。足りないのは行の欄だけで、**足りない欄の名前が出せる**。帰属の文字列が空、原文の URL が空、版の指紋が空、と名前で出る。埋めれば揃う。

4 つ目は、宣言そのものが無い。出すとも出さないとも書かれていないので、**何を埋めればよいかが決まらない**。許諾の名前が書いてあっても同じで、出さないなら帰属の文字列は要らないし、出すなら要る。先に決めるのは欄ではなく、出すか出さないかのほうになる。

だからこの部品は、外に出す宣言を**いちばん先に**見る。`出さない` ならそこで終わり、空ならそこで終わり。要求される欄を見に行くのは、`出す` と書かれた行だけだ。この順番が、2 つの状態を別の値に分ける物理的な形になっている。

### 配らないと宣言した行に、足りない欄は無い

もう 1 つ、数え方で手が滑るところがある。

私の記録には、上流から取った協会けんぽの JSON について「照合専用」と書いてある。自前の抽出結果と 47 支部ぶんが一致するかを毎回確かめるために置いてあるもので、本番の行として引く対象ではない。前回の回では、この行は「参照されないのが正しい状態」として別枠に置いた。

今回も同じ行が出てくるが、**入る枠が違う**。前回は参照されるかどうかの軸だったので別枠だった。今回は外に出すかどうかの軸なので、「出さないと宣言された」という本体の値に入る。軸が違えば、同じ行でも入る場所が変わる。

この行の許諾の名前は上流と同じ MIT で、その MIT は帰属の文字列を要求すると宣言されている。けれど配らないのだから、帰属の文字列が空でも足りない欄は 0 件だ。ここを足りない側に混ぜると、**埋めようのない欄が待ち行列に並ぶ**。

### 許諾の名前を推測しない

最後に、この種の道具がいちばん壊れやすいところを書いておく。

出典元の名前を見れば、たいてい見当はつく。当てを道具に入れると、名前の欄が空でも動く道具になる。けれどそうすると、**名前が書かれていないという事実そのもの**が見えなくなる。書かれていないことと、書いた上でその許諾が何も要求していないことは別の状態だ。だからこの部品には、出典元の名前や URL の形から許諾を当てる呼び出しを 1 つも持たせていない。名前の欄が空の行と、書いてあるが登録表に無い行は、どちらも別枠に出る。そのかわり、**別枠の各行には必ず出典を付ける**。誰がどこにそう書いた(あるいは書かなかった)かを併記しないと、その行は推測の置き場になるからだ。

名前と、その名前が書かれている場所の食い違いも入口で止める。出典元の台帳に「許諾の名前が書かれている場所」の欄があり、場所が空なのに行に名前が書いてあれば止まる(名前の出どころが無い)。逆に場所が在るのに行の名前が空でも止まる(書かれているものを行に写していない)。

この図は論評ではなく一覧だ。行が出どころで、左から、やっていること(記録の文そのもの)、手元で引く側か配る側か、許諾について書かれていること(在るものだけそのまま写す)、機械で突き合わせた結果、版と日付、出典になる。出典はファイル名を伏せた行番号で書いた。

**許諾について書かれていることの欄が、上の 3 行で空になっている。** そこは私が推測で埋めなかったところだ。自前抽出の 3 領域は、出典元もファイル名も抽出器も年度も記録に在るのに、許諾の名前だけがどこにも書かれていない。この型の約束として、書かれていない欄に「たぶんこれ」とは書かない。

淡い藍のセルが、原文に宣言が在るところだ。上流由来の 2 行には許諾の名前が在る。照合専用の行には、出さないと読める宣言が在る。いちばん下の自分のコードと記事の行だけが、出すと読める宣言と、許諾の名前と、その条件の 3 つとも揃っている。

**淡い橙が、書かれていないか、行の欄としては空のところになる。7 行のうち 5 行で、外に出す宣言そのものが書かれていない。** 名前が在る上流由来の 2 行でさえ、出すとも出さないとも書いていない。いちばん下の行も、repo 全体への宣言は在るが、行ごとの帰属の文字列の欄は手元の記録に無い。

**規制側の反応の列は置かなかった。** 問い合わせも回答も手元に無いので、列ごと欠けていることを図の脚注に書いてある。どの規約が当たるかも、配ってよいかも、この図には書いていない。並べたのは、宣言が在るか無いかと、その在りかだけだ。

収集範囲の限界も書いておく。見たのは手元の 3 つのファイルと、公開している repo の README までだ。各出どころの規約の本文は 1 つも読んでいない(だから道具にも読む経路を作っていない)。件数と年度は記録に書かれた数字の写しで、自分で数え直してはいない。実在の料率も金額も、図にも記事にも出していない。

## 手順

ひな型を出す。行の台帳・許諾の登録表・出典元の台帳・配布物の目録の 4 枚が出る。

```
python share_terms.py init ひな型/
```

行の台帳には、収録した rule を 1 行ずつ書く。

```csv
table_id,rule_id,rows,origin_id,license_name,attribution,source_url,fingerprint,share,source
H1,K11,120,G1,MIT,合成の帰属の文字列 A(架空),,9a1c0f22b7d4,出す,私の棚卸し記録(非公開)L37
H1,K12,55,G1,MIT,,,9a1c0f22b7d4,出す,私の棚卸し記録(非公開)L37
H3,K31,141,G3,,,,c40d2a6b1f85,出す,私の抽出のメモ(非公開)L64
H4,K41,39,G4,,,,71b9e3d08a2c,,私の抽出のメモ(非公開)L64
H6,K61,47,G7,MIT,,,e619d7c3b45f,出さない,私の上流のメモ(非公開)L68
```

`share` が外に出す宣言で、`出す` と `出さない` と空欄の 3 通りしか受け取らない。`attribution` は帰属の文字列で、**書いてある文字列をそのまま写す欄**になる。道具が文面を組み立てる経路は無い。`source` は出典で、空欄の行があれば 1 件も数えずに止まる。

許諾の登録表には、その許諾が何を要求すると宣言されているかを書く。

```csv
license_name,needs_attribution,needs_source_url,needs_fingerprint,declared_in
MIT,要る,要らない,要らない,私の上流のメモ(非公開)L18
公共データ利用規約,要る,要る,要る,私の上流のメモ(非公開)L68
合成の公開の宣言(架空),要らない,要らない,要らない,私の配る側のメモ(非公開)L95
```

要求される欄は帰属の文字列・原文の URL・版の指紋の 3 つだけで、**ここを増やす経路を入力側に持たせていない**。規約の本文から欄を起こす変換が無いからだ。`declared_in` はその宣言の出典で、空欄なら止まる。3 行目のように **要求される欄が 0 個の許諾**も書ける。そのときは 3 欄が全部空でも揃っていると出る。道具が既定を持たないことの、いちばん分かりやすい形になる。

出典元の台帳には、取得した版と、許諾の名前がどこに書かれているかを書く。

```csv
origin_id,fingerprint,got_on,license_written_at
G1,9a1c0f22b7d4,2026-05-11,私の上流のメモ(非公開)L18
G3,c40d2a6b1f85,2026-05-11,
```

`license_written_at` が空の出典元を指す行は、許諾の名前も空でなければならない。食い違えば止まる。`got_on` は取得日だが、**この欄は記録するだけで判定には 1 度も使わない**。日付で判定が変わると、同じ表を別の日に通したときに答えが変わってしまうからだ。

配布物の目録には、どの出す先にどの rule を入れるかを 1 行ずつ書く。

```csv
bundle_id,file_name,rule_id,swap,source
B1,合成の配布 A(架空).json,K11,逆順,私の配布のメモ(非公開)L12
B1,合成の配布 A(架空).json,K14,,私の配布のメモ(非公開)L12
B2,合成の配布 B(架空).csv,K31,,私の配布のメモ(非公開)L12
```

出さないと宣言された行や、出す宣言の無い行がここに載っていれば止まる。宣言と目録の食い違いは数える前に出す。

整備の度合いを返す呼び方は無い。返るのは件数と行数と分母だけで、**最後の 11 行は消せない**。`terms` にすると、判定ごとの一覧、**空の欄の名前つき一覧**、登録表に無い許諾の名前を指す行の一覧、出典元の台帳に無い出典元 id を指す行の一覧、目録に載っているのに台帳に無い rule の一覧、**配布物ごとに要る帰属の文字列**が出る。2 つ目の一覧が、そのまま次に埋める欄の名前になる。

最後に、この手続き自体が決定論かどうかを実測する。

```
python share_terms.py verify 行の台帳.csv 許諾の登録表.csv 出典元の台帳.csv 配布物の目録.csv
```

`verify` は 5 つ見る。2 回読んで判定部分のバイト列の指紋が同じか、宣言された入れ替え方で 4 枚の行順を入れ替えても同じ出力になるか、件数の合計が 5 通りとも合うか、そして 2 つの写しだ。**1 欄を空にした写し**では、その行だけが揃っている側から欄が空の側へ移って、空の欄の一覧にその欄名が 1 件現れ、行数がその rule の行数ちょうどだけ移ること。**許諾を 1 件外した写し**では、その名前を指す「出す」の行だけが別枠へ移って、同じ名前を持つ「出さない」の行は動かないこと。写しはメモリの中だけで、入力の表には 1 文字も書かない。

ふたつめが、その 2 通りの内訳になる。欄が空が 3 rule・169 行、名前が登録表に無いが 4 rule・211 行だ。前者は空の欄が名前で出る(5 件)。後者は要求される欄が分からないので、**足りない欄を 1 件も数えない**。ここを同じ列に潰すと、埋める欄が決まっている 169 行と、まだ許諾が決まっていない 211 行が同じ資格で待ち行列に並ぶ。さらに別枠の内訳も 2 通りで、名前の欄が空なのが 3 rule・208 行、書いてあるが登録表に無いのが 1 rule・3 行になる。

みっつめが、出す宣言が無い 2 rule・51 行だ。この行は空の欄の一覧に 1 件も出ない。出すか出さないかが決まっていないので、何を埋めればよいかも決まらないからだ。出さないと宣言された 1 rule・47 行も同じで、混ぜると空の欄が 5 件から 6 件に増える。

よっつめが、2 つの写しの違いになる。帰属の文字列を 1 欄空にすると、その行だけが揃っている側から欄が空の側へ移って、行数は 389 行から 149 行へ、つまりその rule の 240 行ちょうどだけ動く。いっぽう登録表から MIT を外すと、MIT を指す「出す」の 4 rule・196 行が別枠へ移って、**同じ MIT を指す「出さない」の行は動かない**。宣言を先に見ていることが、ここで数として出る。

いつも成り立つことは 1 文にして、性質テストで確かめている。読んだ範囲は 2 通りしかない。rule 1 件ごとに 5 値のどれか 1 つが付き、5 値の合計が rule の数に等しく、4 値の合計が名前が登録表に在る rule の数に等しく、出典元ごとと数表ごとの内訳の合計も rule の数に等しく、出典元ごとの行数の合計と 5 値ごとの行数の合計がどちらも全体の行数に等しく、揃っている行は要求された欄が 1 つも空でなく、欄が空の行は空の欄が名前つきの一覧に出て、出さないと宣言された行と出す宣言が無い行と別枠の行は空の欄を 1 件も持たず、4 枚の行順を入れ替えても同じバイト列になるか、1 件も数えずに理由コードが返るか、だ。どちらの場合も入力は 1 文字も書き換わらない。出典元を 1 つから 3 つ、許諾の名前が書かれている場所の在る・無いを引き、数表を 1 つから 2 つ、rule を 1 件から 2 件ずつ、3 つの欄をそれぞれ空か埋まっているかから引く。乱数は固定で、毎回同じ 200 通りになる。崩し方は 10 通りで、1 件も数えずに止まる理由コード 10 個に 1 対 1 で対応させた。5 値の分け方はテストの側で別に実装している。2 本目は「出さないと宣言された行と出す宣言が無い行は空の欄を持たない」ことだけを総当たりで見ていて、上限は 300 にしてある。

書いている途中で 1 つ捕まえたのは、性質テストではなく `verify` の側だった。合成した 4 枚で `verify` を 1 回走らせたら、許諾を 1 件外した写しの「合うか」が false で返った。**最初は、外したときに動く行を許諾の名前だけで選んでいた**。同じ MIT を持つ「出さない」の行まで動く側に数えてしまい、件数が 1 件ずれた。実際にはその行は動かない。宣言を先に見ているので、許諾が登録表から消えても出さないままだからだ。動く行を「出すと宣言されている行」に絞り、**同じ名前だが動かない行**を別の欄で数えてから測り直した。**宣言を先に見る道具を、宣言を見ずに試そうとして詰まった形**になる。

## 図 2 宣言が揃っているかを数えるまでの流れと、止まる場所

![4 枚の表を読み、出典と形と宣言どうしの食い違いを見て、外に出す宣言で先に分け、許諾を引き当てて要求された欄が空かを 1 つずつ見て、5 値に分けて検算するまでの流れ図](figures/share_terms_flow.png)

段は 7 つで、橙のピルが関所になる。前の 3 段は数える前の検査で、表の形と出典、宣言どうしの食い違いを見ている。

この図で見てほしいのは、描かれていない経路のほうだ。**出典元から「たぶんこの許諾」へ出る矢印が無い。** 規約の原文へ取りに行く矢印も、帰属の文字列を組み立てる矢印も、欄が空と宣言が無いを 1 つの箱に合流させる矢印も無い。出さないと宣言された行から足りない欄へ合流する矢印も、別枠から「理由」へ出る矢印も、件数から「割合」や「順位」へ出る矢印も、行を引く矢印も、ファイルを配る矢印も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

4 段目と 5 段目が本体になる。4 段目で外に出す宣言を見て先に分ける。`出さない` は別の値へ、空は別の値へ。どちらも要求される欄を見に行かない。残るのは `出す` と書かれた行だけだ。5 段目で許諾の名前を登録表に当てる。無い名前と空欄は別枠へ。当たった行だけが、要求される欄の一覧を宣言から受け取る。

6 段目で、要求された欄が空かを 1 つずつ見る。全部埋まっていれば揃っている、1 つでも空なら欄が空で、**足りない欄の名前を残す**。要求が 0 個の許諾なら、欄が全部空でも揃っていると出る。7 段目で検算する。5 値の合計、4 値の合計、内訳の合計、行数の合計。5 通りの数え方を別の経路で持っていて、どれか 1 つを差し替えると合わなくなる。

最後に、この図の関所がぜんぶこの部品自身の話であることを書いておく。**4 枚のどれかが 1 行でも壊れていたら、どの rule も数えない。** 5 値は全て 0、空の欄も 0 件になって、理由コードだけが返る。相手の「欄が空」に、この部品の「読めない」を混ぜないためだ。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/share_terms) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。取得日の検査も日付の型を使わず、年月日の文字列の形だけを見ている。時計を読む呼び出しを 1 つも持ち込まないためだ。

手元で書くのは 4 枚だけで、重いのは許諾の登録表になる。といっても行数は許諾の種類の数しかない。重いのは行数ではなく、**どの規約が当たるかを決めること**と、**その規約が何を要求すると読めるかを書くこと**で、そこは人の仕事として道具の外に残してある。道具が見るのは、宣言の出典の欄が埋まっているかまでだ。

合成した表が置き場に入っているので、同じ数字が手元で出るかを確かめられる。**実在の料率も金額も 1 つも入っていない。** 数表 id も rule id も出典元 id も出す先 id も架空だ。許諾の名前だけは、名前の形が分からないと読めないので `MIT` と `公共データ利用規約` を置き、3 つ目は架空の名前にした。写したのは形だけで、名前が書かれている出どころと書かれていない出どころが混ざること、出すと宣言されたのに欄が空の行が在ること、出さないと宣言された行が在ること、出すとも出さないとも書かれていない行が在ること、要求される欄が 0 個の許諾が在ること、逆向きの欠けが 2 種とも在ること、同じ帰属の文字列を 2 つの rule が持つ配布物が在ること、の 7 つになる。

使い方として想定しているのは、何かを外に出す前に 1 回通すことだ。出てきた空の欄の一覧が、そのまま埋める欄の名前になる。別枠が出たら、どの許諾が当たるかを決める番になる。**整備が何割済んだかは出ない。出るのは件数と行数と欄の名前だけだ。**

## 別の業種なら

この部品が持っている欄は、数表 id・rule id・行数・出典元 id・許諾の名前・帰属の文字列・原文の URL・版の指紋・外に出す宣言・出典だけで、給与や社会保険の言葉は 1 つも入っていない。どの分野でも「手元では引けるが、配るときは出どころごとに条件が違う表」の形は同じだと考えている。会計なら、勘定科目と税区分の表に、自分で作った行・会計ソフトの初期設定から写した行・公的な公表物から取った行が混ざり、社外に配る雛形に全部入れると行ごとに条件が違うまま出る。買い物の仕組みなら、送料表に運送会社の公表運賃から取った行と自分の取り決めの行。医療や介護なら、点数・単価の表に公的な公表分と団体の資料から写した分。建設なら、単価表に公表された労務単価と見積から写した行。製造なら、部品表に規格由来の行と取引先の資料由来の行。私が測ったのは上の合成した 4 枚の範囲だけなので、ほかの分野は同じ詰まり方になりそうな例であって実測ではない。変わるのは表に書く中身だけになる。

## できないこと

- **配ってよいかは分からない。** この部品が返すのは宣言が揃っているかだけで、どの規約が当たるか、その規約の下で配れるかは人が決める。終了コード 0 も「手元の 4 枚に欠けが無い」であって、配布の許可ではない
- **許諾が要求する欄を、この部品は知らない。** 登録表に書かれた宣言を読むだけなので、宣言そのものが間違っていれば結果も間違う。宣言の出典を書かせるのはそのためだが、**この部品は出典の欄が埋まっていることまでしか見ない**(その行に本当にそう書いてあるかは人が読む)
- **要求される欄は 3 つに固定。** 帰属の文字列・原文の URL・版の指紋の外を要求する許諾は、この部品では表せない。増やす経路を入力側に持たせていない
- **帰属の文字列の中身は見ない。** 空かどうかだけを見るので、文面が許諾の求める形かは分からない。文面を作る経路も持たない
- **名前が書かれていない理由は分からない。** 未調査なのか調べた上で無いのかを分けないので、理由は読む人が書く
- **取得日より後に規約が変わっても気づかない。** 規約の原文を取りに行かないので、登録表の宣言が古いままなら古いまま数える
- 図 1 の形は、手元の 3 つのファイルと公開している repo の README の範囲を拾ったもので、各出どころの規約の本文は 1 つも読んでいない。私の環境での話であって、ほかの人の台帳が同じ形だとは言えない
- 上の件数は合成した 4 枚の表に対する測定で、他の人の環境で同じ数字になるとは限らない
