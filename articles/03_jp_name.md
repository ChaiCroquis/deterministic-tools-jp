2 つの名簿を突き合わせて「同じ人」を見つける作業は、どこかで必ず「似ているから同じ人だろう」という判断に行き着く。その判断を機械に任せると、間違いが静かに混ざる。この記事では、表記を決定論で寄せて照合キーを作るところまでを機械の仕事とし、同一人物かどうかの判断は理由コードを付けて人に返す部品を 1 か所にまとめる。類似度のしきい値は 1 つも持たせない。

**なぜ重要か**: 名寄せの失敗は、文字コードや和暦の失敗と違って音を立てない。読めなかった日付は例外で止まるが、別人に寄った 1 行は「処理できた 1 行」として後ろへ流れていく。給与や社会保険の突合でこれが起きると、別の人の金額や資格情報を、正しく処理された行として扱い続けることになる。しかも名寄せは「9 割当たれば上出来」という空気で語られやすく、外れた 1 割がどこに行ったかは記録されない。私の記録では、氏名を寄せるコードが 8 か所以上に別々に書かれていて、異体字の表も、空白の扱いも、少しずつ違っていた。同じ 2 つの名簿を別の道具に通すと、別の結果が出る状態だった。

**要点**:
- 機械が決めるのは「照合キーが一致するか」だけにする。同一人物かどうかは決めない
- 寄せてよい範囲は同値表に書いてあるものだけ。表に無い組(斉 と 斎)は別のキーのままにする
- キーが自分側でも相手側でも一意でなければ、相手が 1 件でも照合しない
- 判断待ちには理由コードと候補が付く。人が見る行が、名簿全体から数えられる行数まで絞られる

**数字で見る**: 合成した 1,000 人ぶんの名簿 2 つで、文字列の完全一致で決まったのは 187 件、うち 13 件は別人に当たっていた。類似度 0.8 以上を同じ人として自動採用すると 793 件が決まり、そのうち 116 件が別人だった。この道具は 865 件を照合し、別人への結合は 0 件、残り 135 件を理由コード付きで判断待ちにした。

---

## 何を解決するのか

名簿の氏名は、同じ人でも書き方が揃わない。給与ソフトの社員名簿は「渡辺　太郎」と全角空白で出てくる。社会保険の手続きに使う側は「渡邊太郎」と異体字で、区切りが無い。銀行口座の名義欄は「ﾜﾀﾅﾍﾞ ﾀﾛｳ」の半角カナで、勤怠システムは「わたなべ たろう」のひらがなだ。同じ列の中で、旧姓を括弧で併記した行が混ざることもある。

この 4 つの表記は、文字列としては全部違う。だから完全一致で突き合わせると、ほとんどの行が「相手なし」として残る。そこで多くの道具は次の一手として類似度を持ち出す。2 つの文字列がどれくらい似ているかを数値で出し、しきい値を超えたら同じ人として採用する。この一手が、静かな間違いの入口になる。

類似度が危ないのは、当たらないからではない。よく当たるからだ。表記の揺れは 1 字か 2 字の差なので、類似度は高く出る。同時に、同姓同名の別人や、同じ姓の別の人も高く出る。「渡辺 太郎」と「渡辺 次郎」は 1 字しか違わない。しきい値は、この 2 種類の「似ている」を区別できない。合成データで試すと、0.8 のしきい値で自動採用した 793 件のうち 116 件が別人だった。採用された行は全部「決まった行」として扱われるので、この 116 件はどこにも記録されずに下流へ流れる。

完全一致なら安全かというと、そうでもない。同じ合成データで完全一致だけを使うと 187 件が決まり、そのうち 13 件は別人に当たっていた。同姓同名の別人が「そのまま」の表記で相手側に残り、本人の表記だけが揺れていた行だ。完全一致は「表記が同じ」を見ているだけで、「その名前が 1 人を指すか」を見ていない。

だから私は、道具の役割をここで切った。表記を寄せるのは機械の仕事にする。寄せた結果キーが一致するかを見るのも機械の仕事にする。そのキーの一致が同一人物を意味するかは、機械の仕事にしない。決めない代わりに、決められなかった理由をコードにして返す。

## 図 1 入力の種類ごとに、どこまで機械が決め、どこから人に返すか

![入力の種類 × 突合の仕方 — どこまで機械が決め、どこから人に返すか](figures/jp_name_cases.png)

左の列が素朴な突合(完全一致で外れたら類似度で自動採用)、右の列がこの道具だ。上の 5 行は表記の揺れで、ここは決定論で寄る。機械が決めてよい領域なので、全部寄せる。下の 3 行は寄せてはいけないもので、素朴な突合はここで静かに間違える。この道具は同じ 3 行を判断待ちに落とす。左右の違いは精度ではなく、決める範囲をどこで切るかだ。

## 手順

最初に決めるのは「照合キー」の作り方で、これが正本になる。段は 2 つしかない。

表記の正規化では、NFKC で全角を半角に、半角カナを全角カナに寄せ、空白と区切りを落とす。これで「渡辺　太郎」「渡辺・太郎」「渡辺太郎」が同じ形になる。姓と名の切り分けはしない。「渡辺太郎」を姓と名に割るには、どこまでが姓かを推測することになり、推測を入れた時点で決定論ではなくなる。空白を落としてしまえば、切り分けなしで揃う。

異体字の同値化は、同値表で代表字に畳む。表はこれだけだ。

| 代表字 | 同じ組にある字 |
|---|---|
| 辺 | 邊 邉 |
| 斉 | 齊 |
| 斎 | 齋 |
| 高 | 髙 |
| 崎 | 﨑 |
| 沢 | 澤 |
| 浜 | 濱 濵 |
| 島 | 嶋 嶌 |
| 吉 | つちよし |
| 富 | 冨 |
| 徳 | 德 |
| 国 | 國 |
| 広 | 廣 |
| 郎 | 郞 |
| 竜 | 龍 |
| 真 | 眞 |
| 恵 | 惠 |
| 瀬 | 瀨 |
| 柳 | 栁 |
| 桧 | 檜 |
| 亀 | 龜 |
| 増 | 增 |

22 組ある。ここで大事なのは、表に無い組は畳まれないということだ。斉 と 斎 は別の字なので、同じ組に入れていない。つまり「斉藤」と「斎藤」は別のキーになり、突き合わせると判断待ちになる。これは取りこぼしではなく、この表が置いている判断だ。同じように、井ノ口 と 井之口 も畳まない。表を 1 組増やすことは、それ自体が「この 2 つは同じ家名として扱ってよい」という判断なので、増やすときはテストを足す。

漢字と読み(カナ)も畳まない。この部品は読みを持っていないので、「渡辺 太郎」と「ワタナベ タロウ」を結び付ける根拠が無い。根拠が無いものを寄せないのが、この道具の一貫した態度だ。

```python
VARIANT_GROUPS = (
    ("辺", "邊", "邉"),
    ("斉", "齊"),
    ("斎", "齋"),      # 斉 の組とは別。斉藤 と 斎藤 は畳まない
    ("高", "髙"),
    ...
)
_VARIANT_MAP = {ord(v): g[0] for g in VARIANT_GROUPS for v in g[1:]}
_KANA_MAP = {c: c + 0x60 for c in range(0x3041, 0x3097)}      # ひらがな → カタカナ

def normalize(text: str) -> str:
    """NFKC で全角 → 半角・半角カナ → 全角カナに寄せ、空白と区切りを除く。"""
    return _DROP.sub("", unicodedata.normalize("NFKC", text))

def to_key(text: str) -> str:
    """照合キー。異体字を代表字に畳み、ひらがなをカタカナに寄せる。"""
    s = normalize(text)
    return s.translate(_VARIANT_MAP).translate(_KANA_MAP)
```

キーができたら、あとは引くだけだ。ここに判断は入れない。入るのは件数の判定だけで、件数で決まらないものは全部人に返す。

```python
def match(name, index, self_index=None):
    reason = scope_reason(name)          # 旧姓・通称の併記 / 3 語以上 / 空の氏名
    key = to_key(name)
    if reason:
        return Decision(name, key, PENDING, reason, ())
    if self_index is not None and len(self_index.get(key, ())) >= 2:
        return Decision(name, key, PENDING, "自分側が重複", self_index[key])
    hits = index.get(key, ())
    if not hits:
        return Decision(name, key, PENDING, "相手なし", ())
    if len(hits) >= 2:
        return Decision(name, key, PENDING, "相手が複数", hits)
    return Decision(name, key, OK, "", hits)
```

判断待ちの理由は 5 つある。どれも「機械では決まらない理由」の名前になっている。

| 理由コード | 意味 |
|---|---|
| 空の氏名 | 氏名が空、または記号だけで照合キーが作れない |
| 対象外表記 | 旧姓・通称の併記、または 3 語以上(ミドルネーム)。畳まずに人へ返す |
| 相手なし | 同じキーの相手がいない。別表記・未登録・別人のどれかは機械では決まらない |
| 相手が複数 | 同じキーの相手が 2 件以上ある(同姓同名の可能性) |
| 自分側が重複 | 同じキーの行が自分側にも 2 件以上ある。キーが人を一意に指さない |

最後の「自分側が重複」が、この道具でいちばん手加減しないところだ。左の名簿に同姓同名が 2 人いるとき、右の名簿に同じ名前が 1 件しか無ければ、キーの照合としては一意に当たってしまう。当たるが、それは「2 人のうちどちらか」でしかない。だから相手が 1 件でも照合しない。キーが人を一意に指していない時点で、キーは答えを出せる立場にない。

コマンドラインからも使える。判断待ちが 1 件でもあれば終了コード 3 になるので、バッチの中に置いて止められる。

```
python jp_name.py --key 渡邊太郎 ﾜﾀﾅﾍﾞ ﾊﾅｺ      # 表記 TAB 照合キー
python jp_name.py A.csv B.csv --column 氏名     # A の各行を B に当てる。判断待ちがあれば exit 3
```

```python
from jp_name import to_key, build_index, match, match_all

to_key("渡邊 太郎")          # '渡辺太郎'
to_key("ﾜﾀﾅﾍﾞ ﾊﾅｺ")         # 'ワタナベハナコ'

for d in match_all(左の名簿, 右の名簿):
    if d.status == "判断待ち":
        print(d.name, d.reason, d.note, d.candidates)   # 人が見る行だけが残る
```

返ってくるのは「照合」か「判断待ち + 理由コード + 候補」のどちらかで、確率もスコアも返さない。返さないことに意味がある。スコアを返せば、受け取った側はいつか必ずしきい値を書く。

## 検証

テストは 59 件。fixture は合成データで、氏名は架空のものだ。実行結果をそのまま載せる。

```
$ python -m pytest tools/jp_name -q

```

内訳は次のとおり。

| 入力 | 期待 | 結果 |
|---|---|---|
| 全角空白 / 中黒 / コンマ / 区切り無し | 同じキー | 一致 |
| 半角カナ / ひらがな / 全角カナ | 同じキー | 一致 |
| 異体字(渡辺・渡邊・渡邉、高・髙、崎・﨑、沢・澤、富・冨) | 同じキー | 一致 |

| 旧姓・通称の併記 / 3 語以上 / 空の氏名 | 対象外表記・空の氏名で判断待ち | 一致 |

| 合成した 2 つの名簿(19 行と 15 行) | 各行の期待どおり | 一致 |
| CLI: 照合キー / 突合 / 終了コード 3 / 列が無いとき | それぞれ | 一致 |

計測のテストも同じファイルにある。固定した乱数の種で名簿 2 つを合成する。作り方は次のように決め打ちにしてある。左は 1,000 行で、970 通りの姓名のうち 30 通りは同姓同名の別人が 2 行ずつ(合わせて 60 行)、さらに 20 行は旧姓を括弧で併記した形にする。右は左の 1,000 人から 40 人を落とし、右にだけいる同姓同名の別人を 15 行足して 975 行にする。右の表記は、そのまま / 区切り無し / 全角空白 / 異体字 / 中黒 の 5 種類に散らす。

```
[measure] exact string match: 187/1000 matched, wrong 13
[measure] similarity >= 0.8 auto-adopt: 793/1000 adopted, different person 116
[measure] this tool: matched 865/1000, wrong 0, pending 135 {'自分側が重複': 60, '相手が複数': 15, '相手なし': 40, '対象外表記': 20}
[measure] kana 3 notations x 1000: same key 1000/1000
```

1 行目が完全一致だけの突合で、決まったのは 187 件、そのうち 13 件は別人に当たっている。2 行目が類似度 0.8 以上の自動採用で、793 件が決まり、116 件が別人だった。決まった件数は 4 倍以上に増えるが、増えた分に間違いが混ざっていて、出力を見ても区別が付かない。

3 行目がこの道具だ。865 件を照合し、そのうち別人に結合したものは 0 件だった。残りの 135 件は判断待ちで、内訳は 自分側が重複 60 件、相手が複数 15 件、相手なし 40 件、対象外表記 20 件になる。この 135 件は、合成のときに仕込んだ数とそのまま一致する。同姓同名にした 60 行、右にだけ同姓同名を置いた 15 行、右から落とした 40 人、旧姓を併記した 20 行だ。言い換えると、この道具が人に返したのは「機械には決められない形にしてある行」だけで、それ以外は取りこぼしていない。

4 行目は、カナの名簿 1,000 件を 全角カナ / ひらがな / 半角カナ の 3 表記に散らしたもので、1,000 件とも 3 表記が同じキーになった。

865 や 116 という数は、合成の仕方(表記の散らし方、同姓同名を何組入れるか)で決まる値で、実際の名簿でこの割合になるという意味ではない。比べているのは割合ではなく、「決まらないものを決めてしまうか、理由を付けて返すか」という性質の違いだと考えている。

## 図 2 名寄せの流れ

![氏名の名寄せの流れ — 文字を寄せるところで止めて人に返す](figures/jp_name_flow.png)

段は 5 つ。表記を正規化する、異体字を畳む、照合キーにする、キーを引く、人に返す。橙のピルが関所で、旧姓や通称の併記はキーを作る前に、相手の件数で決まらないものはキーを引いたあとに、それぞれ判断待ちへ抜ける。抜けた行には理由コードと候補の表記が付くので、人が目で見る対象がその行だけに絞られる。名寄せを速くする道具ではなく、人が見るべき行を数えられる形にする道具だと思っている。

## 道具

[jp_name](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/jp_name) に置いた。`jp_name.py` 1 ファイルと、テスト、合成 fixture の生成スクリプトが入っている。依存は無く、標準ライブラリだけで動く。ライセンスは MIT。

使い方は上の手順のとおり。関数として呼ぶなら `to_key(text)` / `build_index(names)` / `match(name, index, self_index)` / `match_all(left, right)`、コマンドラインなら `python jp_name.py --key 氏名` か、CSV を 2 つ渡して突合。fixture を作り直したいときは `python fixtures/make_fixtures.py`。同値表を自分の名簿に合わせたいときは `VARIANT_GROUPS` に組を足して、テストを 1 つ足す。

## 別の業種なら

この部品は、給与や社会保険の語彙を 1 つも持っていない。持っているのは文字の同値表と、件数の判定だけだ。会計の取引先マスタ、EC の顧客名簿、医療・介護の利用者名簿、学校の名簿でも、同じ人が別表記で二重に登録され、突合のたびに誰かが目で見て寄せている形は同じだと考えている。私が実測したのは給与まわりの社員名簿と、上の合成データだけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。変わるのは入力の CSV の列名だけで、部品そのものは書き換えずに持ち出せる。たとえば取引先マスタなら「取引先コード,取引先名,登録日」の取引先名を `--column` で指すところが、上の社員名簿と同じ扱いになる。法人名には法人格(株式会社・(株))という別の正規化が要るので、そこは別の部品になる。

## できないこと

- 同一人物かどうかは決めない。決めるのは「照合キーが一致するか」だけで、判断待ちの行を人が見る前提の部品だ。人手を減らす道具ではなく、人が見る行を絞る道具になる
- 読み(ふりがな)を持っていないので、漢字表記とカナ表記は結び付かない。読みの列がある名簿なら、読みを別のキーとして併用するのが早い
- 旧姓・通称・ミドルネームは対象外表記として判断待ちに落とす。どちらが現姓かは名簿の外にある情報で、機械では決まらない
- 同値表は 22 組しか持っていない。手元の名簿に出る異体字が足りなければ足すことになるが、足すこと自体が判断になる
- 島 と 嶋、浜 と 濱 を畳むのは、この表が置いている判断だ。別の家として扱いたい名簿では、その組を外してテストを直す
- ローマ字表記の大文字小文字は畳まない。姓名の順序も判定しない。敬称や役職が付いた列は、先に切り落としてから通す
- 上の数字は合成データと私の環境での実測で、他の人の環境で同じになるとは限らない。特に 187 と 793 と 116 は、合成の仕方で変わる
