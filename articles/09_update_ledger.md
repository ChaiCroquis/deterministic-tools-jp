前の 2 本で、毎年変わる数表を行で持ち、数式も行に置いた。どちらも表を**引くとき**の話だった。今回は**書き換えるとき**の話になる。表そのものは毎年書き換わる。書き換えを手作業や、取得したファイルを読ませた要約で回すと、いつ何が変わったかが後から数えられず、間違いが混ざった回を特定できない。この記事では、更新 1 回を台帳の 1 行にして、検査に落ちた回は本番ファイルを触らない部品を作る。

**なぜ重要か**: 引き当ての仕組みをどれだけ固めても、その下にある表は毎年書き換わる。書き換えの作業には、値を直すのと同時に「前の行を閉じる」「公表時点を入れる」「経過措置の行を足す」といった、表の形を保つための操作が混ざる。ここで 1 か所を書き忘れても、表は読める形のまま残り、引き当ては何かを返し続ける。しかも更新の記録が本番ファイルの上書きだけだと、あとから「どの回で入った間違いか」を絞れない。だから更新のほうにも、引き当てと同じ性質が要る。決まらないときに進まないことと、決まったときに何を根拠にしたかが残ることだ。

**要点**:
- 更新 1 回を台帳 1 行にする。通った回も止まった回も必ず 1 行残り、行の書き換えと削除はしない
- 差分は 6 種に分けて数え、丸めない。1 つの行が 2 つの側面で同時に動くので、動いた行数は別の列に持つ
- 検査に落ちた回は本番ファイルを書き換えない。前の回の sha256 がそのまま次の行に繋がる
- 台帳そのものを自己検査できる。鎖・実行時刻・件数の積み上げが合わなければ理由コードで止まる

**数字で見る**: 合成の表で更新を 20 回流したところ、関所で止まったのは 6 回で、その 6 回は本番ファイルの sha256 が 1 度も動かなかった。出来上がった台帳を 1 か所ずつ書き換えた 13 通りのうち 12 通りは自己検査が止め、止められなかったのは先頭の行を消した 1 通りだった。

## 何を解決するのか

まず、これが私の手元で起きている形だという前提のほうから書く。

私の道具の棚卸しでは、履歴の扱いで詰まった道具が 27 本あった。そのうち料率・最低賃金・等級表を「適用開始日つきの履歴」で持つ共通の表は、配布できそうなものの 4 番目に挙げてあって、そこに「毎年の更新運用が要る点が要判断」と自分で書き残していた。つまり、表を作るところまでは道具になっているが、毎年書き換える作業のほうは道具になっていない、という状態だった。

その表を作り直して、いまは 1,681 行、45 種類のルールが入っている。更新は無人で回す手順にしてあり、台帳には 11 回ぶんの実行が残っている。この記事は、その 11 行を読み直すところから始まった。読み直して 4 つのことが分かった。以下は一般論ではなく、自分の台帳 1 本を見た話になる。

**失敗した回は、何を変えようとした回だったのかが残っていない。** 11 回のうち 2 回は、わざと壊した値を流して本番ファイルが書き換わらないことを見るための失敗試験だ。この 2 行は差分の欄が空になっている。止まったこと自体は残っているが、その回が何行を足そうとしていたのかは行から読めない。止まった回こそ中身を知りたいのに、そこだけ抜けている。

**前の回の sha256 が行に無いので、鎖として辿れない。** 5 回目で本番ファイルの sha256 が動き、6 回目でまた別の値になったのだが、6 回目の値は 1 回目・2 回目と同じ値だった。足した行を戻したのだから当然といえば当然で、実際そうなのだが、**それは私が経緯を覚えているから言えることで、台帳の行からは決まらない**。各行が「この回のあとの sha256」しか持っていないと、戻したのか、たまたま同じ内容になったのかを区別できない。

**同じ実行時刻の行が 2 つある。** 2 回目と 3 回目は秒まで同じ時刻で記録されている。連続で流したので当たり前なのだが、この 2 行だけは、どちらが先かが台帳からは決まらない。1 行 1 件の一覧として使うつもりの台帳で、順序が決まらない箇所があるのは具合が悪い。

**差分 0 と記録されているのに本番ファイルが動いた行が 1 行ある。** 10 回目は追加も削除も変更も 0 なのに、sha256 が 9 回目と違っている。行の数え方に入らない部分(並び順や添え物の欄)が動いたのだと思うが、そう書いてある行は無い。差分の件数と本番ファイルの変化が食い違う回があると、件数のほうを信じてよいのかが分からなくなる。

一方で、台帳が一覧として使えている部分もあった。11 行の追加と削除を先頭から順に積み上げると 1,301 行、1,302 行、1,301 行、1,501 行、1,681 行と動いて、最後は私が別に書いてある行数と一致した。件数を残しておけば行数は再構成できる。足りないのは、**その再構成が合っているかを機械が確かめる仕組み**のほうだった。

### 足すのは列で、経路ではない

直し方は、更新の手順にチェックを足していくことではない。手順に足したチェックは、手順を書き直したときに一緒に消える。足すのは台帳の行の列だ。

| 足す列 | その行が言えるようになること |
|---|---|
| 差分 6 種の件数 | この回が何を何件動かしたか。止まった回も数えて残す |
| 動いた行数 | 何行が動いたか。件数の合計とは別の数になる |
| 入力の指紋 | 何を取得した回か(ファイルごとの sha256 と取得時刻) |
| 前の回の sha256 | 本番ファイルが前の行から繋がっているか |
| 判定と理由コード | 通ったのか、どこで止まったのか |

そして、検査に落ちた回は本番ファイルを書き換えない。これがこの部品でいちばん大事なところだと考えている。更新の手順に「失敗したら前のを使う」と書いてあっても、本番ファイルを先に開いてから検査していれば、途中まで書いたファイルが残る。だから順番を逆にして、全部の検査を通った回だけ、しかも呼ぶ側が差し替えを明示した回だけ書く。

### 差分 6 種と、識別の決め方

差分を数えるには、前回の行と今回の行を突き合わせる鍵が要る。この部品では、その鍵を `key`(何を求めるか)と対象セグメントと有効開始日と公表開始日、それに順位の 5 つにした。前回の記事で作った行の形のうち、行を特定する側の列を全部使っている。

**順位まで鍵に入れてあるのは、同じ有効期間・同じ公表時点で本則と経過措置が並ぶ表が実際にあるからだ。** 順位を入れないと、その 2 行が同じ鍵になる。同じ鍵の行が 2 つあると、どちらとどちらを突き合わせたかで差分の種類が変わり、数えるたびに件数が変わりうる。

鍵が同じ行どうしを比べて、動いた列から種を決める。

| 種 | 何が動いたら数えるか |
|---|---|
| 追加 | 今回だけにある鍵 |
| 削除 | 前回だけにある鍵 |
| 値の変更 | 値の列。下の 3 種に入らない列が動いた場合もここに数える |
| 有効期間の変更 | 終了日の列。開いていた行を閉じた、期限を延ばした |
| 公表時点の変更 | 知識の終了日と、公表日が実値か仮置きかの列 |
| 出典欄の変更 | 出典・出典 URL・備考の列 |

分類の決まっていない列が動いたときに値の変更へ数えるのは、引き当ての答えを変えるかもしれない側へ寄せておくためだ。出典欄の変更に混ぜてしまうと、答えが変わる書き換えが「出典を直しただけ」の件数に紛れる。

もう 1 つ、**6 種の件数を足した数は、動いた行数と一致しない**。1 つの行が値と出典の両方で動けば、件数は 2 つ、動いた行は 1 行になる。どちらも要るので、台帳には両方を別の列で持たせた。一致しないほうが自然なので、一致させるために片方を丸めたりはしない。

## 手順

台帳は 1 行 1 件の JSONL で、追記だけする。1 行にはこれだけ入っている。

| 列 | 意味 |
|---|---|
| `run_at` | 実行時刻。同じ値の行は 2 つ作れない |
| `inputs` | 取得したファイルごとの指紋(名前・sha256・取得時刻) |
| `counts` | 差分 6 種の件数 |
| `changed` | 動いた行数 |
| `rows_prev` / `rows_now` | 前回と今回の行数 |
| `status` / `reason` / `detail` | 通ったか止まったかと、理由コード |
| `findings_total` / `findings` | 表そのものの検査で見つかった不備の数と見本 |
| `samples` | 差分の見本 |
| `applied` | 本番ファイルを差し替えたか |
| `sha256` / `prev_sha256` | この回のあと / 前の本番ファイルの sha256 |

呼び方は 4 つで、記録・一覧・再構成・表の検査になる。

```
python update_ledger.py record --ledger 台帳.jsonl --now 今回.csv --prev 前回.csv \
       --output 本番.json --input 料率表=取得した.xlsx --run-at 2026-09-21T09:00:00+00:00 --apply
python update_ledger.py inventory --ledger 台帳.jsonl
python update_ledger.py replay --ledger 台帳.jsonl --at 2026-09-21T12:00:00+00:00
python update_ledger.py validate 今回.csv
```

初回は前回の表が無いので、全部が追加になる。

```
$ python update_ledger.py record --ledger 台帳.jsonl --now 前回.csv --output 本番.json \
    --input 料率表=取得した.txt --run-at 2026-09-21T09:00:00+00:00 --apply
{"run_at": "2026-09-21T09:00:00+00:00", "status": "ok", "reason": "",
 "inputs": [{"name": "料率表", "sha256": "b94aee226a75...", "fetched_at": "2026-09-30T00:29:00+00:00"}],
 "first_run": true, "rows_prev": 0, "rows_now": 43, "changed": 0,
 "counts": {"追加": 43, "削除": 0, "値の変更": 0, "有効期間の変更": 0, "公表時点の変更": 0, "出典欄の変更": 0},
 "applied": true, "sha256": "49b06b27f6d5...", "prev_sha256": ""}
```

2 回目は前回の表と突き合わせて、6 種に分かれる。

```
$ python update_ledger.py record --ledger 台帳.jsonl --now 今回.csv --prev 本番.json \
    --output 本番.json --input 料率表=取得した.txt --run-at 2026-09-22T09:00:00+00:00 --apply
{"status": "ok", "rows_prev": 43, "rows_now": 47, "changed": 15,
 "counts": {"追加": 6, "削除": 2, "値の変更": 5, "有効期間の変更": 5, "公表時点の変更": 1, "出典欄の変更": 6},
 "samples": [{"kind": "値の変更/出典欄の変更",
              "identity": "key=料率_甲 valid_from=2024-03-01 known_from=2024-02-01 priority=0 地域I",
              "old": "9.90", "new": "9.92"}, ...],
 "applied": true, "sha256": "32745c2e2aba...", "prev_sha256": "49b06b27f6d5..."}
```

値の変更から出典欄の変更までの 4 種を足すと 17 件だが、動いた行は 15 行になっている。値と出典が同時に動いた行が 2 行あるからだ。

期間が重なる行を含む表を流すと止まる。このとき本番ファイルは開かない。

```
$ python update_ledger.py record --ledger 台帳.jsonl --now 重なる表.csv --prev 本番.json \
    --output 本番.json --input 料率表=取得した.txt --run-at 2026-09-23T09:00:00+00:00 --apply
{"status": "failed", "reason": "有効期間の重なり",
 "detail": "有効期間の重なり が 2 件(料率_甲 行 13/44)",
 "rows_prev": 47, "rows_now": 44, "changed": 15,
 "counts": {"追加": 3, "削除": 6, "値の変更": 5, "有効期間の変更": 5, "公表時点の変更": 1, "出典欄の変更": 6},
 "findings_total": 2, "applied": false,
 "sha256": "32745c2e2aba...", "prev_sha256": "32745c2e2aba..."}
```

止まった行でも差分の件数が残っているところが、自分の台帳から直した点になる。この回が何を入れようとしていたのかが、あとから数えられる。終了コードは 3 で、本番ファイルの sha256 は前の回と同じ値のまま残る。

止まる理由コードは 8 つで、これ以上増やしていない。

| 理由コード | 何が起きたか |
|---|---|
| 有効期間の重なり | 同じ対象・同じ順位で、有効期間も知識の期間も重なる行がある |
| 期間の穴 | 同じ対象・同じ順位で、前の行の終了日と次の行の開始日が離れている |
| 行数の急変 | 行数が前回からしきい値を超えて動いた。取得か抽出の失敗を疑う |
| 指紋が前回と同一なのに差分あり | 取得したファイルは前回と同じなのに行が動いた。入力以外から行が入っている |
| 指紋が違うのに差分 0 | 取得したファイルは変わったのに行が 1 つも動いていない |
| 台帳の鎖が切れている | 前の行の sha256 と今の本番ファイルが繋がらない。台帳を通さない書き換えがあった |
| run_at の重複 | 同じ実行時刻の行がすでにある |
| 入力の列が足りない | 入力が行の表として読めない |

最後から 2 つめだけは扱いが違う。同じ実行時刻で追記すると、その台帳は以後どちらが先か決まらなくなるので、**行を書かずに拒む**。終了コードは 2 になる。

```
$ python update_ledger.py record --ledger 台帳.jsonl --now 今回.csv --prev 本番.json \
    --output 本番.json --run-at 2026-09-23T09:00:00+00:00 --apply
{"ok": false, "error": "run_at の重複: 2026-09-23T09:00:00+00:00 の行はすでにある。
                        追記すると実行の順序が台帳から決まらない"}
```

### 台帳そのものを検査する

台帳を一覧として使うつもりなら、その台帳が一覧として成り立っているかを確かめる手立てが要る。`replay` は先頭から辿って、実行時刻の重複と順序、前の行の sha256 との繋がり、そして件数の積み上げ(前回の行数 + 追加 - 削除 = 今回の行数)を見る。

```
$ python update_ledger.py replay --ledger 台帳.jsonl
{"ok": true, "runs": 3, "rows": 47, "sha256": "32745c2e2aba..."}

$ python update_ledger.py replay --ledger 台帳.jsonl --at 2026-09-21T12:00:00+00:00
{"ok": true, "runs": 1, "rows": 43, "sha256": "49b06b27f6d5..."}
```

時点を渡すと、そこまでの行だけで行数と本番ファイルの sha256 を組み直す。合わない台帳は止まる。

```
$ python update_ledger.py replay --ledger 書き換えた台帳.jsonl
{"ok": false, "reason": "台帳の鎖が切れている",
 "detail": "行 2 の件数が積み上がらない: 43 + 追加 7 - 削除 2 = 48 だが rows_now は 47", "line": 2}
```

関数として呼ぶなら `record` と `read_ledger` と `inventory` と `replay` の 4 つになる。`record` には「決まらなければ最新へ」に相当する引数が無い。差し替えは呼ぶ側が明示した回だけで、既定は差し替えない。これはテストで固定してある。

## 検証

テストは 45 件。fixture は合成データで、地域名も値も出典名も架空だ。実在の料率や限度額は 1 つも入れていない。

```
$ python -m pytest tools/update_ledger -q
45 passed in 2.70s
```

測定は 3 つある。どれも決定論で、乱数を使っていない。

1 つめは差分の数え方だ。合成の 43 行の表を、年度の改定を反映した 47 行の表へ書き換える。書き換えの中身は、新年度の行を足して古い行を閉じる、値だけ直す、出典欄だけ直す、値と出典を同時に直す、公表側の差し替えを入れる、古い行と期限切れの経過措置を消す、の 6 とおりにしてある。

```
[measure] 前回 43 行 → 今回 47 行: 追加 6 / 削除 2 / 値の変更 5 / 有効期間の変更 5 / 公表時点の変更 1 / 出典欄の変更 6
[measure] 動いた行は 15 行、種別の合計は 17 件(2 つの側面が同時に動いた行が 2 行)
```

追加と削除を除いた 4 種の合計が 17 件で、動いた行は 15 行になる。差が 2 行ぶんあるのは、値と出典が同時に動いた行が 2 行あるからだ。ここで固定しているのは件数そのものではなく、**件数の合計と動いた行数が一致しない場面が実際に出る**ことのほうになる。

2 つめは運用の測定だ。合成の表を使って更新を 20 回流す。途中に、期間が重なる表、穴のある表、行数が急に減った表、指紋が前回と同じまま中身が違う回、指紋だけ変わって中身が同じ回、列が足りない表を混ぜてある。

```
[measure] 更新 20 回: 通った 14 回 / 止まった 6 回、本番ファイルの sha が動いた 10 回
[measure] 止まった 6 回で本番ファイルの sha が動いた回数: 0
          (理由コードの内訳 有効期間の重なり / 期間の穴 / 行数の急変 / 指紋が前回と同一なのに差分あり /
           指紋が違うのに差分 0 / 入力の列が足りない)
[measure] 台帳の自己検査: 20 行を辿って行数 47 を再構成
```

止まった 6 回は理由コードが全部違っていて、そのどれでも本番ファイルの sha256 は動かなかった。通った 14 回のうち sha256 が動いたのは 10 回で、残りは同じ内容を書いた回になる。この測定の弱いところは、止まるべき回をこちらで作って流している点だ。現実の更新で何回に 1 回止まるかは、これでは分からない。

3 つめは台帳の自己検査だ。上の 20 行の台帳を、1 か所ずつ書き換えた 13 通りを作って `replay` に流す。行を消す、順序を入れ替える、実行時刻を前の行と同じにする、件数を 1 増やす、行数を 1 増やす、sha256 を書き換える、差し替えたのに差し替えていないことにする、登録していない理由コードにする、指紋を前の行と同じにする、といった書き換えになる。

```
[measure] 台帳を 1 か所ずつ書き換えた 13 通り: 自己検査が止めた 12 通り(止められなかった 1 通り = 先頭の行を消す)
[measure]   台帳の途中の 1 行を消す → 台帳の鎖が切れている
[measure]   run_at を前の行と同じにする → run_at の重複
[measure]   指紋を前の行と同じにする → 指紋が前回と同一なのに差分あり
[measure]   差分 0 の行の指紋だけ変える → 指紋が違うのに差分 0
[measure]   先頭の行を消す →
```

止められなかった 1 通りは正直に書いておきたい。**先頭の行を切り落とされると、台帳の中からは分からない。** 鎖は「前の行の sha256 と繋がるか」で見ているので、いちばん前を消すと比べる相手がいなくなる。これは仕組みの限界で、台帳を置く場所の側(追記しかできない置き場や版管理)で補うことになる。

残りのテストは、8 つの理由コードに全部到達する道があること、同じ期間・同じ公表時点で本則と経過措置が並ぶ表を 2 行として数え分けること、分類の決まっていない列の変化を値の変更に数えること、施行日が政令待ちの行が重なりにも穴にも数えられないこと、差し替えを明示しない回は本番ファイルを触らずに 1 行だけ残すこと、台帳が追記だけで前の行が変わらないこと、同じ表を書けば必ず同じ sha256 になること、終了コードが通ったら 0・理由コードで止まったら 3・台帳や引数が壊れていたら 2 になること、を見ている。合成 fixture が生成器から決定論的に出ることも、ディスク上の CSV と突き合わせて確かめてある。

## 図 2 更新 1 回の流れと、止まる場所

![指紋を取る、差分を数える、表を検査する、台帳に追記する、差し替える、後から辿る、の流れ図](figures/update_ledger_flow.png)

段は 6 つで、橙のピルが関所だ。台帳への追記が差し替えより**前**にあるところを見てほしい。差し替えてから記録すると、差し替えた直後に落ちた場合に記録が残らない。順番を逆にしておけば、止まった回も差し替えた回も同じ 1 行として残る。

この図でも、描かれていない経路のほうが本題になる。どの関所から出ても行き先は理由コードで、「取得できなかったので前回の値を使う」や「検査に落ちたが新しいほうが新しいので入れる」に戻る矢印がどこにも無い。実装でも同じで、記録の関数には受け皿の引数を持たせていない。差し替えの引数も既定は差し替えないほうにしてある。落ちる先が無ければ、落ちる経路も書けない。

## 道具

[update_ledger](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/update_ledger) に置いた。`update_ledger.py` 1 ファイルと、テスト、合成 fixture の生成スクリプトが入っている。依存は無く、標準ライブラリだけで動く。ライセンスは MIT。

入力の表の形は前回・前々回の部品と同じなので、そのまま繋がる。自分の現場に合わせるときに触るのは、行数のしきい値と、指紋を取るファイルの並びだけになる。部品のコードは触らない。差分の 6 種をどの列で分けるかは 1 か所にまとめてあるので、列の名前が違う表ならそこを差し替える。

## 別の業種なら

この部品は、給与や社会保険の語彙をひとつも持っていない。持っているのは行の識別の決め方と、数える 6 種と、止まる理由だけだ。会計の税率表や勘定科目マスタ、EC の送料表と手数料表、医療や介護の点数表、運送の距離運賃表、建設の歩掛りでも、外から配られる表が毎年書き換わり、書き換えた回の記録が残っていない形は同じだと考えている。私が実測したのは上の合成データと、自分の表の更新記録だけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。変わるのは行を識別する列の名前と、指紋を取るファイルの数だけで、部品そのものは書き換えずに持ち出せる。保険料率の表を消費税率の表に替えても、送料表の改定に替えても、部品の側からは同じことになる。実行 1 回 = 台帳 1 行という作りに業種の語彙が入っていないからだ。

## できないこと

- 値そのものの正しさは判定しない。改正の解釈もしない。何行がどう動いたかを数えて残すだけで、間違った値が正しい形で入ってくれば通る
- 台帳の先頭の行を消されると、台帳の中からは分からない。上の測定で止められなかった 1 通りがこれになる。追記しかできない置き場か版管理と組み合わせて補う
- 行数のしきい値(既定は 20%)は表ごとの事情で決める値で、根拠のある数ではない。私の 11 回では最大が 15.4% だったので既定ではどれも止まらないが、これは私の表の話になる
- 上流が中身を変えずに書式だけ変えた回は「指紋が違うのに差分 0」で止まる。止まる側に倒してあるので、そのまま進めたいときは人が見て次の回で通すことになる。手間が増えるほうを選んだ
- 取得そのものに失敗した場合は台帳に行を残さずに終了コード 2 で落ちる。「実行 1 回 = 台帳 1 行」が崩れるのはここだけで、取得の失敗は取得する側の記録に残る
- 台帳は 1 つの本番ファイルにつき 1 本の想定になる。複数の表を 1 本の台帳で混ぜると鎖が繋がらない
- 上の数字は合成データと私の環境での測定で、他の人の表で同じ内訳になるとは限らない。特に差分の件数は、合成の書き換え方をこちらで決めているので、その決め方で変わる値だ
- 11 回という記録は 2026-09-19 の私の手元の実行だけで、そのうち 2 回は意図的な失敗試験だ。網羅でも、長期の運用でもない。週に 1 回動かすスケジュール登録はまだしていないので、無人で回した実績はまだ無い
