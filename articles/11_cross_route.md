前回、配布元の原本から値 1 件を取り出して「ピン 1 行」にする形を作った。ただしピンが言えるのは「原本のこの場所に、この文字で書いてあった」ことまでで、その値そのものが合っているかは原本の中では確かめようがない。確かめたければ、同じ値を別の経路からもう 1 回取って突き合わせることになる。今回はその突き合わせを部品にするのだが、主役は「どちらが正しいか」ではない。

**なぜ重要か**: 2 系統で取った値が食い違ったとき、人は反射的にどちらを正とするかを決めにいく。だが私の記録に残っている食い違いの実例は、値の優劣ではなかった。別の制度の数字を、似た名前で同じ行に並べていただけだった。片方は労使で折半する率、もう片方は事業主だけが負担する率で、名前が近いので同じものに見えていた。ここで「どちらを正とするか」を決める仕組みを先に作っていたら、優先順位の高いほうが勝って、名前の取り違えは表に残ったまま静かに通る。だから部品が先にやるべきなのは、値を比べることではなく、2 つの値が同じものを指しているかどうかを検査することになる。

**要点**:
- 比べる前に「同じものを指しているか」を見る。対象や負担区分の宣言と単位が揃っていない組は、値が一致していても比べない
- 判定は 4 値にする。一致・不一致・片方の経路にしか無い・比べられない。不一致のときにどちらかを正として返す経路を持たない
- 正規化は名前で呼ぶ。名前が空欄の行は比べずに止める。末尾の 0 をそろえることも名前で書かせる
- 一致率は分子と分母だけでは返らない。照合できていない行の件数と、分母に何を含めたかの文字列が必ず一緒に付く

**数字で見る**: 合成の 2 経路(13 行と 14 行)を突き合わせると、名前の和集合 15 のうち一致 7・不一致 1・片系統だけ 3・比べられない 4 になる。比べられた 8 行だけを分母にした一致率は 0.8750、照合できていない 7 行を含めた全 15 行を分母にすると 0.4667 で、同じ突合から 2 つの数字が出る。

---

## 何を解決するのか

私の数表は、いま 1,681 行、45 種類のルールが入っている。前回はこの行を作る工程、つまり原本から値を取り出してピンにする話を書いた。ピンは原本のファイルの指紋と、原本の中の場所と、生の文字を持っていて、使うたびにそこへ突き合わせに行く。だからピンが切れていないことは分かる。

分からないのは、原本に書いてある値が合っているかだ。取り出し方がどれだけ固くても、原本の値そのものが間違っていれば、間違ったまま接地する。これは原本の中では確かめようがない。確かめる手は 1 つしかなくて、同じ値を別の経路からもう 1 回取り、突き合わせることになる。

私の手元で、2 経路あるのはごく一部だった。自分で原本から抽出した料率と、上流の公開データの料率で、全支部ぶんが一致している。限度額のいくつかは、2 か所の公表物から取って一致している。基本的な日額の最低額は、式から計算した値と公表された値が 3 年ぶん一致している。残りは、照合相手の経路がそもそも無い。

### 食い違いは、値の問題ではなかった

その「2 経路ある」部分で、値が食い違ったことが 1 度ある。上流の表に、似た名前の率が 2 つ入っていて、自分の抽出した値と合わなかった。

調べた結果は、どちらも正しかった。片方は新しく始まった制度の率で、労使で折半する。もう片方は事業主だけが負担する率だ。別の制度の数字で、そもそも比べる対象ではなかった。公式の表の見出しを読んで決着した。

ここが今回の出発点になる。**もしこのとき「どちらを正とするか」を決める仕組みが先にあったら、片方が勝って、名前の取り違えは消えていた。** 優先順位が高いほうの値が表に残り、下流はそれを使う。合わない値が出てこなくなったぶん、誰も疑わない。

食い違いを見つける仕組みが、食い違いを消す仕組みになってしまう。これは検算の作り方としてまずい。

### 足すのは列で、優先順位ではない

直し方は、値の優劣を決める仕組みを足さないことだ。足すのは行の列になる。

| 足す列 | その行が言えるようになること |
|---|---|
| 対象の宣言 | その値が何を指しているか。対象の範囲、負担区分など。呼ぶ側が言葉で書く |
| 単位 | 円なのか、円/日なのか、率なのか |
| 正規化の名前 | その経路の値を、比べられる形にどう直したか |
| 出典(両方の経路) | どのファイルから取ったか。指紋も一緒に |

この 4 つが両方の経路に揃って、はじめて「同じものを比べている」と言える。揃っていない組は、値が一致していても比べない。一致していても比べない、という扱いにするところが肝で、たまたま数字が合っている組を「照合できた」に数えないためにこうしてある。

## 図 1 手元の領域ごとに、照合相手の経路が在るか

![領域ごとに、経路が 2 つ在って一致した件数・片系統だけ・比べられない、の 3 列に分けた対応表](figures/cross_route_map.png)

行が手元の領域で、列が照合の状態になる。藍が 2 経路あって一致したところ、橙が照合できていないところと、比べられないところだ。

この図でいちばん見てほしいのは、**藍の列が表の一部しか占めていないこと**だ。私の数表の大半には、照合相手の経路が無い。上流の表だけが出どころの項目は、最低賃金が 1,079 行、業種別の率が 55 業種あり、どれも突き合わせる相手がいない。適用開始日が原本に書かれていない項目は、所定の日数の 39 行と、もう 1 件の仮置きがある。これらは「一致した」でも「一致しなかった」でもなく、**照合していない**。

いちばん下の行が、さっき書いた食い違いの実例になる。2 つの経路に行はあるのだが、指しているものが違うので比べられない。藍でも、不一致でもない、3 つめの箱が要る。

部品のほうでも同じにしてある。突合の表は、照合できていない行を 1 行として必ず出す。一致率を出す呼び出しも、この行数を一緒に返す。

## 手順

経路 1 本の行はこれだけの列を持つ。

| 列 | 中身 |
|---|---|
| `key` | 何の値か。2 経路の突き合わせはこの名前で行う |
| `value` | その経路が出した値 |
| `unit` | 単位。一方でも空欄か、食い違っていれば比べない |
| `scope` | その値が指しているもの。対象の範囲や負担区分を呼ぶ側が言葉で宣言する |
| `source_file` | 出典のファイル |
| `source_sha256` | 出典の指紋。報告に載せるために持つ(現物は見ない) |
| `normalizer` | 値を比べられる形にする正規化の名前 |
| `captured_at` | 取り出した時刻 |
| `raw_text` | 原本にある生の文字。持ち越すだけで、比較には使わない |
| `locator` | 原本の中の場所。持ち越すだけで、比較には使わない |

前回のピン 1 行に、単位と対象の宣言の 2 列を足した形になっている。だからピンの表に 2 列足せば、そのまま経路の表として読める。生の文字と場所は持ち越すだけで、突合には使わない。使ってしまうと、別の原本から取った値は文字が違うので必ず食い違うことになる。

### 比べる順序を固定する

突合の順序は 3 段で、この順を変えない。

まず、両方の行の正規化の名前を通して値を直す。名前が空欄の行は、ここで止まる。次に、対象の宣言と単位が両方あって一致するかを見る。片方でも空欄なら止まるし、違っていても止まる。**値を比べるのは、この 2 段を通った組だけ**になる。

```
python cross_route.py check  route_a.csv route_b.csv --name-a 自前抽出 --name-b 別の経路
python cross_route.py report route_a.csv route_b.csv --format csv
python cross_route.py rate   route_a.csv route_b.csv
python cross_route.py get    route_a.csv route_b.csv 料率_地域I
```

判定は 4 値になる。

| 判定 | 何が起きたか |
|---|---|
| `agree` | 両経路に 1 行ずつあり、指しているものが同じで、正規化後の値が一致した |
| `disagree` | 指しているものは同じだが、正規化後の値が違った |
| `single_route` | 片方の経路にしか無い。照合できていない |
| `incomparable` | 比べられない。対象の宣言や単位が揃っていない、正規化の名前が無い、など |

一致した組を引くと、値と一緒に両方の出典が返る。

```
$ python cross_route.py get route_a.csv route_b.csv 料率_地域I
{"ok": true, "key": "料率_地域I", "value": "9.31", "unit": "%", "scope": "地域I・労使折半",
 "routes": ["自前抽出", "別の経路"],
 "sources": [{"route": "自前抽出", "source_file": "keiro_a_genpon.txt",
              "source_sha256": "95fb49f628997309aefec32af031a997d6869b481c20ea3e1712d427a071304e",
              "normalizer": "パーセント+桁そろえ"},
             {"route": "別の経路", "source_file": "keiro_b_joryu.json",
              "source_sha256": "aaaaa01fb91a1902109e5cbe8296f097bee2c8c92f9e1c900200ef5620e87770",
              "normalizer": "桁そろえ"}]}
```

値が食い違う組を引くと止まる。終了コードは 3 になり、**どちらを正とするかは返さない**。

```
$ python cross_route.py get route_a.csv route_b.csv 上限額_区分B
{"ok": false, "key": "上限額_区分B", "reason": "disagree",
 "detail": "突合を通らない key: 上限額_区分B(disagree)"}
```

引き当てには、優先する経路を選ぶ引数が無い。片方へ落ちる引数も無い。これは関数の引数の形と、CLI の option の集合をテストで固定してある。落ちる先が無ければ、落ちる経路も書けない。

### 値が合っていても、比べないことがある

分かりやすいのが、適用開始日の組だ。片方の経路は和暦混じりの表記、もう片方は年月日を並べた表記で、正規化を通すと同じ日付になる。それでも判定は「比べられない」になる。

```
{"key": "適用開始日_給付日数", "judgment": "incomparable", "reason": "scope 空欄",
 "detail": "経路 別の経路 に scope の宣言が無い"}
```

片方の経路が「この日付が何の適用開始日なのか」を宣言していないので、値が合っていても同じものだとは言えない。前回の仮置きの話と同じ扱いで、**宣言されていないものは、たまたま合っていても照合済みに数えない**。

食い違いの実例のほうは、こう出る。

```
{"key": "支援金率", "judgment": "incomparable", "reason": "scope 不一致",
 "detail": "自前抽出 は '労使折半'、別の経路 は '事業主のみ'"}
```

不一致ではなく、比べられない。人が見るべきなのは値ではなく名前のほうだ、ということが判定から分かる形にしてある。

### 正規化は名前で呼ぶ

正規化は `そのまま` / `全角半角` / `カンマ除去` / `パーセント` / `円` / `桁そろえ` / `日付` の 7 つを登録してあり、`+` でつないで左から順に適用する。前回の部品と同じで、名前が空欄の行は評価せずに止める。

今回ひとつ増やしたのが `桁そろえ` で、末尾の 0 をそろえる。2 経路で桁の書き方が違うのはよくあるのだが、それを部品が黙って同じ扱いにすると、「どこまでを同じとみなしたか」が表から消える。だから名前で書かせる。桁を落とす丸めはしないので、末尾が 0 でない数はそのまま残る。

### 止まる理由コードは 9 つ

| 理由コード | 何が起きたか |
|---|---|
| 経路名が同じ | 2 つの経路に同じ名前が付いている。報告のどちらの列がどの経路か決まらない |
| 同じ key が同じ経路に 2 行 | 片方の経路に同じ名前が 2 行ある。その経路の値が表から決まらない |
| 列が足りない | 経路の行として読めない。必要な列が空、登録されていない正規化の名前 |
| normalizer 空欄 | 正規化の名前が書かれていない。既定を持たないので比べない |
| normalizer を通せない | 名前の正規化が値を扱えない。数として読めない、年月日として読めない |
| scope 空欄 | その値が何を指しているかの宣言が無い。値が合うかより先にここで止める |
| scope 不一致 | 2 経路が別のものを指している。値を比べない |
| unit 不一致 | 単位が違う、または一方が空欄。値を比べない |
| 突合前に get を呼んだ | 突き合わせる前に値を取りに来た |

片方の経路にしか無いことは、理由コードではなく記録として扱う。片系統だけの行があっても突合そのものは通ったことにして、終了コードは 0 になる。前回、取れない原本を異常にしなかったのと同じ理由で、異常にすると照合相手の無い行を表から消す動機が生まれるからだ。

## 検証

テストは 33 件。fixture は合成データで、値も区分名も出典名も架空になっている。実在の料率や限度額や最低賃金は 1 つも入れていない。出典の指紋は合成の原本 3 ファイルの現物から計算しているので、表と出典は内部で噛み合っている。

```
$ python -m pytest tools/cross_route -q
33 passed in 6.64s
```

測定は 3 つある。どれも決定論で、乱数を使っていない。

1 つめは、合成の 2 経路の突合そのものだ。

```
[measure] 合成の 2 経路(経路 A 13 行 / 経路 B 14 行)の key の和集合 15:
          agree 7 / disagree 1 / 片系統だけ 3 / 比べられない 4
[measure]   scope 空欄: 1 件
[measure]   片方の経路にしか無い: 3 件
[measure]   scope 不一致: 1 件
[measure]   unit 不一致: 1 件
[measure]   normalizer 空欄: 1 件
```

ここで固定しているのは一致した件数そのものより、**比べられなかった組が、比べられなかったという形で表に残る**ことのほうになる。4 つの判定の合計は必ず名前の和集合と等しくなるので、どこかに吸収されて消える行は作れない。

2 つめは、2 経路の表を 1 か所ずつ書き換えて、判定が変わるか止まるかを見る測定になる。

```
[measure] 2 経路の表を 1 か所ずつ書き換えた 16 通り: 判定が変わった / 止まった 15 通り
          (変わらなかった 1 通り = 両経路の value を同じように書き換える)
[measure]   経路 A の value を 1 桁変える → disagree
[measure]   経路 B の unit を変える → incomparable: unit 不一致
[measure]   経路 A の scope を空にする → incomparable: scope 空欄
[measure]   経路 B の scope を別の負担区分にする → incomparable: scope 不一致
[measure]   経路 A の normalizer を空にする → incomparable: normalizer 空欄
[measure]   経路 A の normalizer を登録外の名前にする → incomparable: 列が足りない
[measure]   経路 A の normalizer を そのまま に変える → disagree
[measure]   経路 A の value に注記が残る → incomparable: normalizer を通せない
[measure]   経路 A の captured_at を空にする → incomparable: 列が足りない
[measure]   経路 A の source_file を空にする → incomparable: 列が足りない
[measure]   経路 B からその行を消す → single_route: 片方の経路にしか無い
[measure]   経路 A に同じ key の行を 2 行にする → incomparable: 同じ key が同じ経路に 2 行
[measure]   経路名を両方同じにする → 表を読まない: 経路名が同じ
[measure]   両経路の value を同じように書き換える → agree
[measure]   突合前に get を呼ぶ → 止まる: 突合前に get を呼んだ
[measure]   経路 A に key が空の行を足す → incomparable: 列が足りない
```

9 つの理由コードには、この書き換えの集合から全部到達している。

変わらなかった 1 通りは正直に書いておきたい。**両方の経路の値を同じように書き換えると、一致したまま通る。** これは仕掛けの穴というより、2 系統で突き合わせることの限界そのものだ。2 つの経路が同じ原本に由来していれば、原本の側の誤りは 2 系統あっても捕まらない。部品にできるのは、両方の出典を返り値に載せ続けて、同じファイルを指していることが人から見える形にしておくところまでになる。

3 つめは一致率で、分母を 2 つ出す。

```
[measure] 一致率: 比べられた 8 行だけを分母にすると 0.8750、全ての行 15 を分母にすると 0.4667
[measure]   分母に含めたもの: 比べられた行のみ = agree 7 + disagree 1 = 8
            (照合できていない 7 行 = 片系統だけ 3 + 比べられない 4 を除いた分母)
            / 全ての行 = 15(照合できていない 7 行を含む分母)
```

同じ突合から、0.8750 と 0.4667 が出る。前者だけを引用すれば「ほぼ合っている」に見えるし、後者だけを見れば「半分も照合できていない」に見える。どちらも同じデータで、違うのは分母だけだ。だから一致率を返す呼び出しは、片方だけを返す形を持たない。4 つの判定の件数と、分母に何を含めたかの文字列が必ず一緒に返る。

部品には性質テストも付けた。2 経路の表を毎回乱数で作り直し、値を返す条件が崩れていないかを 200 通り見る。もう 1 本は分母の恒等式で、照合できていない行を分母から外した一致率は、全ての行を分母にした一致率を必ず上回るか等しくなる。つまり狭い分母だけを引用すると、一致率は必ず上振れする側に出る。

この測定の弱いところは、合成の 2 経路をこちらで作って並べている点だ。現実にどれくらいの割合が照合できるかは、これでは分からない。分かるのは、照合できていない行を並べたときに表から消えないという、部品の側の性質だけになる。

## 図 2 突合の流れと、止まる場所

![両経路を読む、名前で正規化する、指すものを検査する、値を比べる、4 値で判定する、2 つの分母で出す、の流れ図](figures/cross_route_flow.png)

段は 6 つで、橙のピルが関所だ。3 段めの「指すものを検査する」が 4 段めの「値を比べる」より前にあるところを見てほしい。この並びが今回の全部で、ここを逆にすると、名前の取り違えが「値の不一致」として現れ、どちらかを正とする判断に化ける。

この図でも、描かれていない経路のほうが本題になる。不一致の箱から先へ進む矢印が無い。優先する経路を選ぶ分岐も、片方へ落ちる分岐も無い。実装でも同じで、引き当ての関数にはその引数を持たせていない。

いちばん右の段が「2 つの分母で出す」になっているのも同じ理由だ。照合できていない行を外した一致率だけを出す口があれば、人はそれを引用する。口を作らないほうが早い。

## 道具

[cross_route](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/cross_route) に置いた。`cross_route.py` 1 ファイルと、テスト、合成 fixture の生成スクリプトが入っている。依存は無く、標準ライブラリだけで動く。ライセンスは MIT。

経路の表は CSV でも JSON でもよく、前回のピンの表に 2 列足した形になっている。自分の環境に合わせるときに触るのは、対象の宣言の書き方と、正規化の名前の並びだけだ。部品のコードは触らない。

## 別の業種なら

この部品は、給与や社会保険の語彙をひとつも持っていない。持っているのは、名前と値と単位と、対象の宣言と、正規化の名前と、出典だけだ。会計なら同じ売上を会計の側と販売の側から取って突き合わせる、通販なら在庫を倉庫の側と販売の側から取る、建設なら数量を積算書と現場の日報から取る、医療や介護なら点数を公表物と請求ソフトから取る、という形は同じだと考えている。そして「合わないときにどちらを正とするか」を先に決めたくなる場面であることも、たぶん同じだ。私が実測したのは上の合成データと、自分の表の突合の記録だけなので、他の分野は「同じ詰まり方になりそうな例」であって実測ではない。入力の例を料率の 2 経路から売上の 2 経路に替えても、在庫の 2 経路に替えても、部品の側からは同じことになる。

## できないこと

- 原本が同じなら、2 経路でも原本側の誤りは捕まらない。両方の経路の値を同じように書き換えると一致したまま通る。上の測定で判定が変わらなかった 1 通りがこれになる
- 2 つの経路が本当に独立かは測れない。片方が他方からコピーしたものでも、表の上では 2 経路に見える。同じ出典ファイルを指していることは報告に出るので、そこは人が見ることになる
- 値そのものの正しさは判定しない。どちらの経路が信頼できるかも判定しない。同じものを指しているか、指しているなら合うか、だけを見る
- 対象の宣言は人が書く。書き方が揃っていなければ、同じものでも「指すものが違う」になるし、違うものに同じ宣言を書けば比べてしまう。ここは機械では決まらない
- 出典ファイルの現物や指紋は見ない。列として持ち越して報告に載せるだけで、原本との突き合わせは前回の部品の仕事になる
- 上の数字は合成データでの測定で、他の人の表で同じ内訳になるとは限らない。特に照合できた割合は、こちらで経路を作って並べているので、その作り方で変わる値になる
- 私の手元で 2 経路あるのは一部の領域だけで、網羅ではない。照合できていない領域が多いことは図 1 に出してあるが、その内訳も私の収集範囲の話になる
