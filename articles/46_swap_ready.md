前回は、同じ処理の写しを文字の一致で段に分けた。今回はその手前ではなく、ひとつ先に立つ。寄せた後の部品を、後から別のものに入れ替えるところだ。骨は 1 行で言える。**「ここは入れ替えてよい」と宣言された経路が在っても、入れ替えられる状態かどうかは別で、受け入れ検査が入れ替える側と同じ束に入っている(内蔵)うちは、宣言は使われないまま残る。**

**なぜ重要か**: 私の記録には、許可と、それが止まっている理由が同じ 1 行に書いてある場所がある。作業状況をまとめた記録の 128 行目に「独立 golden (registry の acceptance) | pipeline 内蔵検証のみ、別 golden 未作成 | work-tools 規約 5 の『差し替え』はまだできない」とある。許してよいと決めたのは自分で、できないと書いたのも自分だ。**ここで並んでいる 2 つは、同じ種類の事実ではない。** 前者は宣言で、後者は状態になる。しかも「入れ替わっていない」と「入れ替わった跡を数える欄が無い」も、同じ種類の事実ではない。更新履歴の欄に、どの実装を入れ替えたかを書く列が無ければ、0 回なのか記録していないのかは台帳から言えない。この 3 つを 1 語にまとめて「まだできていない」と呼ぶと、何を足せば入れ替えられるのかが決まらない。

**要点**:
- 入れ替えの経路 1 件を 1 行として、許す宣言・受け入れ検査の所属・跡の欄と件数の 3 つだけで 4 値に分ける。入れ替えるべきかは決めない
- **「入れ替えていない」と「跡を数える欄が無い」を同じ値にしない。** 欄が無い経路には 0 ではなく `数えられない` を返す
- **独立と書いただけでは独立にしない。** 検査が在る束の名前を書かせ、入れ替える側の束と同じ名前なら矛盾する宣言として別枠へ出す
- **滞留の理由を推定しない。** 理由は入力の注記を出典ごと写すだけで、書かれていない経路には `理由の記載なし` を入れる

**数字で見る**: 合成した 5 枚(経路 14 行 / 受け入れ検査 10 行 / 跡 7 行 / 記号の登録表 4 行と 3 行)を通すと、**経路 14 件が 4 値 7 件と別枠 7 件に分かれ、許す側の宣言が在る 11 件のうち「使われている」は 2 件**になる。私の記録から起こした 6 経路のほうでは、許す側の宣言が在る 5 件のうち使われているのが 1 件だった。

## 何を解決するのか

### 許可と、それが止まっている理由が同じ行に書いてある

さっきの 128 行目をもう一度見る。表の形になっていて、左から「項目」「状態」「影響」の 3 列だ。項目が「独立 golden (registry の acceptance)」、状態が「pipeline 内蔵検証のみ、別 golden 未作成」、影響が「work-tools 規約 5 の『差し替え』はまだできない」になる。

**許可の在りかも、止まっている理由も、どちらも出典の側に書いてある。** 推定が要らない。要るのは、この 1 行を「宣言が在る」「検査が内蔵である」「だから使われていない」の 3 つに割って、同じ形の経路がほかに何件あるかを数えることだけだ。

### 受け入れ検査が、入れ替える側と同じ束に在る

検査の置き場所も、記録のほうにはっきり書いてある。私の記録の README の 10 行目に「validate 重複 0 + 協会けんぽ 7,050 セル再計算一致 + 上流 47 支部一致が通らなければ exit≠0」とあり、12 行目に「全段通るまで本番 file を触らない」とある。33 行目と 34 行目は流れの説明で、「スケジューラが `pipeline.py` を週 1 回実行 → 上流 pull → 変換 → 検証 → 差分 → manifest」「検証に落ちれば `manifest.json.status = failed`、本番 `rules_unified.json` は前回のまま」と続く。

検査としては、これで筋が通っている。落ちれば本番は前のままだ。**ただしこの検査は、入れ替える側と同じ束の中に在る。** パイプラインを別の実装に入れ替えたら、受け入れ検査もいっしょに入れ替わってしまう。入れ替えた後の結果を受け止める側が残らないので、入れ替えてよいと書いてあっても手が出ない。

### 入れ替えの経路ごとに、跡の残り方が違う

跡のほうは、実行履歴を数えれば出る。履歴は 11 行あって、欄は `run_at` / `status` / `upstream` / `diff` / `sha256` / `error` の 6 つだ。

- **本番の行の差し替えは、跡が在り実績も在る。** `diff` の欄で、追加か削除か変更のどれかが 0 でない行が 4 行ある(初回の作成を除く)
- **上流の版の差し替えは、欄は在るが実績が無い。** 11 行すべての `upstream` が同じ commit で、通った回だけが並んでいる
- **実装の差し替えは、欄そのものが無い。** 6 つの欄のどれも「何を入れ替えたか」を書く場所ではない
- **呼び出しの跡も残らない。** 作業状況の記録の 129 行目に「CLI 実行時の event 追記 (work-tools 規約 4) | 未実装 | AI が呼ぶ時に手動追記の運用」とある

上流の版が動いていない理由も、推定しなくてよい。同じ記録の 130 行目に「スケジューラ登録 | `register_task.ps1` 未実行 (常駐設定の変更のため chai 実行待ち) | 現状は手動 `python pipeline.py`」と書いてある。**跡が 0 件なのは、経路が壊れているからではなく、通す段取りがまだ登録されていないからだ。** これも出典の側に在る。

### 同じ 1 行が、片方には許可で片方には禁止

もう 1 つ、同じ記録の 18 行目が面白い形をしている。「上流 clone (MIT)。script は実行しない、`src/data/*.json` を読むだけ (協会けんぽは照合専用)」とある。

許諾の側は MIT なので、実装の利用も許している。**それなのに、通す経路は data だけに限ると自分で宣言している。** つまり同じ 1 行が、data を通す経路には範囲つきの許可を出し、実装を通す経路には許さないと言っている。借りている範囲も 42 行目に書いてあって、雇用保険料率・最低賃金・労災・消費税の 4 つだけになる。

ここで気をつけたのは、**`照合専用` という注記の文字から範囲を当てない**ことだ。文字を読んで範囲を決める処理を入れると、言い回しが変わるたびに判定が変わる。道具が見るのは、人がもう 1 つの欄に記号で書いた「範囲に含める対象の種別」だけにした。

### 読む人に渡している許可も、同じ形をしている

最後に自分の側を見る。公開している repo の README の 106 行目には「[MIT License](LICENSE)。コード・図の生成器・生成した図・記事本文を含む repo 全体に適用します(第三者の再利用・改変・再配布を許可、著作権表示の保持のみ条件)」と書いてある。読む人は道具を入れ替えてよい。

**では、入れ替えられる状態になっているか。** 道具のテストは同じ repo の `tools` の下に入っている。つまり道具を別の実装に入れ替えると、受け入れ検査もいっしょに入れ替わる。私が借り物について書いたのと同じ形が、私が配るものにも在った。

## 図 1 入れ替えられると言える根拠が、どの層に何と書かれているか

![行を入れ替えの経路、列を「許可の根拠」「受け入れ検査の所属」「跡の欄と件数と 4 値」にして、各セルに出典をファイル名と行番号で置いた表](figures/swap_ready_map.png)

この図は論評ではなく、2 つの記録から取った一次記述を、経路ごとに 3 列へ割り直したものだ。行が入れ替えの経路 1 つ、1 列目が許可の根拠、2 列目が受け入れ検査の所属、3 列目が跡の欄と件数と 4 値になる。各セルに出典を行番号で置いた。

**入れ替えるべきかの列は置いていない。** 正しい側の列も、順位の列も無い。この図が答えるのは「どこに何と書いてあるか」までだ。

橙の 4 行が、宣言が使われないまま残っている経路になる。上から、上流の版(検査が内蔵)、上流の data(検査は独立だが跡が 0 件)、自前の抽出器(検査が内蔵で、しかも跡の欄が無い)、配った道具(検査が内蔵)の 4 つだ。藍の 1 行が、唯一「使われている」になった本番の行の差し替えで、`diff` の欄に 4 件の跡が残っている。

**2 列目の所属は、私が読んで記号に落としたものだ。** 上流の data と本番の行を独立だと読んだのは、突き合わせる相手が公式の表という別の束だからで、記録にその言葉で書いてあるわけではない。ここは読み手によって変わる。変わったときに 4 値がどう動くかは、後で verify の側で見る。

3 行目が、同じ 1 行から別の宣言が出た例になる。data を通す経路には範囲つきの許可、実装を通す経路には許さない。**線の外は未規定とは別の記号で返す**ので、この行は「まだ整備していない」の一覧には入らない。

## 手順

ひな型を出す。経路の台帳・受け入れ検査の台帳・跡の台帳の 3 枚と、記号の登録表 2 枚が出る。

```
python swap_ready.py init ひな型/
```

経路の台帳に、入れ替えたい経路を 1 行ずつ書く。

```csv
route_id,kind,bundle,permission,scope_note,scope_kinds,declared_on,source
R01,版,借り物の束,許す,—,—,2026-01-05,合成の経路のメモ(架空)L1
R03,data,借り物の束,範囲つきで許す,照合専用,data,2026-01-05,合成の経路のメモ(架空)L3
R04,実装,借り物の束,範囲つきで許す,照合専用,data,2026-01-05,合成の経路のメモ(架空)L4
```

`kind` が入れ替える対象の種別で、版・実装・data・行の 4 つしかない。`bundle` が入れ替える側の束の名前になる。`permission` は許す宣言の記号で、登録表に在る記号しか受け取らない。**`scope_note` と `scope_kinds` を分けたのが、この部品でいちばん迷ったところだ。** 前者は `照合専用` のような限定の文字列を生のまま置く欄で、後者は範囲に含める種別を記号で書く欄になる。上の R03 と R04 は注記が同じ `照合専用` で、違うのは通す対象の種別だけだ。R03 は範囲の中、R04 は範囲の外になる。

受け入れ検査の台帳が、この部品の要になる。

```csv
check_id,route_id,placement,bundle,source
C01,R01,内蔵,—,合成の検査のメモ(架空)L1
C03,R03,独立,照合用の束,合成の検査のメモ(架空)L3
C14,R13,独立,借り物の束,合成の検査のメモ(架空)L14
```

`placement` が所属の記号で、独立・内蔵・無いの 3 つだ。`bundle` は検査が在る束の名前で、**独立の宣言だけがこの欄を要求する。** 3 行目を見てほしい。独立と書いてあるのに、束の名前が入れ替える側(借り物の束)と同じになっている。**これは矛盾する宣言として別枠へ出る。** 独立かどうかを自己申告で決めさせず、束の名前を書かせて突き合わせる形にした。

跡の台帳には、入れ替わりの跡を残す欄と、その欄で何件観測できたかを書く。

```csv
route_id,field,observed,range,reason,source
R01,入れ替えの欄,3,11 行,,合成の跡のメモ(架空)L1
R03,版の欄,0,11 行,,合成の跡のメモ(架空)L3
R03,—,—,—,取りに行く段取りが未登録,合成の跡のメモ(架空)L4
R05,—,—,—,別の束の受け入れ検査がまだ無い,合成の跡のメモ(架空)L5
```

`field` が `—` の行は、**跡を数える行にはならないが、理由と出典は残る。** 3 行目がそれで、同じ経路に件数の行と理由の行を別々に置いている。件数と理由が別の場所に書かれていることが実際にあるので、出典を 1 つに押し込めない形にした。`reason` が空なら `理由の記載なし` が入る。**理由を言い当てる辞書も分類器も、この部品には無い。**

記号の登録表 2 枚で、「その記号が何を要求するか」を宣言する。

```csv
permission,means,requires,source
許す,入れ替えてよいと書かれている,宣言された日,合成の許す宣言の登録のメモ(架空)L1
範囲つきで許す,範囲を限って入れ替えてよいと書かれている,許可の範囲,合成の許す宣言の登録のメモ(架空)L2
許さない,入れ替えないと書かれている,—,合成の許す宣言の登録のメモ(架空)L3
```

4 値を付ける。基準日は呼び出し側が渡す(道具は時計を読まない)。

```
python swap_ready.py check 経路.csv 検査.csv 跡.csv 許す宣言.csv 検査の所属.csv 2026-09-20
```

入れ替えてよい経路の一覧は返らない。返るのは件数と分母と滞留の量だけで、**最後に並ぶ 10 行は消せない**。`report` にすると、経路ごとの一覧と、種別ごと・束ごとの内訳と、理由と、判定部分の指紋が付く。

4 値の決め方も書いておく。別枠が先に当たり(出典が空 → 記号が登録の外 → 要求する欄が空 → 矛盾する宣言 → 許可の範囲の外)、その後で許す側の宣言かを見る。許さないなら線の外、宣言なしなら未規定だ。許す側なら検査の所属を見て、独立でなければ (B)。独立なら跡の欄を見て、欄が無ければ別枠、件数が 1 以上なら (A)、ちょうど 0 なら (C) になる。

**跡の欄が無いことで別枠へ出るのは、許す宣言が在って検査も独立な経路だけ**にした。(A) か (C) のどちらかに分かれるはずの経路が、欄が無いせいで分かれないからだ。(B) や (D) の経路では、跡の欄の有無は列に出るだけで 4 値は変わらない。図 1 の 4 行目がその形で、4 値は (B)、跡の欄は `数えられない` になっている。

最後に、この手続き自体が決定論かを実測する。

```
python swap_ready.py verify 経路.csv 検査.csv 跡.csv 許す宣言.csv 検査の所属.csv 2026-09-20
```

`verify` は 5 つ見る。2 回読んで判定部分の指紋が同じか、5 枚の行順を 3 通りに入れ替えても同じ出力になるか、3 通りの数え方の合計が合うか、そして 2 つの差し替えだ。**1 件の跡の件数に 1 足す**と、その経路だけが (C) から (A) へ移ること。**1 件の検査の所属を内蔵から独立に変える**と、その経路だけが (B) から動くこと。どちらも写しはメモリの中だけで、5 枚の CSV には 1 文字も書かない。

## 検証

テストは 19 件で、測っているものは 8 つある。経路 14 件が 4 値と別枠に分かれる側、**許す側の宣言が在る 11 件のうち使われているのが 2 件だけ**という側(これが骨)、0 件と `数えられない` を別の値で返す側、独立の宣言が束の名前を要求する側、同じ注記でも範囲の外なら別枠へ出る側、跡に 1 足すと 1 件だけ動く側、所属を独立にすると 1 件だけ動く側、出力の末尾の「持たせていないもの」が 10 行そろっている側だ。4 値の分け方は、テストの側でも 5 枚の行から直に分類し直して確かめている。

読みどころは 4 つある。

ひとつめが、許す側の宣言が在る 11 件のうち、使われていたのが 2 件だったことだ。合成した表なので内訳そのものは私が作ったが、**作ってみて分かったのは、残り 9 件の止まり方が 3 種類に割れることのほうだった。** 検査が内蔵か無い (B) が 2 件、検査は独立だが跡が 0 件の (C) が 1 件、そして 4 値が付かない別枠が 6 件になる。前の 2 つは「何を足せばよいか」が違い、最後の 1 つは「台帳の書き方を直せ」という意味になる。同じ「まだできていない」でも、次にやることが別だ。

ふたつめが、0 件と `数えられない` の分かれ方になる。14 件のうち、跡の件数がちょうど 0 なのは 2 件だけで、`数えられない` は 10 件あった。**そして `数えられない` のうち別枠へ出たのは 1 件だけ**になる。許す宣言が在って検査も独立な経路だけが、欄が無いせいで (A) と (C) に分かれない。残りは (B) か (D) なので、跡の欄が無くても 4 値は決まる。ここを分けないと、「欄を足せ」という指摘が、欄を足しても何も変わらない経路にまで飛ぶ。

みっつめが、独立の宣言の扱いだ。R13 は独立と書いてあるのに、束の名前が入れ替える側と同じになっている。これを矛盾する宣言として別枠へ出した。**束の名前を別にすると、移るのは R13 の 1 件だけで、行き先は 4 値ではなく別枠「跡を残す欄そのものが無い」になる。** 独立だと認めても、まだ 4 値は付かない。跡を残す欄が無いからだ。足りないものが 2 つ重なっていたことが、この 1 件で見える。

よっつめが、2 つの差し替えの分かれ方になる。跡の件数に 1 足すと、(C) の経路が (A) へ 1 段上がる。検査の所属を独立にすると、(B) の経路は (A) ではなく (C) へ移る。**上がり方が 1 段ずつなのが、この部品の形をいちばんよく表している。** 検査を独立の束へ出しただけでは「入れ替えられる」までで、「入れ替えた跡が在る」にはならない。

いつも成り立つことは 1 文にして、性質テストで確かめている。読んだ範囲は 2 通りしかない。経路 1 件ごとに 4 値の 5 欄か別枠 6 のどれか 1 つが付き、その合計が経路の件数に等しく、種別ごとの内訳の合計も束ごとの内訳の合計も同じ数になり、許す側の宣言が無い経路は (A)(B)(C) に入らず、検査が独立でない経路は (A)(C) に入らず、跡の欄が無い経路は `数えられない` を返して 0 件と同じ値にならず、範囲つきで許す経路は通す対象の種別が範囲の記号の列に在るときだけ 4 値へ進み、5 枚の行順を 3 通りに入れ替えても同じバイト列になるか、1 経路も数えずに理由コードが返るか、だ。どちらの場合も 5 枚の表は 1 文字も書き換わらない。経路を 1 件から 3 件、検査と跡を経路ごとに 0 件から 2 件、記号は登録の中と外から引く。乱数は固定で、毎回同じ 200 通りになる。2 本目は「4 値を決めるのは許す宣言と検査の所属と跡の件数だけ」を注記の文字との総当たりで見ていて、上限は 300 にしてある。

書いている途中で 1 つ捕まえたのは、別枠と (D) の順番だった。**最初は許す側の宣言かどうかを先に見ていた。** そうすると、許さないと宣言された経路の出典が空でも、線の外として静かに通ってしまう。出典が無い行は、何が書いてあっても信用できないはずだ。性質テストが、出典が空で許さないと宣言された経路を作ってきて、分類がテスト側の別実装とずれた。そこで別枠を全部先に当てる順に直した。**宣言の中身を読む前に、その宣言に出典が在るかを見る。** 順番がそのまま規律になる。

段は 9 つで、橙のピルが関所になる。前の 3 段が数える前の検査で、表の形と登録の出典、経路 id の重複、記号が揃っているか、基準日と日付の向き、跡の件数が整数かを見ている。

この図で見てほしいのは、描かれていない経路のほうだ。**自分で入れ替える矢印が無い。** 実行する矢印も、import する矢印も、構文解析する矢印も、取りに行く矢印も、理由を言い当てる矢印も、推奨や順位や割合へ出る矢印も、検査の中身を読む矢印も、0 件と欄なしを同じ値にする矢印も、範囲つきの許可を許すへ寄せる矢印も、現在時刻を読む矢印も、入力を書き換える矢印も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

4 段目から 8 段目が本体になる。記号を登録表に当て、その記号が要求する欄が埋まっているかを見て、範囲と束を見比べ、許す側の宣言かを見て、最後に所属と跡で分ける。**別枠が 4 値より先に当たる**ので、台帳の書き方が足りない経路は 4 値の中に混ざらない。

9 段目で 3 通りの合計を検算する。4 値と別枠の合計、対象の種別ごとの合計、入れ替える側の束ごとの合計が、どれも経路の件数に戻る。**3 つは数えている切り口が違う**ので、片方を差し替えると合わなくなる。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/swap_ready) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。通信の経路も、現在時刻を読む呼び出しも、浮動小数点も持たない。

手元で書くのは 5 枚で、いちばん軽いのが記号の登録表 2 枚になる。許す宣言の記号 4 つと検査の所属記号 3 つを並べて、それぞれ何を要求するかを決めるだけだ。重いのは経路の台帳で、「何を」「どの束の中で」入れ替えるのかを 1 行ずつ書き分けるところになる。同じファイルを触る作業でも、版を入れ替えるのと実装を入れ替えるのは別の経路だ。

合成した 5 枚が置いてあるので、同じ数字が手元で出るかを確かめられる。**実在の名前も実在のパスも 1 つも入っていない。** 経路 id は記号、束の名前は「借り物の束 / 自前の束 / 本番の束 / 照合用の束」、出典は「合成の…(架空)」になる。崩した表も付けてあって、止まる理由コード 7 個と、表として読めない 7 通りに道が付いている。

使い方として想定しているのは、入れ替えの作業を見積もる前に 1 回通すことになる。出てきた 4 値の内訳が、そのまま「宣言のうちどれだけが使われていないか」を測る材料になる。**工数は出ない。出るのは経路ごとの 4 値と、跡の件数と、滞留の日数だけだ。**

## 別の業種なら

この部品が持っている欄は、経路 id・対象の種別・束の名前・許す宣言・許可の範囲・宣言された日・検査の所属・跡の欄・件数・理由・出典だけで、給与や社会保険の言葉は 1 つも入っていない。どの分野でも「ここは後で入れ替えられるように作った」と書いたのに入れ替えられない形は同じで、分かれ目は受け入れ検査がどちらの束に在るかになると考えている。会計なら、仕訳取込の実装を別の読み取り器に入れ替えてよいと書いても、残高一致の検査が取込器と同じ束にしか無ければ手が出ない(前期末残高を別の束に置いた検査が要る)。買い物の仕組みなら、送料計算を入れ替える前に、確定済みの請求額を別の束に置いて受け入れ検査にする。運送なら、距離と待機時間の計算に対して確定済みの運賃明細を独立の検査に回す。医療や介護なら、単位数計算の入れ替えに対して請求確定分を別の束に置く。製造なら、型番の読み替え表に対して出荷済みの対応実績を置く。私が測ったのは上の合成した 5 枚と、自分の記録から起こした 6 経路の範囲だけなので、ほかの分野は同じ詰まり方になりそうな例であって実測ではない。変わるのは入力例の語彙だけになると考えている。

## できないこと

- **入れ替えるべきかは分からない。** 4 値を付けるところまでで、どの経路をどう入れ替えるかは読む人が決める。(A) でも「入れ替えてよい」とは言っていない。入れ替えた先が正しく動くかを見ていないからだ
- **検査が十分かは分からない。** 見るのは所属だけで、検査の中身は読まない。独立な検査が 1 件在っても、それが入れ替えを受け止められるかは出力に出ない。走らせた結果を台帳に残すのは別の部品の仕事になる
- **滞留の理由は分からない。** 返るのは入力の注記の写しだけで、注記が無い経路は `理由の記載なし` になる。理由を言い当てない以上、「なぜ止まっているか」は人が書く側に残る
- **跡の件数が正しいかは分からない。** 台帳に人が書いた件数をそのまま使う。欄が無い経路は `数えられない` で、0 回なのか記録していないのかは言えない。言えないことを言えないまま返すのが、この部品の返り値になる
- **許可の範囲が正しく記号に落ちているかは分からない。** `照合専用` が何を許すかは人が別の欄に書く。注記と記号の列がずれていても道具は気づかない。文字から当てる経路を持たせなかったぶん、ここは人の側に残した
- **所属の読み替えは私の判断だ。** 図 1 の 2 列目で 2 件を独立だと読んだのは、突き合わせる相手が別の束だと私が判断したからで、記録にその言葉で書いてあるわけではない。ここが変われば 4 値も変わる
- 上の件数は合成した 5 枚と、自分の記録から起こした 6 経路に対する測定で、ほかの人の環境で同じ数字になるとは限らない
