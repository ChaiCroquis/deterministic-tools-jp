前回は、計算に要る行がそろう年を数える部品を作った。今回は年ではなく、計算そのものの境界を数える。骨は 1 行で言える。**値が返ってきたことと、その値で計算が終わっていることは別だ。行が無ければ例外で止まるが、式の節が未実装のときは値がそのまま返り、仕上げの一手だけが呼び出し側に残る。設計上そもそも表の外に置いたもの(人の判断・主体ごとの値・履歴の走査)も、返り値には現れない。だから引く前に、求める値ごとに「道具の中で済む」「返るが一手残る」「外から渡す前提」「止まる」の 4 つを境界の表 1 枚にして、線の外に何が在るかを数える。**

**なぜ重要か**: 道具を作った側は、できていないことを文書に書く。私もそうしてきた。けれど読む側に届くのは、呼んだときに返ってくる値と終了コードだけだ。私の引き当ての出口は 3 値しかなく、成功と、該当なし・入力不足と、表の不備に分かれている。**この 3 値には「値は返ったが、まだ上限を当てていない」という状態を入れる場所が無い。** そして実際に、私の記録にはその形の行が在る。年金の定額部分の式は呼べて値が返るが、月数の上限は呼び出し側で当てる作業が残る、と自分で書いている。終了コードは 0 で返る。何も言わずに。

**要点**:
- 求める値ごとに、要る節を並べて 4 つに分ける。道具の中で済む / 返るが一手残る / 外から渡す前提 / 止まる。値を計算せず、宣言を突き合わせるだけにする
- 未実装と設計上の外を同じ列に入れない。線の内側の未完成と、線の外に置いた設計判断は、やることが別になる
- 宣言表に無い節は判定しない。残りの節に収録済を当てて答えを作らず、別枠に出す
- 残る一手は名前と出典で返すだけにして、道具の側では埋めない。足すべき節も、着手の順も出さない

**数字で見る**: 合成した宣言表 11 行・レシピ表 12 行・問い 12 件を通すと、12 件が 道具の中で済む 2 / 返るが一手残る 3 / 外から渡す前提 3 / 止まる 3 / 宣言が無い 1 に分かれた。**値が返る問いは 8 件あり、そのうちその値で計算が終わっているのは 2 件だけだった。** 残る一手の一覧は 14 行で、問いの数より多い。同じ未実装の節を要る問いは 4 件あるのに、その節を収録済に替えて答えが動いたのは 1 件だけで、残り 3 件は別の一手に隠れていた。

## 何を解決するのか

引き当ての部品を作るとき、私は「引けない」を例外にした。黙って現行値を返さない、と決めたからだ。前回の回では、引く前に収録の端を数えるところまで作った。どちらも「引けるか」の話だった。

今回はその先にある、**引けた後の話**になる。

### 値が返るのに、計算が終わっていない

私の作業状況の文書に、こういう行がある。年金の定額部分の被保険者月数の上限について、状態は未実装で、数式は単価と乗率と月数の掛け算だけなので、呼び出し側で上限の適用が要る、と。

この行を初めて読み返したとき、私は少し驚いた。**未実装と書いてあるのに、値は返るのだ。** 式は在って呼べる。返ってきた数字は、上限を当てる前の数字になっている。呼んだ側がそれを知らなければ、上限を超えた金額をそのまま使ってしまう。

同じ文書の 1 行上には、報酬比例部分の乗率が画像の PDF で未抽出なので報酬比例額が計算できない、と書いてある。こちらは値が返らない。行が無いので例外になる。

**同じ年金の中で、引ける節と引けない節と、引けるが一手残る節が混ざっている。** そして出口はどれも同じ 3 値のどれかに落ちる。

### 設計上そもそも外に置いたものがある

もうひとつ別の形がある。

私の棚卸しの文書には、表に入らないものを分類した章がある。要件該当性の判断は、判断結果を case の属性として受け取る、人間か大規模言語モデルが起票する、表は属性が確定した後だけ動く、と書いてある。主体ごとのパラメータは同じ行形式の第 2 層を持つ、状態遷移は数式側が状態機械を持って表からは閾値と率だけ供給する、とも。

これらは未完成ではない。**線の外に置くと決めたものだ。** けれど呼んだ側から見ると、未実装と見分けがつかない。どちらも「返り値には現れない何か」として同じに見える。

**違うのは、やることだ。** 未実装なら、いずれ私が実装すれば消える。設計上の外なら、誰が何年やっても消えない。呼ぶたびに外から渡す。この 2 つを足して「できていないことが n 件」と数えると、消える数と消えない数が混ざる。

### この回と、前の回の違い

自分の道具の「できないこと」の宣言とソースの経路を突き合わせる回を、前に書いた。あれは**できないと書いたことが本当に無いか**を見る道具で、対象はソースの側だった。今回は向きが逆で、**できると答える値の側に残っている一手**を数える。取りに行く前の取得の地図を作る回は、線の位置が取得の側にあった。前回の年の在庫は、端が仮置きかどうかを別枠にしていて、そちらはそちらの仕事になる。

## 図 1 線の外に何が在るかを 1 行 1 件に並べる

![手元の 3 つの文書から拾った 11 件を、領域と節 / 原文 / 4 値のどこに出るか / 出典 の 4 列で並べた一覧表](figures/handoff_edge_map.png)

この図は論評ではなく一覧だ。手元の 3 つの文書から拾えた行を、そのまま並べてある。引用は要約せず原文のまま置き、出典はファイル名を伏せた行番号で書いた。

読みどころは 3 つある。

ひとつめが、右から 2 列目の色の分かれ方だ。藍の 3 行は値が返る。橙の 5 行は値が返らない。無彩の 3 行は、そもそも返り値に現れない。**どれも元の文書では「できていないこと」として同じ表に並んでいる。** 並べ直して初めて 3 つに割れる。

ふたつめが、藍の 3 行の中身になる。月数の上限、独立した受け入れ検査、呼んだときの記録の追記。この 3 つは、呼べば値が返り、終了コードは 0 になる。**何も起きていないように見える。** 外に残っているのは、上限を当てる作業と、検査を別に作る作業と、手で追記する作業だ。

みっつめが、数式の実装についての行だ。棚卸しの文書には数式の実装が未実装で id の文字列だけ、と書いてある。ところが作業状況の文書には数式が 14 ある、と書いてある。**どちらも私が書いた文書で、日付が 1 日違う。** 1 日のあいだに実装が入った、というだけのことだが、同じ問いに対して文書が 2 つの答えを持っている状態ではある。境界の表を作るなら、どの文書のどの行を宣言として採るかを決めるところから始まる。

収集範囲の限界も書いておく。見たのは手元の 3 つの文書と、公開済みの自分の記事までだ。条文も官報も実装のコードも見ていない。原文自身が、値は未取得で、棚卸しの各行は出典 URL の照合前で、条文照合は未実施だと書いている。だから**この一覧は網羅ではなく、手元の文書に書かれた範囲の一覧**だ。件数は丸めていない。この型はふつう各行に URL を求めるが、ここに URL は無く、ファイル名を伏せた行番号と原文の日付で代えている。料率も金額も、記事にも図にも 1 つも出していない。収録の規模だけは原文から引くと、1,681 行 / 45 rule になる。

## 手順

ひな型を出す。守備範囲の宣言表とレシピ表と問いの一覧の 3 枚が出る。

```
python handoff_edge.py init ひな型/
```

守備範囲の宣言表には、節 1 つを 1 行で書く。節というのは 1 つの rule か 1 つの式のことで、求める値より細かい単位になる。

```csv
node_id,belongs_to,state,exit,remaining_step,source
N01,合成の rule 甲(架空),収録済,値が返る,,私の設計メモ / 私の設計の記録(非公開)
N03,合成の式 丙(架空),未実装,値が返る,上限を当てる,articles/30_cover_stock.md L14
N04,合成の rule 丁(架空),未対応,止まる,乗率を取ってくる,私の設計の記録(非公開)
N05,合成の rule 戊(架空),設計上の外,値が返る,判断を属性で渡す,articles/18_scope_ledger.md L32
```

`state` が節の状態で、登録してあるのは 収録済 / 未実装 / 未対応 / 設計上の外 の 4 つだけだ。**ここに無い状態を書くと止まる。空欄も止まる。収録済を既定として当てる経路は無い。** `exit` が出口で、値が返るか止まるかのどちらかを書く。`remaining_step` が呼び出し側に残る一手の名前で、収録済以外の行には要る。

ここが仕掛けになっている。**収録済で出口が止まる行は止まる。** 収録してあるのに引けないという宣言は、宣言として矛盾しているからだ。**逆に、未実装で値が返る行は矛盾ではない。** 通さないと、この記事の骨そのものが書けなくなる。

計算のレシピ表には、求める値 1 つに要る節を並べる。

```csv
value_id,node_ids,source
V02,N01|N02,私の設計の記録(非公開)
V05,N01|N04,私の設計の記録(非公開)
V07,N01|N03|N05,私の設計の記録(非公開)
V10,N01|N99,私の設計の記録(非公開)
```

`V07` は 3 つの節を要る値で、その 3 つが別の答えを返す。あとでこれが出てくる。`V10` が参照している `N99` は宣言表に無い。

問いの一覧には、訊きたい値を並べる。

```csv
value_id,source,swap
V01,私の設計メモ / 私の設計の記録(非公開),逆順
V02,私の設計の記録(非公開),
```

まず数える。

```
python handoff_edge.py check 守備範囲の宣言表.csv 計算のレシピ表.csv 問いの一覧.csv
```

```

 "完成度の割合を出さない": "出すのは件数と 2 つの分母の内訳だけで …",
 "状態に既定を当てない": "宣言表に無い節を参照している問いは別枠に出す …",

```

何割できているかを返す呼び方は無い。件数には必ず分母の内訳が付くし、**最後の 7 行は消せない。** `edge` にすると、問いごとの内訳に加えて**残る一手の一覧**が出る。1 行 1 件で、求める値 / 節 / 状態 / 残る一手の名前 / 出典 の 5 列だ。**どれから手を付けるべきかの順位は付かない。**

節を集めて 1 つの値にするとき、順番がある。手前の関門が勝つ順で、宣言が無い、止まる、外から渡す前提、返るが一手残る、道具の中で済む、と並ぶ。**この順番そのものが仕様だ。** 宣言が無いのは、そもそも判定できないから先頭に置く。止まるは値が 1 つも返らないので、いちばん強い言い方として次に置く。外から渡す前提は、呼ぶ前に渡しておく一手なので、返ってから残る一手より時間の順で手前になる。

最後に、この手続き自体が決定論かどうかを実測する。

```
python handoff_edge.py verify 守備範囲の宣言表.csv 計算のレシピ表.csv 問いの一覧.csv
```

`verify` は 5 つ見る。2 回読んで判定部分のバイト列の指紋が同じか、宣言された入れ替え方で 3 枚の行順を入れ替えても同じ出力になるか、件数の合計が合うか、そして 2 つの写しだ。**状態を未実装から収録済に替えた写し**では、動く辺が「返るが一手残る → 道具の中で済む」の 1 本だけであることを見る。**節を 1 つ宣言表から外した写し**では、別枠が増えた分だけほかの 4 値が減ることを見る。後の 2 つは、この部品が自分で自分を崩しにいく検算になっている。写しはメモリの中だけで、入力の表には 1 文字も書かない。

読みどころは 4 つある。

ひとつめが、値が返る 8 件の分かれ方だ。計算が終わっているのは 2 件だけで、6 件は値が返ってから一手が残る。**終了コードで見れば 8 件とも 0 だ。** 分けているのは終了コードではなく、節ごとの宣言になる。

ふたつめが、残る一手の数になる。問いは 12 件なのに、一覧は 14 行ある。1 つの問いに 2 つ残ることがあるからだ。さらに、値が返らない止まる問い 3 件にも一手が 5 件載っている。**止まったから何も要らない、ではない。** 行を足す作業や、乗率を取ってくる作業が外に残っている。

みっつめが、隠れる一手だ。同じ未実装の節を要る問いは 4 件あるのに、その 4 件の答えは 3 通りに分かれている。返るが一手残るが 2 件、外から渡す前提が 1 件、止まるが 1 件だ。**手前により強い関門があると、未実装の一手は答えの側に出てこない。** だからその節を収録済に替えても、動いたのは 1 件だけだった。残り 3 件は、別の一手が片付くまで動かない。節ごとの内訳を残しているのは、この隠れた分を数えるためになる。

よっつめが、崩しの向きだ。状態を直すと「返るが一手残る → 道具の中で済む」の 1 本しか動かない。節を外すと別枠へしか動かない。**どちらも、動いてはいけない向きに動かないことを測っている。** 直したら急に別の値へ飛ぶなら、どこかで勝手に既定を当てていることになる。

いつも成り立つことは 1 文にして、性質テストで確かめている。読んだ範囲は 2 通りしかない。問いごとに 5 値が 1 つだけ付き、5 値の合計が問いの数に等しく、節の判定別の合計が判定した節の延べ数に等しく、別枠の問いは節を 1 つも判定せず、状態を未実装から収録済に替えると 1 本しか動かず、節を外すと別枠へしか動かず、判定部分に時刻もホスト名も絶対パスも入らず、3 枚の行順を入れ替えても同じバイト列になるか、1 件も判定せずに理由コードが返るか、だ。どちらの場合も入力は 1 文字も書き換わらない。節を 1 つから 3 つ作って状態と出口と残る一手の 3 つ組を整合するものから引き、レシピを 1 本から 3 本、要る節を 1 つから 3 つ引く。問いは 1 件から 2 件。3 割くらいの確率でどこか 1 か所を崩す。乱数は固定で、毎回同じ 200 通りになる。**節の判定と問いの 5 値はテストの側で別に実装している**(部品の判定を呼ばない)。同じファイルの 2 本目は 300 通りで、宣言表に無い節に収録済を当てないことを見ている。

この性質テストは、書いている途中で 1 つ私の思い違いを捕まえた。状態を未実装から収録済に替える写しで、出口が止まるの節まで一緒に替えてしまうと、止まるから道具の中で済むへ 2 段飛ぶ問いが出る。**「一手が消えた分だけ中で済むが増えた」という読みにならない。** だから替えるのは、未実装で、いま値が返っている節だけにした。

## 図 2 判定するまでの流れと、止まる場所

![3 枚の表を読み、出典と id と宣言を見て、問いごとに節を集めて 5 値に分けるまでの流れ図](figures/handoff_edge_flow.png)

段は 6 つで、橙のピルが関所になる。前の 3 段は判定の前の検査で、表の形と出典と id、それに状態と出口の宣言が登録のものかを見ている。

この図で見てほしいのは、描かれていない経路のほうだ。**状態の空欄から「とりあえず収録済にする」へ出る矢印が無い。** 未実装と設計上の外から同じ列へ合流する矢印も無い。残る一手の空欄から「道具が名前を書く」へ出る矢印も無い。件数から「足すべき節を出す」「着手の順を出す」へ出る矢印も無い。4 値から「終了コードに写す」へ出る矢印も無い。値を計算する矢印も、式を評価する矢印も、行を引く矢印も無い。割合を返す矢印も無い。実装でも同じで、そういう引数を持たせていないから、落ちる先が無く、落ちる経路も書けない。

4 段目が、この回の本体になる。問いごとに要る節を集めて、宣言表に無い節が 1 つでもあれば別枠へ出す。**このとき、残りの節の判定も出さない。** 2 つの節のうち 1 つが宣言表に在って収録済だったとしても、もう 1 つが無ければ「半分はできている」とは言わない。言えるのは、判定できない、だけだ。

5 段目で 1 つの値にする。節ごとの内訳は 5 値とは別に全部残るので、**どの節がどの理由で外に出たかは潰れない。** 1 つの値に畳むのは読むためで、畳んだ結果しか返さないわけではない。

最後に、この図の関所がぜんぶこの部品自身の話であることを書いておく。**宣言表が 1 行でも壊れていたら、どの問いも判定しない。** 5 値は全て 0 になり、理由コードだけが返る。測っている相手の「止まる」の欄に、この部品の「読めない」を混ぜないためだ。同じことを相手にも求めているのだから、自分の側でやらないわけにはいかない。

## 道具

道具は [GitHub](https://github.com/ChaiCroquis/deterministic-tools-jp/tree/main/tools/handoff_edge) にある。ライセンスは MIT で、自由に使える。標準ライブラリだけで動く(テストの実行には pytest と hypothesis が要る)。

手元で書くのは、守備範囲の宣言表とレシピ表と問いの一覧の 3 枚だけだ。合成した表が置き場に入っているので、同じ数字が手元で出るかを確かめられる。**実在の料率も金額も 1 つも入っていない。** 節 id も rule の名前も架空で、値も日付も 1 つも入っていない。写したのは形だけで、状態が 4 種に分かれていること、未実装なのに値が返る節が在ること、設計上の外に置いた節が在ること、レシピの参照先が宣言表に無いことが在ること、の 4 つだ。

使い方として想定しているのは、道具を人に渡す前に 1 回通すことだ。道具の中で済む値だけが、渡した相手がそのまま使える値になる。返るが一手残るが出たら、その一手の名前を渡す相手に伝える。外から渡す前提が出たら、それは不足ではなく線の引き方なので、線の位置を伝える。止まるが出たら、値は返らない。宣言が無いが出たら、まだ境界の表の側が書けていない。**何割できているかは出ない。出るのは、線の外に何が在るかの一覧だけだ。**

## 別の業種なら

この部品が持っている欄は、節 id・属する rule または式 id・状態・出口・残る一手の名前・出典だけで、給与や社会保険の言葉は 1 つも入っていない。会計なら、仕訳や試算表を出す道具が、税率は引けるが交際費の損金不算入の判定は外から渡してもらう前提で止まり、返ってきた金額を見てもその一手が残っているとは分からない。買い物の仕組みなら、送料と手数料は表から引けるがクーポンの併用可否は人が決める前提で、注文 1 件の金額が返っても併用の判定が外に残る。運送なら、距離と重量の運賃は引けるが待機料と付帯作業の認定が外に残る。医療や介護なら、報酬の単価は引けるが算定要件の該当性(人員配置や記録の有無)が外に残る。建設なら、労務単価は引けるが現場ごとの歩掛の補正が外に残る。どれも「表から引ける部分」「表に在るのに未完成の部分」「設計上そもそも外に置いた部分」「行が無くて止まる部分」の 4 つが同じなので、同じ部品がそのまま使えると考えている。私が測ったのは上の合成した 3 枚の範囲だけなので、ほかの分野は同じ詰まり方になりそうな例であって実測ではない。変わるのは表に書く中身だけで、入力例の言葉を替えればそのまま動く。

## できないこと

- 判定したことは「道具の中で済む節と、外に残る一手がどれか」までで、**残る一手を道具側では埋めない**。上限を当てる引数も、代わりの式を選ぶ経路も無い
- **足すべき節も、着手の順も提案しない。** 件数と一覧が残るだけだ
- **何割できているかを出さない。** 言えるのは宣言表に書かれた節の範囲までで、割合を返す経路が無い
- **宣言が本当かどうかは判定しない。** 宣言表に収録済と書けばそう数える。宣言とソースを突き合わせるのは別の回の道具の仕事で、ここは宣言を読む側に立つ
- **実在の料率や金額がいくらかも言わない。** 値の欄そのものを持っていない
- **端が仮置きかどうかも、引ける年も見ない。** 日付の欄を持っていない
- 図 1 の分け方は、手元の 3 つの文書と公開済みの記事に書かれている行までを拾ったもので、条文も官報も実装のコードも見ていない。原文自身が、値は未取得で、棚卸しの各行は出典 URL の照合前だと書いている
- 上の件数は、合成した 3 枚の表に対する測定で、他の人の環境で同じ数字になるとは限らない
