# cross_route — 同じ値を 2 つの経路で取った行を突き合わせる(どちらが正しいかは選ばない)

原本から値 1 件を取り出す部品([source_pin](../source_pin))は、その値が原本の指定場所に書いてあることまでしか
言えない。取り出した値が合っているかは原本の中では確かめられないので、次の手は **同じ値を別の経路で
もう 1 回取って突き合わせる** ことになる。

そこで値が違ったとき、人がまずやるのは「どちらが正しいか」を選ぶことだ。だが私の記録に残っている
食い違いの実例は、**別の制度の数字を同じ名前で並べていた** = 指しているものが違っただけだった。
だからこの部品は、値を比べる前に「同じものを指しているか」を検査し、宣言が足りない行は比べずに止める。

## 経路 1 本の行

| 列 | 中身 |
|---|---|
| `key` | 何の値か(2 経路の突き合わせはこの名前で行う) |
| `value` | その経路が出した値(`normalizer` を通して比べる) |
| `unit` | 単位。一方でも空欄 / 不一致なら比べない |
| `scope` | **その値が指しているもの**(対象の範囲・負担区分など)を呼び出し側が文字列で宣言する。部品は業種の語彙を持たない |
| `source_file` | 出典のファイル |
| `source_sha256` | 出典の sha256(**現物は見ない** = [source_pin](../source_pin) の仕事。報告に載せるために持つ) |
| `normalizer` | `value` を比較の形にする正規化の名前。`+` で連ねる。**既定は無い** |
| `captured_at` | 取り出した時刻 |
| `raw_text` | 原本にある生の文字(持ち越すだけ。比較には使わない) |
| `locator` | 原本の中の場所(持ち越すだけ。比較には使わない) |
| `note` | 覚え書き |

入力は CSV でも JSON でもよい。[source_pin](../source_pin) のピン行に `unit` と `scope` の 2 列を足せば
そのまま経路の行として読める(`raw_text` / `locator` / `method` / `source_kind` は持ち越すだけ)。

## 突合の順序(この順を変えない)

- ① 両方の行の `normalizer` の名前を通して `value` を正規化する。**`normalizer` が空欄の行は比べずに止める**
- ② `key` が一致しても、`scope` か `unit` が一方でも空欄 / 不一致なら比較に進まない。つまり **値が合うかより先に「同じものを指しているか」を見る**
- ③ ②を通った組だけ `value` を比べる

## 判定は 4 値

| 判定 | 何が起きたか |
|---|---|
| `agree` | 両経路に 1 行ずつあり、指しているものが同じで、正規化後の `value` が一致した |
| `disagree` | 指しているものは同じだが、正規化後の `value` が違った |
| `single_route` | 片方の経路にしか無い(= 照合できていない) |
| `incomparable` | 比べられない(`scope`・`unit` の不一致 / 空欄、`normalizer` 空欄 など) |

**`disagree` のときにどちらかを正として返す経路を持たない。** 優先する経路を選ぶ引数(`prefer` /
`authoritative` / `fallback` に相当するもの)も、片方へ落ちる引数も無い。`get(key)` は `agree` の行だけ
値を返し、それ以外は理由コードで止める。これは関数の引数の形と CLI の option の集合をテストで固定してある。

## 正規化(名前で呼ぶ。部品は既定を持たない)

`そのまま` / `全角半角`(NFKC)/ `カンマ除去` / `パーセント` / `円` / `桁そろえ` / `日付`。`+` で左から順に適用する。

`桁そろえ` は **末尾の 0 をそろえるだけ**(`9.310` と `9.31` を同じ形にする)で、桁を落とす丸めはしない
(`9.315` は `9.315` のまま)。2 経路で桁の書き方が違うのはよくあるが、それを黙って同じ扱いにはせず、
`桁そろえ` と名前で書かせる。名前が空欄の行は、値がたまたま一致していても比べずに止める
(丸めの規律は [formula_table](../formula_table)、正規化の規律は [source_pin](../source_pin) と同じ考え方)。

## いつも成り立つこと

`get(key)` が値を返すのは、**その key が両方の経路にちょうど 1 行ずつあり、比較に使う列(`value` / `source_file` / `captured_at`)がどちらも空でなく、両方の `normalizer` が登録済みの名前で空欄でなく通せて、`scope` がどちらも空でなく一致し、`unit` がどちらも空でなく一致し、名前で指定した正規化を通した `value` が両経路で文字として一致する組だけ**で、それ以外(`disagree`・`single_route`・`incomparable`・突合前の呼び出し)は**値を返さず `CrossError` で止まり、どちらかを正として選ぶ経路は無い**。

この 1 文は `tests/test_cross_route_property.py` が性質テスト(hypothesis)で確かめている。2 経路の表を
毎回乱数で作り直す。値は「正規化したあとの答え」を先に決め、そこから各経路が持つ `value` と正規化の
名前を組み立てる(`9.31` から `9.31%` + `パーセント`、`9.3100` + `桁そろえ`、`2017年4月1日` + `日付` を作る、
など)ので、期待値は道具の `normalize` / `crosscheck` / `rate` を通さずに分かる。両方にある組の 3 割くらいに
1 か所だけ困りごと(別の値にする・`scope` を空 / 別の区分にする・`unit` を変える / 空にする・`normalizer` を
空欄 / 登録外の名前 / `そのまま` に変える・`captured_at` や `source_file` を空にする・正規化を通せない
`value` を入れる・同じ `key` を 2 行にする)を入れ、片方の経路にしか無い組も混ぜて、毎回この 1 文が
成り立つかを見る(乱数は固定で、毎回同じ 200 通り)。

同じファイルの 2 本目の性質テストは **分母の恒等式** を見る。`agree` + `disagree` + `single_route` +
`incomparable` が常に突合表の行数に等しく、照合できていない行を分母から外した一致率は、全ての行を
分母にした一致率を下回らない(= 狭い分母だけを引用すると一致率は必ず上振れする側に出る)。

決まった fixture を 1 か所ずつ書き換える `test_measure_tampering` と違い、どちらも 2 経路の表を毎回
作り直す。テストの実行には pytest と hypothesis が要る(道具そのものは標準ライブラリだけで動く)。

## 一致率は分子分母だけでは返らない

`rate()` は一致率を出すが、**`agree ÷ (agree + disagree)` だけを単独で返す呼び方を持たない**。4 判定の
件数と、分母に何を含めたかの文字列を必ず同時に返す。

```
{"agree": 7, "disagree": 1, "single_route": 3, "incomparable": 4,
 "rows": 15, "compared": 8, "unchecked": 7,
 "一致率_比べられた行のみ": "0.8750", "一致率_全ての行": "0.4667",
 "分母に含めたもの": "比べられた行のみ = agree 7 + disagree 1 = 8(照合できていない 7 行 = 片系統だけ 3
                   + 比べられない 4 を除いた分母) / 全ての行 = 15(照合できていない 7 行を含む分母)"}
```

照合できていない行を分母から落とすと、同じデータで `0.4667` が `0.8750` になる。だから片方だけを
引用できない形にしてある。

## 止まる理由コード(9 つ)

| 理由コード | 何が起きたか |
|---|---|
| 経路名が同じ | 2 つの経路に同じ名前が付いている。報告のどちらの列がどの経路か決まらない |
| 同じ key が同じ経路に 2 行 | 片方の経路に同じ `key` が 2 行ある。その経路の値が表から決まらない |
| 列が足りない | 経路の行として読めない(必要な列が空 / 登録されていない `normalizer` 名 / `key` が空) |
| normalizer 空欄 | 正規化の名前が書かれていない。既定を持たないので比べない |
| normalizer を通せない | 名前の正規化が `value` を扱えない(数として読めない / 年月日として読めない) |
| scope 空欄 | その値が何を指しているかの宣言が無い。**値が合うかより先にここで止める** |
| scope 不一致 | 2 経路が別のものを指している(対象・負担区分が違う)。値を比べない |
| unit 不一致 | 単位が違う、または一方が空欄。値を比べない |
| 突合前に get を呼んだ | `crosscheck()` を通る前に値を取りに来た |

`single_route`(片方の経路にしか無い)は理由コードではなく **記録** として扱う。片系統だけの行があっても
`check` は止まらない(終了コード `0`)。異常にしてしまうと、照合相手が無い行を表から消す動機が生まれる。

## 使い方

```
python -X utf8 cross_route.py init route_a.csv                                  # 見出しを書き出す
python -X utf8 cross_route.py check  fixtures/route_a.csv fixtures/route_b.csv  # 4 値で判定
python -X utf8 cross_route.py report fixtures/route_a.csv fixtures/route_b.csv --format csv
python -X utf8 cross_route.py rate   fixtures/route_a.csv fixtures/route_b.csv  # 件数 + 2 つの分母
python -X utf8 cross_route.py get    fixtures/route_a.csv fixtures/route_b.csv 料率_地域I
```

経路の名前は `--name-a` / `--name-b` で付ける(既定はファイル名)。終了コード: `0` = 人が見る行が無い
(`agree` と `single_route` だけ)/ `3` = `disagree` か `incomparable` がある / `2` = 経路の表が読めない。

関数で呼ぶなら `Route.load` / `crosscheck` / `Cross.get` / `Cross.report` / `Cross.rate` / `normalize`。

## 試験

```
python -m pytest tools/cross_route -q
```

fixture は全て合成データ(`fixtures/make_fixtures.py`)で、値も区分名も出典名も架空。実在の料率・限度額・
最低賃金は入っていない。出典の列(`source_sha256`)は合成の原本 3 ファイルの現物から `hashlib` で計算して
いるので、表と出典は内部で噛み合う(部品は現物を読まないが、fixture の噛み合いはテストで見ている)。

後半の `test_measure_*` が記事の数値の出どころ。決定論なので、値が変われば記事の数字も変える。

## できないこと

- **原本が同じなら、2 経路でも原本側の誤りは捕まらない。** 両方の経路の値を同じように書き換えると `agree` のまま通る(測定の 16 通りのうち、判定が変わらなかった 1 通りがこれ)
- 値そのものの正しさ・どちらの経路が信頼できるかは判定しない(同じものを指しているか、指しているなら合うかだけ)
- `scope` は人が書く。書き方が揃っていなければ同じものでも `scope 不一致` になるし、違うものに同じ `scope` を書けば比べてしまう。ここは機械では決まらない
- 出典ファイルの現物・sha256 は見ない(列として持ち越して報告に載せるだけ)。原本との接地は [source_pin](../source_pin) の仕事
- 2 経路の独立性は測れない。片方が他方からコピーしたものでも、表の上では 2 経路に見える
- 依存は標準ライブラリだけ(`csv` / `json` / `hashlib` / `unicodedata` / `decimal` / `argparse`)
